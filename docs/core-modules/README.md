# 핵심 모듈 기록 현황

핵심 모듈 여섯은 소유자가 「무엇을 하는지, 왜 이렇게 했는지, 실패하면 어떻게 되는지」를 직접 쓰고 재현 시험 하나를 돌린다(설계 허브 DEC-0079 D3). 기록은 병합 조건이 아니고 병합 뒤에 쓴다(DEC-0088). 이 표가 아직 쓰지 않은 기록을 보여 준다.

1. 첫 병합을 하는 AI는 그 모듈의 상태를 「기록 미작성」으로 바꾼다. 병합한 PR 번호를 함께 적는 것은 v0.3 제안이다.
2. 소유자가 `docs/core-modules/<번호>-<이름>.md`에 기록을 쓰고 재현 시험을 돌린 뒤 상태를 「기록 있음」으로 바꾼다.
3. AI는 기록을 대신 쓰지 않는다. 빈 칸을 가리키는 질문까지만 한다.

「기록 미작성」이 셋 이상 쌓이면 DEC-0088의 재검토 조건에 따라 개발 방식을 다시 본다.

| 번호 | 모듈 | 상태 | 첫 병합 PR | 기록 |
|---|---|---|---|---|
| 1 | 업무 판정: 작업 상태 전이·권한·승인 | 기록 미작성. 1단계 둘째 묶음: 사람이 작업을 계약의 단계 표대로 넘기고(`Workflow.kt`), 조직이 쓰지 않는 검토 단계는 서버가 지나가게 하며, 바꾸는 요청마다 `version`을 확인한다. 1단계 셋째 묶음 첫 판: 맡길 수 있는지(여기서 만든 수행 준비 작업, 살아 있는 실행 없음)를 서버가 이유와 함께 정하고, 위임한 실행이 시작되면 수행으로, 결과를 내면 결과 검토(쓰지 않으면 완료)로 서버가 옮긴다. 승인·업무 기준은 아직 없다 | #17 | — |
| 2 | 실행 계약과 로컬 연결 프로그램: 작업 청구·중복 방지·재개·종료 | 기록 미작성. 설치·호환 시험용 최소 구현: 서버 쪽 청구·세대 번호·중복 사건 거르기(#3), 연결 프로그램 쪽 청구·보고 묶음·표식 확인 종료(#4). 1단계 셋째 묶음 첫 판: 사람이 작업을 위임하면 서버가 위임과 실행 지시를 만들고, 위임이 정한 기기만 청구하며(기한 8시간, 철회·거두기), 연결 프로그램(`zm-baton agent`)은 이 기기에 등록한 저장소의 위임만 가져가 실행마다 새 Git 작업 트리와 전용 브랜치에서 돌린다. 끝나도 커밋하거나 작업 트리를 지우지 않는다. 실행이 시작되면 작업이 수행으로, 결과를 내면 결과 검토(또는 완료)로 넘어간다. 재개·실행 중 취소·임대 갱신은 아직 없다 | #3 | — |
| 3 | 실행기 어댑터와 실행 보고 표준 | 기록 미작성. 설치·호환 시험용 최소 구현: Claude Code의 stream-json 출력을 계약의 활동 종류로 바꾸기. 1단계 셋째 묶음 첫 판: 실행 보고 `protocol_version` 2(종료 보고의 `executor_started`, Git 변경 목록 `git_changes`의 `files`·`base_overlap`·`base_branch_overlap`), 실행 시도 기록의 작업 트리(저장소·기준 커밋·전용 브랜치), 위임의 도구를 `--allowedTools`로 넘기고 `--restricted`로 사용자 설정이 넓히지 못하게 하기, 보고에서 작업 트리 경로 빼기 | #4 | — |
