# 핵심 모듈 기록 현황

핵심 모듈 여섯은 소유자가 「무엇을 하는지, 왜 이렇게 했는지, 실패하면 어떻게 되는지」를 직접 쓰고 재현 시험 하나를 돌린다(설계 허브 DEC-0079 D3). 기록은 병합 조건이 아니고 병합 뒤에 쓴다(DEC-0088). 이 표가 아직 쓰지 않은 기록을 보여 준다.

1. 첫 병합을 하는 AI는 그 모듈의 상태를 「기록 미작성」으로 바꾼다. 병합한 PR 번호를 함께 적는 것은 v0.3 제안이다.
2. 소유자가 `docs/core-modules/<번호>-<이름>.md`에 기록을 쓰고 재현 시험을 돌린 뒤 상태를 「기록 있음」으로 바꾼다.
3. AI는 기록을 대신 쓰지 않는다. 빈 칸을 가리키는 질문까지만 한다.

「기록 미작성」이 셋 이상 쌓이면 DEC-0088의 재검토 조건에 따라 개발 방식을 다시 본다.

| 번호 | 모듈 | 상태 | 첫 병합 PR | 기록 |
|---|---|---|---|---|
| 1 | 업무 판정: 작업 상태 전이·권한·승인 | 기록 미작성. 1단계 둘째 묶음: 사람이 작업을 계약의 단계 표대로 넘기고(`Workflow.kt`), 조직이 쓰지 않는 검토 단계는 서버가 지나가게 하며, 바꾸는 요청마다 `version`을 확인한다. 1단계 셋째 묶음 첫 판: 맡길 수 있는지(여기서 만든 수행 준비 작업, 살아 있는 실행 없음)를 서버가 이유와 함께 정하고, 위임한 실행이 시작되면 수행으로, 결과를 내면 결과 검토(쓰지 않으면 완료)로 서버가 옮긴다. 셋째 묶음 둘째 판: AI가 돌린 수행 작업은 이어서 맡기고(끊김·취소 뒤, 돌려보낸 결과), 결과 검토의 결과는 이유를 받아 돌려보내며 같은 요청으로 이어서 맡긴다. 사람이 수행하던 작업과 살아 있는 실행이 있는 작업은 이유와 함께 거절한다. 살아 있는 실행이 있으면 작업 취소를 막고 「실행 취소」로 먼저 멈추게 한다. 결정 쓰기(`work/decisions-write`): 여기서 만든 결정의 제안·고치기·채택·기각·대체 규칙(`DecisionRules.kt`)과 승인자를 정하는 한 곳(`Approvals.kt`의 `ApprovalPolicy`, 1단계는 소유자)이 생겼고, 채택·기각은 승인 기록(`approvals`)으로 남는다. 문서(`work/documents`): 문서판은 초안으로 시작해 승인자가 한 번 승인하고(`DocumentRules.kt`), 같은 승인 기록에 남는다. 사람 검토 고르기(`work/review-pick`): 맡긴 실행의 결과를 스냅샷 커밋에 고정하고 위험 경로 패턴과 맞춰 사람 검토 요청을 만들거나 표본으로 뽑고, 나머지는 「사람 미확인」으로 둔다(`RiskPaths.kt`, `Reviews.kt`). 열린 위험 요청이 있으면 결과 검토를 건너뛰지 않고 완료로 옮기지 못하게 하며(`Workflow.kt`), 사람만 승인·반려하고 AI 주체의 판정은 거절해 감사 기록에 남긴다. 반려는 마지막 결과의 결과 검토일 때만 작업을 수행으로 돌리고(반려 이유가 이어서 맡긴 실행의 지시에 들어간다), 완료된 작업의 표본 반려는 고침 작업을 만들고, 나머지는 기록만 한다. 위험 목록은 사람만 고치고 감사 기록에 남는다(`ReviewSettings.kt`). 질문과 재협의(`work/questions`): 작업에 남긴 질문을 종류에 따라 원문 책임자·작업 책임자·승인자에게 보내고(`Questions.kt`의 `QuestionRouting`), 답을 기다리는 동안 작업에 `waiting_answer`를 달고 마지막 질문에 답하면 뗀다. 무응답은 답이나 승인으로 치지 않고 기한마다 다시 알린다. AI 실행이 물은 것을 사람이 질문으로 남기면 결과 검토의 그 결과가 수행으로 돌아가고, 작업을 취소하면 질문도 닫힌다. 권한 판정·업무 기준은 아직 없다 | #17 | — |
| 2 | 실행 계약과 로컬 연결 프로그램: 작업 청구·중복 방지·재개·종료 | 기록 미작성. 설치·호환 시험용 최소 구현: 서버 쪽 청구·세대 번호·중복 사건 거르기(#3), 연결 프로그램 쪽 청구·보고 묶음·표식 확인 종료(#4). 1단계 셋째 묶음 첫 판: 사람이 작업을 위임하면 서버가 위임과 실행 지시를 만들고, 위임이 정한 기기만 청구하며(기한 8시간, 철회·거두기), 연결 프로그램(`zm-baton agent`)은 이 기기에 등록한 저장소의 위임만 가져가 실행마다 새 Git 작업 트리와 전용 브랜치에서 돌린다. 끝나도 커밋하거나 작업 트리를 지우지 않는다. 실행이 시작되면 작업이 수행으로, 결과를 내면 결과 검토(또는 완료)로 넘어간다. 셋째 묶음 둘째 판: 연결 프로그램이 5초마다 임대를 갱신하고 그 답으로 사람의 실행 취소와 지시를 받는다. 서버는 임대 만료 뒤 재연결 유예(5분, 서버가 꺼져 있던 시간은 빼고 센다)가 지난 실행을 `lost`로 끝낸다. 실행 취소는 실행을 `stopping`으로 두고, 연결 프로그램이 표식을 확인해 실행기(Windows는 하위 프로세스까지)를 멈춘 뒤 `cancelled`로 보고한다. 띄우기 전 취소는 실행기를 띄우지 않는다. 이어서 맡긴 실행은 이전 실행 시도와 이어 가는 이유를 기록하고, 같은 기기에서 이전 실행기와 하위 프로세스가 끝난 것을 확인했을 때만 이전 작업 트리와 세션을 이어 쓴다(아니면 이전 브랜치 끝에서 새 작업 트리). 실행기를 띄우기 전에 준비 검사(위임 범위·실행기 판·저장소·작업 트리 폴더·디스크·기준·작업 트리)를 하고 미달이면 `readiness_failed`를 단다. 질문과 재협의(`work/questions`): 이전 실행의 질문에 답이 왔으면 이어서 맡긴 실행의 이어 가는 이유가 `answer_arrived`이고 지시에 질문과 답이 들어가며, 그 실행기가 시작하면 질문이 해결된다(같은 세션이면 `resume`, 아니면 `new_session`) | #3 | — |
| 3 | 실행기 어댑터와 실행 보고 표준 | 기록 미작성. 설치·호환 시험용 최소 구현: Claude Code의 stream-json 출력을 계약의 활동 종류로 바꾸기. 1단계 셋째 묶음 첫 판: 실행 보고 `protocol_version` 2(종료 보고의 `executor_started`, Git 변경 목록 `git_changes`의 `files`·`base_overlap`·`base_branch_overlap`), 실행 시도 기록의 작업 트리(저장소·기준 커밋·전용 브랜치), 위임의 도구를 `--allowedTools`로 넘기고 `--restricted`로 사용자 설정이 넓히지 못하게 하기, 보고에서 작업 트리 경로 빼기. 셋째 묶음 둘째 판: 맡긴 실행은 지시와 사람의 지시를 표준 입력(`--input-format stream-json`)으로 넣고 되돌려 받은 메시지(`--replay-user-messages`)로 전달을 확인한다. 시작 보고에 어댑터 능력(`capabilities`: 실행 중 입력·재개), 끝 보고에 준비 검사(`readiness`)와 지시 상태(`inputs`), 작업 트리에 시작 방식(`origin`)을 싣는다. `--resume`으로 같은 세션을 이어 쓰고, 세션이 없으면 같은 작업 트리에서 새 세션으로 시작한다. 실행 시험도 `--restricted`를 쓰고, 둘 다 `--strict-mcp-config`를 더한다. 모든 지시 끝에 에이전트 행동 규범(원문 `executor/agent-norms.txt`)을 붙인다. 사람 검토 고르기(`work/review-pick`): 연결 프로그램이 실행이 끝날 때 작업 트리의 내용을 임시 인덱스로 묶은 스냅샷 커밋을 `refs/zm-baton/snapshots/<실행 시도 번호>`에 두고(작업 트리·인덱스·브랜치는 그대로), 끝 보고의 `git_changes`에 `snapshot`으로 싣는다 | #4 | — |
