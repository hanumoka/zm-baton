# 핵심 모듈 기록 현황

핵심 모듈 여섯은 소유자가 「무엇을 하는지, 왜 이렇게 했는지, 실패하면 어떻게 되는지」를 직접 쓰고 재현 시험 하나를 돌린다(설계 허브 DEC-0079 D3). 기록은 병합 조건이 아니고 병합 뒤에 쓴다(DEC-0088). 이 표가 아직 쓰지 않은 기록을 보여 준다.

1. 첫 병합을 하는 AI는 그 모듈의 상태를 「기록 미작성」으로 바꾼다. 병합한 PR 번호를 함께 적는 것은 v0.3 제안이다.
2. 소유자가 `docs/core-modules/<번호>-<이름>.md`에 기록을 쓰고 재현 시험을 돌린 뒤 상태를 「기록 있음」으로 바꾼다.
3. AI는 기록을 대신 쓰지 않는다. 빈 칸을 가리키는 질문까지만 한다.

「기록 미작성」이 셋 이상 쌓이면 DEC-0088의 재검토 조건에 따라 개발 방식을 다시 본다.

| 1 | 업무 판정: 작업 상태 전이·권한·승인 | 기록 미작성. 1단계 둘째 묶음: 사람이 작업을 계약의 단계 표대로 넘기고(`Workflow.kt`), 조직이 쓰지 않는 검토 단계는 서버가 지나가게 하며, 바꾸는 요청마다 `version`을 확인한다. 1단계 셋째 묶음 첫 판: 맡길 수 있는지(여기서 만든 수행 준비 작업, 살아 있는 실행 없음)를 서버가 이유와 함께 정하고, 위임한 실행이 시작되면 수행으로, 결과를 내면 결과 검토(쓰지 않으면 완료)로 서버가 옮긴다. 셋째 묶음 둘째 판: AI가 돌린 수행 작업은 이어서 맡기고(끊김·취소 뒤, 돌려보낸 결과), 결과 검토의 결과는 이유를 받아 돌려보내며 같은 요청으로 이어서 맡긴다. 사람이 수행하던 작업과 살아 있는 실행이 있는 작업은 이유와 함께 거절한다. 살아 있는 실행이 있으면 작업 취소를 막고 「실행 취소」로 먼저 멈추게 한다. 결정 쓰기(`work/decisions-write`): 여기서 만든 결정의 제안·고치기·채택·기각·대체 규칙(`DecisionRules.kt`)과 승인자를 정하는 한 곳(`Approvals.kt`의 `ApprovalPolicy`, 1단계는 소유자)이 생겼고, 채택·기각은 승인 기록(`approvals`)으로 남는다. 문서(`work/documents`): 문서판은 초안으로 시작해 승인자가 한 번 승인하고(`DocumentRules.kt`), 같은 승인 기록에 남는다. 사람 검토 고르기(`work/review-pick`): 맡긴 실행의 결과를 스냅샷 커밋에 고정하고 위험 경로 패턴과 맞춰 사람 검토 요청을 만들거나 표본으로 뽑고, 나머지는 「사람 미확인」으로 둔다(`RiskPaths.kt`, `Reviews.kt`). 열린 위험 요청이 있으면 결과 검토를 건너뛰지 않고 완료로 옮기지 못하게 하며(`Workflow.kt`), 사람만 승인·반려하고 AI 주체의 판정은 거절해 감사 기록에 남긴다. 반려는 마지막 결과의 결과 검토일 때만 작업을 수행으로 돌리고(반려 이유가 이어서 맡긴 실행의 지시에 들어간다), 완료된 작업의 표본 반려는 고침 작업을 만들고, 나머지는 기록만 한다. 위험 목록은 사람만 고치고 감사 기록에 남는다(`ReviewSettings.kt`). 질문과 재협의(`work/questions`): 작업에 남긴 질문을 종류에 따라 원문 책임자·작업 책임자·승인자에게 보내고(`Questions.kt`의 `QuestionRouting`), 답을 기다리는 동안 작업에 `waiting_answer`를 달고 마지막 질문에 답하면 뗀다. 무응답은 답이나 승인으로 치지 않고 기한마다 다시 알린다. AI 실행이 물은 것을 사람이 질문으로 남기면 결과 검토의 그 결과가 수행으로 돌아가고, 작업을 취소하면 질문도 닫힌다. 권한 판정·업무 기준은 아직 없다 | #17 | — |
