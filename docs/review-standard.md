# zm-baton 검토 기준 v0.3

**목적**: zm-baton의 PR을 기본 브랜치에 병합해도 되는지 판정하는 기준을 정한다. 첫 코드보다 먼저 있어야 하는 문서다.
**독자**: PR을 쓰고 병합하는 AI 에이전트(Claude Code·Codex·Grok 등), PR을 검토하는 AI 세션, 설계 확정을 맡고 병합된 변경을 나중에 보는 소유자.
**적용 범위**: 제품 저장소 `zm-baton`에 들어가는 모든 PR이다. 코드·계약·설정·문서를 가리지 않는다. 사람이 쓴 PR과 AI가 쓴 PR에 같은 기준을 적용한다(G42.2). 작성자에 따라 달라지는 것은 누가 검토하느냐뿐이다.
**정본 관계**: 2026-10-05부터 이 저장소의 이 문서가 정본이다. 설계 허브 `zm-docs`에서 옮겨 왔다(DEC-0087). 실행기별 규칙 파일(`AGENTS.md`·`CLAUDE.md`·Grok 규칙 등)은 그 원본에서 만들어 배포하며 손으로 따로 고치지 않는다(G25.1). 이 기준이 결정 기록과 어긋나면 결정 기록이 우선하고 이 문서를 고친다.
**소유자·마지막 검토**: hanumoka · 2026-10-05
**근거 번호**: DEC-NNNN은 설계 허브 `zm-docs`의 결정 기록이다. G·R·F·V·FN·S는 그 허브의 권장 기준표·요구사항·기술 검증·검증 계획·기능 명세·추가 아이디어 번호다. 허브는 지금 비공개라 링크 대신 번호만 적는다.
**표시 규칙**: 규칙마다 괄호에 근거 번호를 단다. 결정 기록에 없는 값을 작성자가 정한 곳에는 「v0.1 제안」이라고 적는다. 그 위임은 DEC-0079에서 받았다. 소유자는 그 결정에서 작성 AI에게 검토 기준 설계를 진행하라고 했다.

## 이 문서에서 쓰는 말

- **작성자**: PR의 변경을 만든 사람 또는 AI 세션.
- **세션**: 실행기를 한 번 띄워 이어 가는 대화 하나. 실행기가 주는 세션 번호로 구분한다.
- **검토자**: 이 기준에 따라 변경을 읽고 판정을 남기는 AI 세션 또는 사람.
- **사람 필수 변경**: 정책 문서, 권한·보안·비밀값, DB 구조, 배포 설정처럼 사람이 봐야 할 변경. 병합하는 AI가 판단 이유를 남기고 위임받은 판단임을 표시한 뒤 병합하며, 소유자는 나중에 본다(DEC-0088).
- **핵심 모듈**: 소유자가 직접 설명·재현 기록을 써야 하는 모듈 여섯. 기록은 병합 뒤에 쓴다(DEC-0088). 목록은 아래 「핵심 모듈 여섯은…」 절에 있다.

## 결론: 다음 중 하나라도 해당하면 병합하지 않는다

1. PR이 작업 하나에 연결되지 않았다. 또는 다른 작업의 변경이 섞여 있다(G02.4, R38).
2. AI가 쓴 PR에 작성 세션과 다른 역할·세션의 AI 검토 승인이 없다(DEC-0064, G03).
3. 사람이 쓴 PR에 작성자가 아닌 검토자의 검토가 없다(G42.1, G42.2).
4. 검토 승인이 PR의 현재 커밋을 가리키지 않는다. 승인 뒤에 새 push가 있었는데 다시 승인받지 않았다(G03, G26.2). 검토 뒤 바뀐 것이 `docs/reviews/`의 검토 기록 파일뿐이면, 그 검토는 지금 커밋에도 적용된다(v0.2, 소유자 결정).
5. 작성과 다른 실행기·세션의 독립 검토가 지금 커밋에 대해 「병합 가능」이 아니다(DEC-0088).
6. 사람 필수 변경인데 병합하는 AI의 판단 이유와 위임 표시가 PR에 없다. 변경 종류가 불분명하면 사람 필수 변경으로 본다(DEC-0088, G03.3).
7. 검증 결과가 없다. 또는 실패하거나 건너뛴 시험을 통과로 적었다(G26.1, G31.2).
8. 시험한 환경과 버전이 적혀 있지 않다(G17.2).
9. 핵심 모듈의 첫 병합인데 `docs/core-modules/README.md`의 기록 미작성 목록에 올리지 않았다(DEC-0079 D3, DEC-0088).
10. 비밀값·토큰·로그인 정보가 코드, 시험 자료, 로그, PR 본문 어디에든 들어 있다(G23.2, G16.2).
11. 서버의 권한 판정을 거치지 않는 요청 경로가 있다. 또는 실행기를 권한 확인을 건너뛰는 모드로 돌린다(G03, F06).
12. Multica 코드를 옮겨 왔다. 또는 가져온 제삼자 코드의 고지가 빠졌다(G32.1, F03).
13. 손으로 쓴 파일 하나가 1,000줄을 넘는다(v0.1 제안).
14. 검토자가 「병합 막음」으로 표시한 지적이 풀리지 않았다. 작성 AI가 지적에 동의하지 않으면 병합하지 않고 소유자에게 묻는다(DEC-0088).
15. 검토 결과에 적용한 기준 버전이 없다(G42.2).

이 목록은 GitHub 자동 병합을 켜는 조건이 아니다. 병합하는 AI가 아래 「병합 직전」 절을 확인한 뒤 직접 병합한다(DEC-0088). GitHub 자동 병합 기능은 쓰지 않는다(DEC-0065 3항).

## PR이 갖춰야 할 것

PR은 처음에 초안으로 만든다(G03). 검증을 마치고 아래 일곱 가지를 채운 뒤 검토 요청으로 바꾼다. 검토자는 빈 항목이 있으면 내용을 보기 전에 돌려보낸다.

1. **작업 하나에 연결한다.** 작업 번호, 책임자, 실행 담당을 적는다(G02.4). AI가 실행했어도 책임자는 사람이다. 다른 작업의 변경을 같은 PR에 넣지 않는다(R38).
2. **누가 썼는지 밝힌다.** AI가 쓴 PR은 본문 첫 줄에 에이전트가 썼다고 밝힌다(G38.2). 실행기 이름과 버전, 모델, 세션 번호, 실행 계정 종류(개인 구독·조직 계정·API)를 적는다(G35.7, G16.2). AI가 만든 커밋에는 공동 작성 표시를 남긴다(v0.1 제안).
3. **무엇을 왜 바꿨는지 쓴다.** 검토한 다른 방법이 있었으면 고르지 않은 이유를 한 줄씩 적는다(G27.3). 이 칸이 비면 소유자가 나중에 그 코드를 설명할 근거가 사라진다. 결정 이유와 대안이 빠진 것은 인지부채로 관리한다(G27.1).
4. **검증 결과를 붙인다.** 돌린 명령, 통과·실패 수, 실패 메시지 원문, 그 명령을 돌린 커밋을 적는다. 다른 커밋에서 돌린 결과는 쓰지 않는다(G26.2). 에이전트가 「시험을 통과했다」고 말한 것만으로는 검증 결과로 인정하지 않는다(G26.1).
5. **시험한 환경과 버전을 적는다.** OS, 언어 런타임(JDK·Go·Node.js), 실행기 버전을 적는다(G17.2). F02 1차 실험이 적은 「Claude Code 2.1.289, codex-cli 0.160.0, grok 1.0.46」 정도로 구체적이어야 한다.
6. **실패와 확인하지 못한 것을 그대로 쓴다.** 실패한 시험, 건너뛴 시험, 시험하지 못한 OS와 실행기를 따로 적는다. 실패를 성공으로 표시하는 것은 이 제품이 0건이어야 하는 사례다(G31.2). 제품을 만드는 과정에도 같은 기준을 적용한다.
7. **변경 종류와 핵심 모듈 해당 여부를 표시한다.** 아래 「변경 종류마다…」 절의 종류를 모두 표시한다(DEC-0063). 핵심 모듈을 건드리면 모듈 번호와 첫 병합인지를 적는다(DEC-0079 D3).

작업 번호를 어디에 둘지는 아직 정하지 않았다. 정하기 전에는 작업 브랜치 이름을 적는다(v0.1 제안). PR 양식은 `.github/pull_request_template.md`에 있다. PR 본문은 다음 형식을 쓰고, 해당하지 않는 변경 종류는 지운다.

```markdown
## 작업
- 작업 번호 / 책임자(사람) / 실행 담당(사람 이름 또는 AI 실행기·버전·모델·세션 번호·실행 계정 종류)

## 변경 종류
- 일반 코드 / 계약 / 권한 / 보안 / 시크릿 / DB 구조 / 배포 설정 / 정책 문서 / 의존성 / 일반 문서

## 무엇을 바꿨나

## 왜 이렇게 했나 (고른 방법과 고르지 않은 방법)

## 검증 결과
| 명령 | 결과(통과·실패 수) | 돌린 커밋 |
|---|---|---|

## 시험한 환경과 버전
- OS / 런타임 / 실행기

## 실패·건너뜀·확인하지 못한 것

## 핵심 모듈
- 해당 없음 또는 모듈 번호, 첫 병합 여부, 설명·재현 기록 위치

## 적용한 검토 기준
- zm-baton 검토 기준 v0.3
```

## 작성자와 검토자를 나눈다

| 작성자 | 필요한 검토 | 필요한 승인 |
|---|---|---|
| AI 세션 | 작성과 다른 실행기·세션의 AI 검토 1개 이상 | 병합 직전 확인 뒤 작성 AI가 병합. 사람 필수 변경은 판단 이유와 위임 표시 포함(DEC-0088) |
| 소유자 | 작성자가 아닌 AI 검토 세션 1개 이상 | 소유자가 병합. 본인 승인으로 기록 |
| 공용 AI(2단계부터) | 작성한 공용 AI가 아닌 검토자 1개 이상 | 병합 직전 확인 뒤 작성 AI가 병합(DEC-0088) |

**AI가 쓴 PR은 다른 역할·세션의 AI가 검토한다.** 작성 세션과 다른 세션을 새로 띄워 검토 역할을 준다(DEC-0064, G03). 검토 세션은 작성 세션의 대화를 이어받지 않고 PR 본문, 변경, 이 기준, 관련 계약만 받는다(v0.1 제안). 작성 세션이 자기 결과를 「승인」하면 자체 점검으로만 기록한다(DEC-0064 2항).

**같은 세션은 검토자가 될 수 없다.** 세션 번호가 같으면 검토로 인정하지 않는다. 작성 세션을 재개해 검토 역할을 줘도 같은 세션이다. 검토 결과에 두 세션 번호를 함께 적는 이유가 이것이다.

**1단계에서는 작성 AI가 다른 실행기(Codex)의 검토 세션을 화면 없이 띄운다(v0.3).** 검토 세션은 작성 대화를 이어받지 않고 지시서만 받는다. 공용 AI 리뷰어는 2단계에서 생긴다(DEC-0079 D2). 2단계부터는 공용 AI 리뷰어를 기본 검토자로 쓸 수 있다. 한 작업에서 같은 공용 AI가 작성과 검토를 함께 맡지 않는다(G35.4).

**AI가 병합하는 PR은 다른 실행기로 검토한다.** 별도 세션이라는 사실이 판단의 독립성을 보장하지는 않는다(DEC-0064 4항). 병합 판단까지 AI가 하므로 v0.3부터는 작성과 다른 실행기의 검토를 필수로 둔다(DEC-0088). 예를 들어 Claude Code가 쓴 PR을 Codex 세션이 검토한다. 효과는 아직 측정하지 않았다.

**사람이 쓴 PR도 AI 검토를 거친다.** 같은 기준을 적용하므로 사람이 쓴 PR에도 작성자가 아닌 검토자가 필요하다(G42.1, G42.2). 소유자는 자기 PR의 병합을 승인할 수 있다. 그 승인은 사람이 직접 한 승인으로 기록한다(G37.3).

**판정이 갈리면 소유자가 정한다.** AI 검토자 둘의 판정이 다르거나 작성자가 지적에 동의하지 않으면 AI끼리 결론을 내지 않는다. 양쪽 근거를 PR에 남기고 소유자가 정한다(v0.1 제안). 요구·정책을 바꾸는 답을 AI끼리 정하지 않는다는 G36.3과 같은 방식이다.

사람이 꼭 하는 일은 셋이다(DEC-0088).

1. 설계를 확정한다(DEC-0075).
2. 판정이 갈린 PR을 정한다. 검토자 둘의 판정이 다를 때, 작성 AI가 「병합 막음」 지적에 동의하지 않을 때, 검토 결과가 「판정 불가」일 때다. 이때 AI는 병합하지 않는다.
3. 핵심 모듈의 설명·재현 기록을 병합 뒤에 직접 쓰고 직접 돌린다(DEC-0079 D3). AI는 그 기록을 대신 쓰지 않는다.

소유자는 AI가 병합한 변경을 언제든 되돌리거나 PR을 멈출 수 있다.

## 변경 종류마다 승인 방식이 다르다

작성자가 PR에서 종류를 표시하고 검토자가 맞는지 확인한다(DEC-0063). 한 PR이 여러 종류에 걸치면 해당하는 종류의 요구를 모두 따른다. 종류가 불분명하면 사람 필수 변경으로 본다. 이 두 처리는 DEC-0063 5항이 뒤로 미룬 것을 v0.1에서 정한 것이다(v0.1 제안). 위치는 구성 제안의 폴더 이름 예시를 따른다.

| 종류 | 예시 위치 | 사람 필수 | 더 요구하는 것 |
|---|---|---|---|
| 일반 코드 | 아래 종류에 들지 않는 `apps/*`, `packages/*` | 아니오 | 성공·실패 시험 |
| 계약 | `packages/contracts` | 예 | 모든 사용처를 같은 PR에서 고친다. 형식 검사 통과 |
| 권한 | 업무 판정의 권한·승인·상태 전이 | 예 | 허용 시험과 거부 시험을 함께 둔다 |
| 보안 | 인증, 실행 격리, 실행기 허용 범위 번역, 외부 입력 처리 | 예 | 위협 모델의 해당 항목을 적는다 |
| 시크릿 | 금고, 실행 주입, 로그 가림 | 예 | 값이 로그·보고에 남지 않는다는 시험 |
| DB 구조 | 마이그레이션 파일 | 예 | 되돌리는 방법과 기존 자료에 미치는 영향 |
| 배포 설정 | `deploy/`, CI 설정, 컨테이너 정의 | 예 | 검사를 끄거나 약하게 하는지 적는다 |
| 정책 문서 | 이 기준, 에이전트 행동 규범, 실행기 규칙 원본, `LICENSE`·`NOTICE` | 예 | 바뀌기 전과 뒤의 차이 요약 |
| 의존성 | 새 라이브러리·도구 추가, 주 버전 변경 | 예 | 라이선스와 고지 |
| 일반 문서 | 위에 들지 않는 문서 | 아니오 | 문서 검토 항목 |

권한·보안·시크릿·DB 구조·배포는 G03.3이 승인 정책을 따로 두라고 한 대상이다. 그래서 사람 필수로 둔다. 의존성은 라이선스와 재배포 허용을 사람이 판단해야 하므로 사람 필수로 둔다(F03).

CI 설정과 검사 규칙은 이 기준을 기계로 지키는 수단이다. AI가 검사를 끄거나 줄이면 이 기준이 통째로 빠진다. 그래서 검사를 줄이는 변경은 정책 문서 변경으로도 다룬다. 규칙을 바꿀 권한을 실행 에이전트에게 주지 않는다는 G03.3과 같은 이유다.

## 검토자가 보는 항목 열두 가지

검토자는 아래 항목을 순서대로 본다. 해당 없는 항목은 「해당 없음」이라고 적는다. 건너뛴 항목을 통과로 적지 않는다.

### 1. 수락 조건대로 동작하는가

- 작업의 수락 조건을 변경이 모두 채우는가(G26.1).
- 경계값, 빈 입력, 시간 초과, 연결 끊김 같은 실패 경로를 다루는가.
- 시험이 실제로 그 동작을 확인하는가. 늘 통과하도록 짠 시험이 아닌가.

### 2. 계약을 지키는가

- 상태 이름, 사건 형식, API 형식은 `packages/contracts`가 정본이다. 다른 곳에서 손으로 다시 정의하지 않았는가.
- 실행기 어댑터는 같은 실행 상태와 활동 종류로 보고하는가(G38.1). 지원하지 않는 보고를 미지원으로 표시하는가.
- 실행기 어댑터 PR은 에이전트 행동 규범의 준수 시험을 포함하는가(G38.2).
- 계약을 바꿨다면 모든 사용처를 같은 PR에서 고쳤는가. 모노레포를 고른 이유가 이것이다(DEC-0074).

### 3. 권한을 코드가 막는가

- 모든 요청 경로가 서버의 권한 판정을 거치는가. 화면에서 버튼을 숨기는 것은 권한 검사가 아니다.
- 프롬프트나 훅에 「하지 마라」라고 적은 것을 권한 강제로 보지 않는다(F06). 코드가 막는지 확인한다.
- 실행기를 권한 확인을 건너뛰는 모드로 돌리지 않는가. Multica가 Claude를 그렇게 돌린다. 팀원 PC에서 위험하고 질문 활동이 사라진다(Multica 조사).
- 허용 범위를 실행기마다 맞게 옮겼는가. Codex는 임시 폴더 쓰기 허용을 꺼야 한다. Grok은 Claude 사용자 설정을 읽으므로 작업별 설정을 분리해야 한다(F02 1차).
- AI나 자동 작업이 자기 권한이나 다른 AI의 권한을 넓히는 경로가 없는가(G35.3).
- 허용 시험과 함께 거부 시험이 있는가. 권한 밖 노출과 필수 승인 우회는 0건이어야 한다(G31.2).

### 4. 같은 일이 두 번 일어나지 않는가

- 작업 청구가 조건이 붙은 갱신 한 번으로 끝나는가. 같은 작업이 두 번 실행될 틈이 없는가(Multica 조사).
- 같은 요청 번호와 같은 본문이 다시 오면 저장된 결과를 돌려주는가. 다른 본문이면 거부하는가(협업 계약).
- 외부 동작을 다시 하기 전에 이미 일어난 결과를 조회하는가. 확인할 수 없으면 다시 실행하지 않고 사람 확인을 기다리는가(G30.3).
- 끝났다는 사건 없이 실행이 끊긴 경우를 「결과 확인 필요」로 다루는가(F02 1차).
- 잠금 충돌을 받으면 재시도하지 않고 멈추는가(Multica 조사).
- 프로세스를 끝낼 때 자기가 띄운 PID와 그 하위만 끝내는가. 이름으로 골라 끝내지 않는가(F02 1차).

### 5. 비밀값이 새지 않는가

- 비밀값, 토큰, 로그인 정보가 코드·시험 자료·로그·AI 입력·기억에 없는가(G23.2).
- 실행기 로그인 정보를 읽거나 보관·중계하지 않는가(G16.2).
- 디스크에 남기는 미전송 보고에 토큰을 넣지 않는가(Multica 조사).
- 비밀값을 발견하면 그 값을 PR 댓글에 다시 적지 않는다. 위치만 적고 소유자에게 알린다(v0.1 제안).

### 6. 로그와 실행 보고가 사실대로인가

- 로그에 비밀값, 개인 학습 기록, 업무 본문 전체를 찍지 않는가(G23.2, G28.1).
- 실제 수행자를 기록하는가. AI가 한 일을 사람이 한 일로 기록하지 않는다. 사람이 한 일을 AI 실행으로 기록하지도 않는다(G35.7, S01).
- 실패를 성공 상태로 보고하는 경로가 없는가(G31.2).

### 7. 시험이 안전하고 충분한가

- 새 동작마다 성공 시험과 실패 시험이 있는가.
- 시험이 실제 외부 서비스를 바꾸지 않는가. 브랜치·PR·병합을 실제로 해 보는 시험은 시험용 샘플 저장소에서만 한다(DEC-0074).
- 시험 자료는 합성 자료인가. 회사 자료나 실제 개인정보를 쓰지 않는다.
- 시험 작업 폴더를 임시 폴더 아래 두지 않았는가. 두었다면 임시 폴더 쓰기 허용을 껐는가(F02 1차).

### 8. 파일과 모듈이 한 가지 책임을 지는가

- 청구, 생존 판정, 보고, 재시도를 한 파일에 섞지 않는다. Multica는 데몬 파일이, Paperclip은 heartbeat 파일이 각각 1만 줄과 3만 줄을 넘는다(Multica 조사).
- 손으로 쓴 파일 하나가 500줄을 넘으면 PR 본문에 이유를 적는다. 1,000줄을 넘으면 나눌 때까지 병합하지 않는다. 생성된 코드는 제외한다(v0.1 제안).
- PR 하나에서 손으로 쓴 변경이 400줄을 넘으면 나누기를 먼저 검토한다(v0.1 제안). 소유자가 읽을 수 있는 크기여야 검토가 성립한다.

### 9. 의존성을 늘릴 이유가 있는가

- 새 의존성마다 쓰는 이유, 라이선스, 고정한 버전을 적고 잠금 파일을 함께 올렸는가.
- 같은 일을 하는 의존성이 이미 있지 않은가.
- 확장 모듈이면 출처와 요청 권한을 적었는가(G25.3).

### 10. 라이선스 조건을 지키는가

- Multica 코드를 복사하거나 옮겨 쓰지 않았는가. Multica License는 Apache-2.0 원문에 추가 조건을 붙인 것이다. 가져오면 zm-baton의 Apache-2.0 단일 배포와 맞지 않는다(G32.1, Multica 조사). 설계만 참고하고 독립 구현한다.
- Paperclip(MIT) 같은 다른 오픈소스 코드를 가져왔다면 저작권 고지를 `NOTICE`와 제삼자 고지 목록에 넣었는가(F03).
- 모델, CLI, 컨테이너 이미지를 함께 배포하면 재배포 허용을 확인했는가. 프로세스를 나눴다는 이유만으로 허용된다고 보지 않는다(G32.3).

### 11. 부채 후보를 적었는가

- 검토자는 기술부채와 인지부채 후보를 근거와 함께 적고, 판정은 소유자가 한다(G27.2). 인지부채 후보의 예는 선택 이유가 없는 설계, 소유자가 설명하기 어려워 보이는 흐름, 결정 기록과 어긋나는 구현이다(G27.1).

### 12. 문서가 사실과 절차를 갖췄는가

- 문서가 코드 상태를 단언하면 확인한 커밋이나 브랜치를 함께 적었는가(v0.1 제안, `zm-docs`의 같은 규칙을 따름).
- 정의 없는 비유 대신 번호 매긴 절차로 동작을 적었는가. 실행 절차에 전제조건, 단계, 완료 확인, 실패 시 대응이 있는가.

## 언어별로 더 보는 것

세 언어는 먼저 시험할 후보다(DEC-0079 D6~D8). 설치·호환 시험으로 최종 확정이 바뀌면 이 절을 다시 쓴다. 정적 검사 도구도 그 시험에서 정한다. 정해지기 전에는 컴파일러 경고를 0건으로 유지한다(v0.1 제안).

### Kotlin과 Spring Boot로 쓴 서버

- 권한 판정을 한 곳에서 한다. 애너테이션을 붙였다는 사실만으로 통과시키지 않고 그 경로의 거부 시험을 확인한다.
- 트랜잭션 경계를 명시한다. 작업 청구와 상태 전이는 조건이 붙은 갱신 한 번으로 하고, 바뀐 행 수를 확인한다.
- 마이그레이션 파일은 병합된 뒤 고치지 않는다. 바꿀 것이 있으면 새 파일을 만든다(v0.1 제안).
- 벡터 검색과 전문 검색 결과에도 권한 필터가 걸리는지 거부 시험으로 확인한다. 기준표가 pgvector 필터에 별도 거부 시험을 요구한다.
- `!!`로 null 검사를 건너뛰면 이유를 주석으로 단다. 비밀값이 들어 있을 수 있는 객체를 로그에 통째로 찍지 않는다.

### Go로 쓴 로컬 연결 프로그램·CLI·TUI

- 오류를 버리지 않는다. `_`로 버리면 이유를 주석으로 단다. 오류를 감쌀 때는 `%w`를 쓴다.
- 오래 도는 작업에는 `context.Context`를 넘기고 취소를 처리한다. 끝나지 않는 goroutine이 남지 않는지 본다.
- 시험을 `go test -race`로도 돌린다. `go vet` 경고는 0건이다.
- 경로는 `path/filepath`로 다룬다. Windows·macOS·Linux에서 같은 결과를 내야 한다(G17.1).
- 실행기를 띄울 때 작업별 설정 위치를 분리한다. 실제로 적용된 규칙을 확인해 보고한다(F02 1차, F13).
- 소유자는 Go를 새로 읽는다(DEC-0079 D7). 그래서 Go PR의 설명에는 함수 이름을 나열하지 않는다. 무엇이 어떤 순서로 일어나는지를 번호 매긴 절차로 적는다(v0.1 제안).

### TypeScript·React·Electron으로 쓴 Web과 데스크톱

- `strict` 설정을 켠다. `any`를 쓰면 이유를 적는다.
- 계약 타입은 `packages/contracts`에서 가져온다. 화면 코드에서 손으로 다시 정의하지 않는다.
- 화면에서 권한을 판정하지 않는다. 화면은 서버가 판정한 결과를 보여 주기만 한다.
- Electron은 `contextIsolation`을 켜고 렌더러의 `nodeIntegration`을 끈다. IPC 채널은 허용 목록으로 연다. 렌더러에 비밀값을 넘기지 않는다.
- 외부 자료(문서·대화·외부 메시지)를 HTML로 해석해 그리지 않는다. `dangerouslySetInnerHTML`을 쓰면 정화 방법을 적는다.
- AI의 답과 사람의 답을 글자로 구분해 표시한다(G36.5).
- 키보드 조작, 읽기 순서, 초점, 색이 아닌 상태 표시를 확인한다(G17.3).

## 핵심 모듈 여섯은 소유자가 설명·재현 기록을 쓴다

소유자가 직접 쓰지 않은 코드가 쌓이면 소유자가 그 코드를 설명하지 못하게 된다. DEC-0075는 이것을 인지부채의 위험으로 보았고, DEC-0079 D3는 다음 여섯 모듈에 확인 절차를 정했다.

1. 업무 판정: 작업 상태 전이·권한·승인
2. 실행 계약과 로컬 연결 프로그램: 작업 청구·중복 방지·재개·종료
3. 실행기 어댑터와 실행 보고 표준
4. 기억: 출처·정정·삭제 전파
5. 금고 참조와 실행 주입
6. 마스터 관찰과 공지

첫 병합은 그 모듈의 코드가 기본 브랜치에 처음 들어가는 PR이다. 절차는 다음과 같다.

1. 작성자는 PR에 핵심 모듈 번호와 첫 병합 여부를 표시한다.
2. 첫 병합이면 병합하는 AI가 `docs/core-modules/README.md`에서 그 모듈을 「기록 미작성」으로 바꾼다. 기록은 병합 조건이 아니다(DEC-0088).
3. 병합 뒤 소유자가 아래 형식으로 「무엇을 하는지, 왜 이렇게 했는지, 실패하면 어떻게 되는지」를 직접 쓴다.
4. 소유자가 재현 시험 하나를 직접 돌리고 결과를 적는다. 그다음 목록을 「기록 있음」으로 바꾼다.

이 절차에는 다음 규칙이 붙는다.

- AI가 써 준 설명을 붙여 넣은 것은 기록으로 인정하지 않는다. DEC-0079 D3가 「소유자가 직접 쓴다」로 정했기 때문이다. AI는 빈 칸을 가리키는 질문까지만 한다(v0.1 제안).
- 설명하지 못한 부분은 지우지 않고 「설명하지 못함」으로 남긴다.
- 첫 병합 뒤에 그 모듈의 상태 전이, 실패 처리, 계약을 바꾸는 PR이 오면 소유자가 기록의 해당 칸을 고친다(G27.3, v0.1 제안).
- 기록의 위치와 공개 여부는 저장소를 열 때 소유자가 정한다. 기록은 소유자가 정정할 수 있고, 사람 비교나 평가에 쓰지 않는다(G28.3, G28.4).
- 기록 미작성 모듈이 셋 이상 쌓이면 DEC-0088의 재검토 조건에 따라 개발 방식을 다시 본다.

```markdown
# 핵심 모듈 설명·재현 기록: 모듈 번호와 이름
- 쓴 사람: 소유자 / 쓴 날 / 대상 PR과 커밋 / 적용한 검토 기준 버전

## 무엇을 하는가
이 모듈이 받는 것, 내는 것, 바꾸는 상태를 내 말로 쓴다.

## 왜 이렇게 했는가
- 고른 방법:
- 고르지 않은 방법과 이유:

## 실패하면 어떻게 되는가
| 실패 상황 | 모듈이 하는 일 | 사람이 보는 것 |
|---|---|---|

## 재현 시험
- 전제조건:
- 단계: 1. … 2. …
- 기대한 결과 / 실제 결과:
- 돌린 환경과 버전:

## 설명하지 못한 부분
없으면 「없음」이라고 쓴다.
```

## AI 검토 결과는 근거·확신·기준 버전을 갖춰 남긴다

AI 검토 결과는 병합하는 AI가 병합을 판단하고 소유자가 나중에 확인하는 자료다. 그래서 무엇을 보고 그렇게 판단했는지가 남아야 한다(G26.3). 결과에는 다음 여섯 가지를 넣는다.

1. 적용한 기준 버전(G42.2).
2. 검토자 신원: 실행기·버전·모델·세션 번호·역할. 작성 세션 번호와 다르다는 것도 적는다(DEC-0064, G35.7).
3. 검토한 커밋. 이 커밋이 PR의 현재 커밋과 다르면 그 결과는 무효다(G03, G26.2).
4. 판정: 승인, 수정 요청, 판정 불가 가운데 하나. 판정 불가는 소유자에게 넘긴다.
5. 지적마다 위치(파일과 줄), 검토 항목 번호, 근거, 확신, 병합을 막는지 여부.
6. 확인하지 않은 것. 돌려 보지 않은 시험과 열지 않은 파일을 적는다.

근거는 다시 확인할 수 있는 것이어야 한다. 파일과 줄, 시험 명령과 결과, 계약 조항, 결정 번호가 근거다. 확신은 세 단계로 적는다(v0.1 제안).

- **높음**: 시험을 돌려 재현했거나 계약 조항·코드로 직접 확인했다.
- **중간**: 코드를 읽어 추론했지만 실행하지는 않았다.
- **낮음**: 근거가 부족한 추정이다.

「병합 막음」은 확신이 높음인 지적에 단다. 권한·보안·시크릿 지적은 확신이 중간이어도 단다. 확신이 낮은 지적은 혼자서 병합을 막지 않고 소유자에게 질문으로 넘긴다(v0.1 제안). AI 검토의 승인은 사람 필수 변경의 승인 요건을 채우지 못한다(DEC-0063 3항).

```markdown
## AI 검토 결과
- 적용한 기준: zm-baton 검토 기준 v0.3
- 검토자: 실행기·버전 / 모델 / 세션 번호 / 역할
- 작성 세션 번호(검토 세션과 다름을 확인) / 검토한 커밋
- 판정: 승인 / 수정 요청 / 판정 불가

| 번호 | 위치 | 검토 항목 | 근거 | 확신 | 병합 막음 |
|---|---|---|---|---|---|

### 부채 후보
### 확인하지 않은 것
```

## 병합 직전에 확인하고, 바뀌면 다시 승인받는다

병합하는 AI는 병합 직전에 다섯 가지를 확인한다(DEC-0088).

1. 「결론」의 막는 조건에 하나도 해당하지 않는다.
2. 다른 실행기의 독립 검토 커밋이 PR의 현재 커밋과 같다.
3. CI가 있으면 그 커밋에서 통과했다.
4. 사람 필수 변경이면 판단 이유와 위임 표시를 PR에 남겼다.
5. 핵심 모듈의 첫 병합이면 기록 미작성 목록에 올렸다.

병합할 때는 검토한 커밋을 지정해, 그 사이 새 push가 있으면 병합이 거부되게 한다.

**새 push가 있으면 다시 승인받는다.** 승인 뒤에 새 커밋이 올라오면 기존 승인은 새 커밋에 적용되지 않는다(G03, G26.2). 기본 브랜치를 따라가기만 한 rebase처럼 내용 차이가 없으면, 검토자는 「차이 없음」과 확인한 방법만 적을 수 있다(v0.1 제안). 검토 뒤 바뀐 것이 `docs/reviews/`의 검토 기록 파일뿐이면, 그 검토는 지금 커밋에도 적용된다(v0.2, 소유자 결정). 검토 기록을 같은 브랜치에 커밋하는 흐름 때문이다.

**검토자가 직접 고치면 다시 검토한다.** 검토자가 PR에 커밋을 올리면 그 검토자는 그 커밋의 작성자가 된다. 그 커밋은 다른 세션이 다시 검토한다(G03).

**병합은 squash로 한다(G03).** 커밋 메시지에 작업 번호와 PR 번호를 넣는다. AI가 쓴 변경이면 공동 작성 표시를 남긴다(G38.2).

**강제 푸시는 소유자에게 먼저 묻는다.** 기본 브랜치에는 강제 푸시하지 않는다. 작업 브랜치에서도 AI는 강제 푸시 전에 소유자 승인을 받는다(G03.3). 저장소를 열 때 기본 브랜치 보호 규칙(PR 필수, 승인 필수, 강제 푸시 금지)을 켜고 실제로 막히는지 시험한다(DEC-0065 2항).

**소유자가 멈추라고 하면 AI는 멈춘다.** 소유자가 PR에서 손을 떼라고 하면 AI는 더 push하지 않는다(G38.2, G03.4). 멈춘다고 이미 올린 변경이 되돌려지지는 않는다.

**병합은 완료도 배포도 아니다.** 병합됐다는 사실만으로 작업 완료, QA 통과, 배포를 확정하지 않는다(DEC-0062 4항, DEC-0065 5항). 되돌리는 PR도 이 기준으로 검토한다.

## 이 기준을 바꾸는 절차

1. 바꿀 내용을 PR로 올린다. 이 문서의 변경은 정책 문서이므로 사람 필수 변경이다.
2. AI도 이 기준이나 CI 검사를 바꾸는 PR을 낼 수 있다. 다른 실행기의 독립 검토 뒤 병합하는 AI가 판단 이유와 위임 표시를 남기고 병합한다(DEC-0088). 병합 뒤 소유자에게 바뀐 규칙을 알린다.
3. 규칙이 바뀌면 버전을 올린다(v0.1에서 v0.2로). 문구만 고치면 버전을 올리지 않고 변경 이력에 적는다.
4. 새 버전은 병합된 뒤 새로 시작하는 검토부터 적용한다. 이미 병합된 PR에 소급하지 않는다. 열려 있는 PR은 다음 push 때 새 버전으로 검토한다.
5. 실행기별 규칙 파일을 원본에서 다시 만들고, 각 실행기가 그 규칙을 실제로 읽는지 확인한다. 파일을 만든 것만으로 적용이 끝났다고 보지 않는다(G25.2).

다음 일이 생기면 이 기준을 다시 본다. 기계는 이 조건을 세지 않고 소유자가 판정한다.

| 조건 | 하는 일 |
|---|---|
| 소유자가 「이 지적은 필요 없다」고 넘긴 같은 검토 항목이 3건 쌓인다 | 그 항목을 고치거나 뺀다 |
| 병합 뒤 발견된 결함이 AI 검토의 「확인하지 않은 것」에도 없었다 | 검토 항목과 결과 형식을 고친다 |
| 2단계가 시작돼 공용 AI 리뷰어가 생긴다 | 작성자와 검토자를 나누는 절을 다시 쓴다 |
| 설치·호환 시험으로 언어가 최종 확정된다 | 언어별 절을 다시 쓴다 |

## 정하지 않은 것과 이 기준의 한계

- 정적 검사 도구, 마이그레이션 도구, CI 구성은 설치·호환 시험에서 정한다.
- 파일 500줄·1,000줄과 PR 400줄은 측정 없이 정한 시작값이다.
- 다른 실행기로 검토하면 놓치는 결함이 줄어드는지 측정하지 않았다.
- GitHub 보호 규칙이 이 기준의 조건을 실제로 강제하는지 확인하지 않았다(F09).
- 이 기준은 zm-baton 자체의 개발에 적용한다. 제품이 고객 조직에 제공할 공통 검토 기준 기능(FN-1103)의 기본값은 따로 정한다.
