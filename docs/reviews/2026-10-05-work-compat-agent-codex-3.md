# work/compat-agent 세 번째 Codex 검토

판정은 **병합 가능**이다. 병합 막음 지적은 **0건**이다. Windows proc와 agent를 포함한 전체 Go 시험이 이 검토 환경에서 통과했다. 두 번째 검토의 실행 검증 장애는 해소됐다. 이 판정의 범위는 Windows 설치·호환 시험이다. 완성 제품이나 모든 운영체제의 지원을 승인하는 판정은 아니다.

## 검토 신원과 범위

- 검토자 실행기: Codex CLI `0.160.0`.
- 모델: 세션 지침에서 GPT-6 기반임을 확인했다. 정확한 모델 식별자는 확인하지 못했다.
- 역할: 독립 검토자. 구현은 하지 않았다.
- 검토 세션: `01a10bcc-3097-7d01-8476-a477c34744b5`. `CODEX_THREAD_ID`에서 읽었다.
- 작성 실행기: Claude Code와 그 세션의 하위 작업자.
- 작성 세션: `893848f2-e1a3-4077-8809-4ef52b6cf2f2`.
- 독립성 근거: 실행기와 세션 번호가 모두 다르다. 검토 지시와 저장소 자료를 받았다. 작성 대화나 구현 역할을 이어받지 않았다.
- 검토 커밋: `78c22cc3717d82fa859c0c97177d70c30cecc4a1`.
- 대상 브랜치: `work/compat-agent`. 시작 시 HEAD가 대상 커밋과 같았다. 작업 폴더는 깨끗했다.

- 전체 대조 범위: `git diff main..work/compat-agent`. 이전 검토 기록과 현재 실행·보고 코드도 대조했다.

- 설계 대조: 지정된 외부 설계 저장소의 협업 계약 v1과 데이터 모델을 읽었다. 설계 파일은 수정하거나 복사하지 않았다.

원격 PR 본문과 CI는 이번 검토에 포함하지 않았다. 병합하는 작성 세션은 검토 기준 v0.3의 「병합 직전」 다섯 항목을 별도로 확인해야 한다. 보안 변경에 대한 판단 이유와 「위임받은 AI의 판단」 표시도 그 확인 대상이다.

## R1과 종료 경쟁

다른 PID의 프로세스로 종료 대상이 바뀌는 경로는 제거됐다. `Track`은 Go의 시작 핸들이 남아 있을 때 별도 핸들을 연다. 실행기는 일시 정지 상태에서 작업 객체에 들어간다. 등록에 성공한 뒤에만 실행을 재개한다. Go의 `Wait`가 원래 핸들을 닫아도 `Run.process`는 종료 판단이 끝날 때까지 남는다. `Kill`과 `Close`는 같은 mutex를 쓴다.

열린 핸들이 남아 있으면 프로세스 객체와 PID의 동일성이 유지된다. 이는 [Microsoft의 PROCESS_INFORMATION 설명](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/ns-processthreadsapi-process_information)과 맞는다. 이번 구현은 명령줄 조회에서도 PID를 다시 사용하지 않는다.

종료 경쟁은 다음 세 경우로 나뉜다.

1. 생존 확인 전에 실행기가 끝났으면 `ErrExited`로 거절한다. 남은 자식도 끝내지 않는다. 이 경우는 proc 시험으로 확인했다.
2. 생존 확인 뒤 명령줄 조회가 실패하면 그 오류로 거절한다. 표식이 없으면 `ErrMarkerMismatch`로 거절한다.
3. 표식을 읽은 뒤 실행기가 자연 종료해도 작업 객체 핸들은 그대로다. `TerminateJobObject`가 성공하면 그 객체에 남은 프로세스만 종료 대상이다. 재사용된 PID의 다른 실행기로 바뀌지 않는다. 작업 객체 종료의 범위는 [Microsoft의 TerminateJobObject 설명](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-terminatejobobject)과 대조했다.

README와 결과 문서의 경쟁 설명은 종료 대상의 범위를 바르게 좁혔다. 다만 「확인과 종료 사이에 끝나면 하위 프로세스만 끝난다」는 문장은 종료 호출까지 성공한 경우의 설명이다. 그 사이 명령줄 조회가 실패하면 자식도 끝내지 않는다. 이 경쟁의 각 시점을 강제로 만드는 시험은 하지 않았다.

작업 객체는 악성 실행기의 격리 경계로 검증된 것이 아니다. WMI 같은 간접 생성은 일반적인 자손 상속과 다르다. README는 이 예외를 밝혔다. `Close`에는 `KILL_ON_JOB_CLOSE`가 없다. 정상 종료 뒤 남은 자식과 연결 프로그램 비정상 종료 뒤의 자동 회수는 여전히 보장하지 않는다.

Linux의 변경은 명령줄 함수의 비공개 이름 변경뿐이다. 이전의 자손 PID 목록 종료가 다시 들어오지 않았다. macOS는 명령줄 조회 실패 시 종료를 거부한다. 두 운영체제의 실행 지원은 이번 판정으로 확장하지 않는다.

## NtQueryInformationProcess 검토

현재 Windows/amd64 환경에서 이 API 사용을 막는 결함은 발견하지 못했다. API 호출은 고정된 DLL과 함수 이름을 쓴다. 명령줄을 조회하기 위해 셸이나 별도 프로세스를 띄우지 않는다.

- 정보 클래스 `60`과 반환 형식 `UNICODE_STRING`은 [System Informer의 원본 헤더](https://github.com/winsiderss/systeminformer/blob/master/phnt/include/ntpsapi.h)와 일치한다. Microsoft의 공개 함수 문서는 이 정보 클래스를 직접 명세하지 않는다.
- 조회 권한은 이 환경에서 충분했다. `OpenProcess`의 마스크에는 `PROCESS_QUERY_LIMITED_INFORMATION`이 있다. `PROCESS_QUERY_INFORMATION`과 `PROCESS_VM_READ`는 없다. 이 핸들로 살아 있는 도우미의 명령줄 조회와 정상 종료가 통과했다. 종료·작업 객체 등록·재개·대기에 쓰는 나머지 권한은 별도로 포함돼 있다. 모든 Windows 버전에 같은 결과를 보장한 것은 아니다.
- 버퍼는 4,096바이트로 시작한다. 길이 불일치·버퍼 부족·버퍼 넘침이면 `max(needed, size*2)`로 늘린다. 최대 다섯 번 호출한다. 길이가 계속 변하면 오류로 끝난다. 정상적인 반환 길이에 대해서 크기가 줄거나 재시도가 무한 반복되는 경로는 없다.
- `unicodeString`은 두 개의 16비트 길이와 포인터로 구성된다. amd64에서 포인터 앞 정렬을 포함한 크기는 16바이트다. `Length/2`는 바이트 길이를 UTF-16 코드 단위 개수로 바꾼다. 길이에 끝의 NUL을 포함하지 않는 해석은 [Microsoft의 UNICODE_STRING 설명](https://learn.microsoft.com/en-us/windows/win32/api/ntdef/ns-ntdef-_unicode_string)과 맞는다.
- `unsafe.Pointer`를 `uintptr`로 바꾸는 것은 네이티브 호출의 인자 안에서 한다. 숫자로 바꾼 주소를 나중에 다시 쓰는 경로는 없다. 반환 문자열은 해당 버퍼를 가리키는 포인터로 읽은 뒤 Go 문자열로 복사한다. 다른 프로세스의 주소를 직접 역참조하는 PEB 조회 방식은 아니다.
- 성공 응답의 포인터와 길이가 유효하다는 운영체제 전제에 의존한다. 현재 코드는 `Length`의 짝수 여부나 포인터가 할당한 버퍼 내부인지 따로 검사하지 않는다. 비정상 네이티브 반환값에 대한 방어를 확인했다고 보지는 않는다. 정상 Windows 반환에서 잘못된 메모리 접근이 발생하는 근거는 발견하지 못했다.
- 이미 끝난 실행기는 조회 전에 거절한다. 따라서 끝난 프로세스의 명령줄이 남아 있는지에 따라 정책이 달라지지 않는다. 조회 도중 종료하면 조회 오류나 표식 검사를 거친다. 그 경로도 다른 프로세스의 핸들로 바뀌지 않는다.
- NTSTATUS는 하위 32비트를 검사한다. 길이 관련 상태 외의 실패를 표식 불일치로 바꾸지 않는다. 네이티브 함수는 NTSTATUS로 오류를 보고하므로 `LazyProc.Call`의 마지막 Win32 오류값을 판정에 쓰지 않는 점도 맞는다.

네이티브 API의 장기 호환성은 남은 의존 조건이다. [Microsoft의 함수 문서](https://learn.microsoft.com/en-us/windows/win32/api/winternl/nf-winternl-ntqueryinformationprocess)는 버전별 변경 가능성과 동적 조회를 설명한다. 코드는 `Find` 실패를 Track 오류로 반환한다. 정보 클래스가 지원되지 않는 경우에는 Kill에서 오류를 반환한다. 후자의 경우 실행기가 스스로 끝날 때까지 Runner의 Wait가 계속될 수 있다.

## 새 비막음 지적

### N8. 긴 명령줄과 조회 실패의 직접 시험이 없다

- 위치: `apps/agent/internal/proc/kill_windows.go:147`, `:161`, `apps/agent/internal/proc/kill_windows_test.go:119`.
- 검토 항목: 1. 실패 경로, 7. 시험.
- 확신: 높음. 현재 시험은 짧은 ASCII 표식의 조회와 종료를 확인한다.
- 병합 막음: 아니오. 현재 환경의 정상 경로와 거절 경로는 통과했다. 재시도 구현에서 실제 결함을 재현한 것은 아니다.
- 근거: 4,096바이트를 넘는 명령줄의 재할당과 UTF-16 문자열의 한글·서로게이트 처리를 겨냥한 시험이 없다. 조회 실패가 원래 NTSTATUS로 남는지 확인하는 시험도 없다.
- 고칠 방향: 긴 명령줄 끝에 표식을 놓는 시험을 추가한다. 비ASCII 문자열을 포함한다. 조회 오류를 반환하는 경우에는 표식 오류로 바뀌지 않고 종료가 거절되는지 확인한다.

### N9. 하위 프로세스 범위 문구가 일부 남아 있다

- 위치: `docs/stage1/compat-test-results.md:159`, `apps/agent/internal/proc/kill_windows.go:42`.
- 검토 항목: 12. 문서.
- 확신: 높음. README는 일반적인 생성 경로로 좁혔지만 두 위치는 하위 프로세스 전부로 읽힐 수 있다.
- 병합 막음: 아니오. 실제 종료 대상은 해당 작업 객체로 한정돼 있다. README에 예외도 있다.
- 근거: 결과 문서는 실행기가 띄우는 하위 프로세스가 같은 객체에 들어간다고 일반적으로 서술한다. Run 주석은 `every process the executor starts`라고 적는다.
- 고칠 방향: README와 같이 일반적인 자손 생성·작업 객체 상속 범위로 문구를 좁힌다. WMI 등의 간접 생성까지 보장한다고 읽히지 않게 한다.
