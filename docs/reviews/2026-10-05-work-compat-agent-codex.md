## 병합 막음 지적

### R1. 표식 확인과 종료 사이에 PID의 동일성이 유지되지 않는다

- 위치: `apps/agent/internal/agent/runner.go:214`, `:265`, `:288`; `apps/agent/internal/proc/kill.go:36`; `apps/agent/internal/proc/kill_windows.go:31`; `apps/agent/internal/proc/kill_unix.go:26`.
- 검토 항목: 2. 계약, 3. 권한, 7. 시험, Go의 취소 처리.
- 근거: 협업 계약 v1 「프로세스 관리」, AGENTS 안전 규칙 3.
- 확신: 중간. 경합 가능한 순서를 코드와 런타임 소스로 확인했다. 실제 PID 재사용은 재현하지 않았다.
- 병합 막음: 예. 다른 프로세스를 종료할 수 있는 안전 문제다.

Windows에서 다음 순서가 가능하다.

1. 종료 감시 goroutine이 CIM으로 대상의 올바른 표식을 읽는다.
2. 대상이 스스로 종료된다.
3. 주 goroutine의 `cmd.Wait()`가 돌아온다. Go의 프로세스 핸들도 해제된다.
4. 주 goroutine은 `stopped()`에서 종료 감시 goroutine을 기다린다.
5. 그 사이 PID가 재사용되면 `taskkill /PID`가 다른 프로세스를 대상으로 삼을 수 있다.

`Wait()`가 종료 감시와 동시에 실행되므로, 아직 회수하지 않은 프로세스가 PID 재사용을 막는다는 265행 주석은 성립하지 않는다. 설치된 Go 1.27.1의 `src/os/exec_windows.go`에서 `wait()`가 `doRelease(statusReleased)`를 호출하는 것도 확인했다. Windows에서 프로세스 객체와 PID의 수명은 열린 핸들과 관련된다. [Microsoft의 PID 재사용 설명](https://devblogs.microsoft.com/oldnewthing/20110107-00/?p=11803/).

Linux 경로도 자손의 숫자 PID만 모은 뒤 나중에 `os.FindProcess`로 다시 찾는다. 열거 뒤 자손이 종료되면 당시 프로세스의 동일성을 보장하지 못한다. 열거 도중 새 자손이 생기는 경우도 종료 목록에서 빠질 수 있다.

고칠 방향은 생성한 프로세스의 핸들을 종료 판단이 끝날 때까지 보유하는 것이다. 표식 확인과 종료가 같은 프로세스 객체를 대상으로 해야 한다. 자손도 식별 가능한 핸들이나 실행별 프로세스 묶음으로 관리해야 한다. Windows Job Object 같은 수단을 검토할 수 있다. 단순한 두 번째 표식 조회만으로는 조회와 종료 사이의 경합이 없어지지 않는다.

기존 시험은 이 순서를 검증하지 않는다. `kill_test.go:150`은 `KillRun`이 끝난 뒤에야 `Wait`를 시작한다. 실제 Runner는 그 반대 순서로 동시에 기다린다. 표식을 확인한 직후 대상이 끝나는 경우를 통제하는 시험이 필요하다.

### R2. 보고 전달 실패가 있어도 실행 결과를 성공으로 반환한다

- 위치: `apps/agent/internal/agent/runner.go:155`, `:161`, `:107`; `apps/agent/internal/report/reporter.go:185`, `:237`; `apps/agent/cmd/zm-baton-agent/main.go:82`.
- 검토 항목: 1. 수락 조건, 6. 보고의 사실성, 7. 시험, Go의 오류 처리.
- 근거: 시험 계획의 종료 사건 전달, 검토 기준 G26·G31.2.
- 확신: 높음. 오류를 로그에만 남기고 성공 값을 반환하는 분기를 직접 확인했다.
- 병합 막음: 예.

실행기가 성공 `result`를 출력한 뒤 서버 전송이 계속 실패하면 `rep.Close`는 오류를 돌려준다. `Execute`는 그 오류를 기록만 한다. 반환값은 여전히 `submitted`다. `Run(..., true)`는 오류 없이 반환한다. 따라서 서버가 종료 사건을 받지 못했어도 `--once`의 종료 코드는 0이다. 서버에는 실행이 `running`으로 남을 수 있다.

HTTP 200의 `rejected > 0`도 누락된다. Reporter는 거절 수를 더한 뒤 해당 묶음을 대기열에서 제거한다. `Close`는 `dropped`만 검사한다. 따라서 개별 사건 거절은 `Close`의 오류조차 되지 않는다. HTTP 영구 거절과 일시 오류 재시도 만료는 `Close` 오류가 되지만 Runner에서 사라진다.

고칠 방향은 실행기 종료 이유와 보고 전달 결과를 별도로 반환하는 것이다. 실행기의 `submitted` 사실은 보존해야 한다. 전달 실패나 거절이 있으면 CLI는 비정상 종료해야 한다. 개별 거절도 최종 전달 결과에 포함해야 한다. 성공한 가짜 실행기와 전송 실패 서버를 함께 사용하는 시험이 필요하다. HTTP 200의 거절 응답도 시험해야 한다.

## 비막음 지적과 부채 후보

### N1. 종료 보고의 30초 제한이 진행 중 전송에는 적용되지 않는다

- 위치: `apps/agent/internal/report/reporter.go:167`, `:200`, `:210`; `apps/agent/internal/agent/runner.go:153`.
- 검토 항목: 1. 수락 조건, Go의 취소 처리.
- 확신: 높음. context 전달과 대기 경로를 직접 확인했다.
- 병합 막음: 아니오.

`Close`는 context를 확인하지 않고 먼저 `r.done`을 기다린다. 주기 전송은 `context.Background()`로 시작한다. `flush`는 대기열 전체를 여러 요청으로 비울 때까지 반복한다. 요청별 10초 제한은 있어도 전체 30초 제한은 없다. 느린 여러 묶음이 남으면 30초를 넘어 기다릴 수 있다.

고칠 방향은 진행 중 전송에도 종료 context가 적용되게 하는 것이다. 느린 Sender가 여러 묶음을 받는 동안 `Close`하는 시험을 추가해야 한다. 현재 종료 제한 시험은 `Start`를 호출하지 않아 이 경로를 확인하지 않는다.

### N2. 프로세스 종료 시험은 조회 실패를 종료로 취급할 수 있다

- 위치: `apps/agent/internal/proc/kill_test.go:77`, `:85`; `apps/agent/internal/agent/runner_test.go:268`.
- 검토 항목: 7. 시험.
- 확신: 높음. 명령줄 조회 오류를 버리는 조건을 확인했다.
- 병합 막음: 아니오.

`mustCommandLine`은 조회 오류를 빈 문자열로 바꾼다. `waitGone`은 표식이 없으면 종료된 것으로 판단한다. Runner 시험의 마지막 확인도 조회 오류를 버린다. 따라서 일시적인 CIM 오류와 실제 종료를 구분하지 못한다.

고칠 방향은 살아 있음·종료됨·조회 실패를 구분하는 것이다. 부모의 `Wait` 결과와 자손의 프로세스 핸들 상태를 각각 확인하면 더 강한 근거가 된다.

### N3. 서버의 잠금 보유자 식별은 개선됐지만 보고 연결 자체는 식별하지 않는다

- 위치: `apps/server/src/test/kotlin/io/github/hanumoka/zmbaton/server/RunServiceConcurrencyTests.kt:132`; `docs/stage1/compat-test-results.md:65`.
- 검토 항목: 7. 시험, 12. 문서.
- 확신: 높음. SQL 조건과 문구를 대조했다.
- 병합 막음: 아니오.

`holderPid`는 실제 잠금을 보유하는 트랜잭션 안에서 얻는다. CountDownLatch가 PID를 쓴 뒤 검토 스레드로 전달한다. `holder = any(pg_blocking_pids(pid))`의 방향도 맞다. 이 함수는 지정된 연결을 막고 있는 연결들의 PID를 반환한다. [PostgreSQL 17 공식 문서](https://www.postgresql.org/docs/17/functions-info.html#FUNCTIONS-INFO-SESSION).

현재 시험은 새 작업 행 하나를 잠근다. 그 행에 보고하는 연결도 하나다. 이 범위에서는 다른 작업의 보고가 대기 조건을 대신 만족하는 문제가 해소됐다. 다만 대상 보고 PID 자체를 조건에 넣지는 않았다. 같은 보유자에게 막힌 다른 보고 연결까지 구별한다는 일반적인 보장은 없다.

고칠 방향은 문구를 현재의 새 작업 행과 단일 보고 연결에 한정하는 것이다. 공유 DB에서 같은 행에 여러 보고가 들어오는 시험으로 확장할 때는 대상 보고 PID도 확보해야 한다. 앞선 N3의 핵심은 개선됐지만 문서의 무조건적인 표현은 좁혀야 한다.

- 검토 항목: 7. 시험, 12. 문서.
- 확신: 높음. 문구와 두 Future 대기 호출을 대조했다.

정상 구현도 심한 지연에서는 제한 시간을 넘길 수 있다고 고쳤다. 두 Future는 각각 10초 제한으로 기다렸다고 표현한다. 공통 시작 시각부터 둘 다 10초 안에 끝났다는 주장은 제거됐다.

### N5. Ctrl+C 설명은 실제 신호 경로를 검증한 것으로 읽히지 않아야 한다

- 위치: `apps/agent/README.md:44`; `docs/stage1/compat-test-results.md:171`; `apps/agent/internal/agent/runner_test.go:243`.
- 검토 항목: 6. 보고의 사실성, 7. 시험, 12. 문서.
- 확신: 높음. 시험이 직접 context를 취소하는 것을 확인했다.
- 병합 막음: 아니오.

단위 시험은 `cancel()`을 호출한다. OS의 Ctrl+C 전달이나 `signal.NotifyContext` 연결은 확인하지 않는다. 실행 중 취소에서는 `Run(..., true)`가 `cancelled, nil`을 돌려준다. 따라서 CLI는 130이 아닌 1로 끝난다. README의 일괄적인 「130 Ctrl+C」 표기는 이 경로와 맞지 않는다.

고칠 방향은 context 취소 시험이라고 정확히 적는 것이다. 실행 중 취소의 종료 코드도 문서와 맞춰야 한다.

## 확인한 것

### 실행과 보고

- CLI 진입점은 작업 폴더 검사와 실행 파일 해석을 거친다. 작업 폴더는 실제 경로로 해석한 뒤 임시 폴더 아래인지 검사한다.
- `.cmd`와 `.bat`는 대소문자와 무관하게 거부한다. 실행기 호출에는 셸을 끼우지 않는다.
- 세션 UUIDv4는 실행마다 새로 만든다. `--session-id`에 들어가므로 프롬프트와 분리된다. PID는 `Start` 직후 기록한다.
- `--permission-prompts none`과 `--allowedTools`를 전달한다. 프롬프트 앞에는 `--`가 있다. 위험한 권한 우회 플래그를 추가하는 코드는 없다.
- 실제 Claude 옵션 해석과 사용자 설정의 영향을 가짜 실행기 시험만으로 입증하지는 못한다. 설정 격리는 구현되지 않았다.
- 사건 번호는 `evt_`와 UUIDv7이다. `seq`는 mutex 안에서 1부터 증가한다. 청구 응답의 `generation`을 유지한다. 재시도는 기존 사건 객체를 사용한다.
- `sendMu`가 전송을 직렬화한다. 앞 묶음의 일시 오류가 풀리기 전에는 뒤 묶음을 보내지 않는다. 실행 중에는 주기적으로 재시도한다. 종료 중에는 지수 지연을 사용한다.
- 활동 매핑은 생각·도구 호출·도구 결과·답·오류·사용량을 처리한다. 질문 매핑은 없다. 승인 거절 목록은 사용량 payload에 도구 이름만 남긴다.
- 성공 결과는 `submitted`다. 오류 결과는 `failed`다. 결과 없는 자연 종료는 `lost`다. context 취소는 `cancelled`다. 시간 제한 종료는 `failed`다. 성공 결과가 이미 있으면 취소보다 우선한다.
- 서버의 기존 `lost` 처리와 사건 형식을 대조했다. 새 실행 재개는 없다. 매번 새 세션을 만든다.

### 보안과 시험의 한계

공급자 로그인 파일이나 토큰을 읽고 복사하는 코드는 발견하지 못했다. 환경변수 전체를 사건으로 만드는 코드도 없다. `system` 줄은 매핑에서 제외한다. stderr는 로컬 버퍼와 실패 로그로만 간다. 다만 도구 결과나 답 안에 포함된 비밀값까지 제거하지는 않는다. `sanitize`는 길이와 깊이 제한이며 비밀값 가림이 아니다. 해당 한계는 결과 문서에도 적혀 있다.

서버 URL은 HTTP·HTTPS와 호스트를 요구한다. 사용자 정보·쿼리·fragment를 거부한다. 루프백만 강제하거나 원격 HTTP를 막지는 않는다. 기본 HTTP 클라이언트의 redirect 정책도 유지한다. 현재 로컬 호환 시험의 기본값과 완성 제품의 안전한 전송 정책을 구분해야 한다.

표식이 빈 값이거나 짧거나 불일치하면 `killTree`에 도달하지 않는다. 실행 파일 이름으로 종료 대상을 고르는 코드는 없다. 시험은 시험 바이너리 자신을 도우미로 띄운다. 부모는 직접 얻은 핸들로 정리한다. 자손은 전달받은 PID와 무작위 표식으로 정리한다. 다만 R1과 N2 때문에 모든 경합에서 종료 대상과 종료 완료를 증명했다고 볼 수는 없다.

가짜 실행기는 합성 stream-json을 출력한다. 실제 CLI의 승인 거부·설정 격리·구독 인증·출력 호환성을 증명하지 않는다. Runner 시험은 임시 작업 폴더를 직접 Config에 넣는다. 실제 CLI의 작업 폴더 검사는 별도 시험에서 확인한다. 최상위 시험은 30개다. 하위 시험은 종료 경로 2개와 오류 매핑 3개다. 문서의 개수와 맞는다.

### 범위와 문서

변경은 연결 프로그램 호환 시험과 앞선 서버 검토 후속 조치에 연결된다. 핵심 모듈 2와 3은 기록 미작성 목록에 있다. 소유자의 설명 기록은 대신 작성하지 않았다. 외부 Go 모듈 의존성은 없다. 변경 파일 중 1,000줄을 넘는 파일은 없다. 제삼자 코드 복사를 나타내는 내용은 발견하지 못했지만 출처 전체를 독립 증명한 것은 아니다.

디스크 보관·임대 갱신·재개·빈 순번 재요청 등은 시험 계획의 제외 항목이다. 영구 거절을 한 번에 버리는 현재 동작은 계약의 완성 동작과 다르다. 질문 경로와 설정 격리도 미구현이다. 이 상태를 계약 전체 준수로 인정하지 않았다. README의 「1단계 뒤 작업」은 계획의 「시험 뒤 1단계 작업」과 혼동되지 않게 고치는 편이 좋다.

작성자의 실제 Claude Code 시험 3회는 독립 재현하지 않았다. 사건 7건·시간 제한 종료·외부 종료 후 lost라는 설명은 코드 경로와 양립한다. 실제 실행 사실과 소요 시간은 작성자 보고로만 취급한다. Linux·macOS 실행과 race 검사를 하지 못했다는 문구도 확인했다. macOS 종료 코드는 `/proc` 조회에 실패하면 종료를 거부하는 수준이다.

변경 텍스트에서 실제 비밀값·소유자 PC 절대 경로·회사 정보·내부 주소를 발견하지 못했다. 사용자 경로 패턴의 일치는 짧은 경로 설명용 가상 예시였다. 사설 주소 패턴의 일치는 버전과 숫자 리터럴이었다. 이 검사가 비밀값의 절대 부재를 보증하지는 않는다.

## 실행한 명령과 결과

환경은 Windows NT `10.0.26300.0`이다. PowerShell은 `5.1.26100.9549`다. Git은 `2.50.1.windows.1`이다. Go는 `go1.27.1 windows/amd64`다. Codex CLI는 `0.160.0`이다.

현재 프로세스 PATH에서는 `go`를 찾지 못했다. 사용자 PATH 조회에서도 경로를 얻지 못했다. 알려진 사용자 설치 위치에서 Go를 찾아 절대 경로로 호출했다. 아래 표는 명령 이름을 줄여 적었다. 실제 설치 경로는 공개 기록에 남기지 않는다.

| 명령 또는 확인 | 결과 |
|---|---|
| `git status --short` | 시작 시 변경 없음 |
| `git rev-parse HEAD`, `git rev-parse main` | 지정한 검토 커밋과 기준 커밋 확인 |
| `git diff --stat main..work/compat-agent`, `git diff --numstat main..work/compat-agent` | 21개 파일 범위 확인 |
| `git log --format='%h %s' main..work/compat-agent` | 구현·수정·결과 기록의 커밋 3개 확인 |
| `Get-Content -Encoding utf8`, 범위별 `git diff`, `rg -n` | 기준·계약·데이터 모델·구현·시험·문서 대조 |
| `apps/agent`에서 `gofmt -l .` | 종료 코드 0. 출력 없음 |
| `apps/agent`에서 `go vet ./...` | 종료 코드 1. 표준 패키지를 찾지 못해 분석 미완료 |
| `apps/agent`에서 `go test -count=1 ./...` | 종료 코드 1. 임시 빌드 폴더 생성 거부로 시험 미실행 |
| `git diff --check main..work/compat-agent` | 종료 코드 0. 공백 오류 없음 |
| 변경 파일 줄 수 집계와 `rg -n '^func Test' apps/agent` | 1,000줄 초과 없음. 시험 개수 대조 |
| diff의 경로·주소·비밀값 패턴 검사와 육안 검토 | 확인된 공개 금지 정보 없음 |
| `go version`, `codex --version`, `git --version`, OS·PowerShell·세션 번호 조회 | 위 환경과 신원 확인 |
| 설치된 Go의 `src/os/exec_windows.go` 조회 | Wait의 핸들 해제 확인 |
| Microsoft·PostgreSQL 공식 문서 조회 | PID 재사용과 차단 PID 함수 의미 확인 |

`go vet` 진단에는 `package context is not in std`와 다른 표준 패키지 오류가 있다. 설치 위치의 `src/context/context.go` 파일은 존재했다. 이 진단의 근본 원인은 확정하지 않았다.

`go test` 진단은 `go: creating work dir: mkdir <임시 빌드 폴더>: Access is denied.`다. 꺾쇠 부분은 소유자 경로를 제거한 자리다. 컴파일과 시험 본문에 도달하지 않았다. 시험 통과나 시험 실패 개수로 집계하지 않는다. 저장소 안으로 캐시나 빌드 폴더를 옮기지 않았다.

처음 문서 조회는 기본 인코딩 때문에 한글이 깨졌다. UTF-8로 다시 읽었다. 긴 도구 출력은 파일과 구간을 나눠 확인했다.

## 확인하지 않은 것

- 실제 Claude 실행 파일은 띄우지 않았다. 작성자의 끝에서 끝까지 시험과 거부 시험을 재현하지 않았다.
- Go 단위 시험·vet 완료·race 검사·독립 빌드를 확인하지 못했다.
- 서버 Gradle 시험은 실행하지 않았다. 실제 PostgreSQL의 차단 관계도 관찰하지 않았다.
- PID 재사용 경합과 자손 생성 경합은 실제 프로세스로 재현하지 않았다.
- 실제 OS Ctrl+C와 CLI 종료 코드를 실행 시험하지 않았다.
- Linux·macOS 실행은 하지 않았다.
- 원격 PR의 일곱 필수 항목·CI·사람 필수 변경의 위임 표시는 확인하지 않았다.
- 위협 모델·질문 경로·과금 설계·개별 결정 기록 전체는 이번에 정독하지 않았다.
- 자격 정보 파일은 열지 않았다. 환경변수 전체 덤프도 하지 않았다.

지정된 검토 기록 파일만 작성했다. 구현·브랜치 생성·커밋·push·원격 변경·main 변경·병합은 하지 않았다.
