## 앞선 지적별 처리 결과

### R1. 기본 수신 주소 제한 — 해소

기본 설정은 루프백 한 주소로 제한됐다. 위치는 `apps/server/src/main/resources/application.properties:5`다. 환경 변수로 명시적으로 바꿀 수 있다는 결과 문서의 설명도 설정과 맞는다.

작성자가 기록한 단일 수신 주소, 로컬 health 응답, 다른 IPv4 인터페이스 접속 거절은 이 기본 설정과 모순되지 않는다. 실제 수신 소켓과 접속 거절은 이번 세션에서 재현하지 못했다. 다른 기기에서 접속을 시험했다고 확대 해석하지 않았다.

- 확신: 설정 변경은 높음. 작성자 실측은 독립 확인하지 못함.
- 병합 막음: 아니오.

### R2. 잘못된 종료 이유를 성공으로 바꾸는 처리 — 해소

잘못된 lifecycle은 저장과 상태 갱신 전에 거절된다. 위치는 `RunService.kt:93`, `:128`, `:148`이다. 이하 Kotlin 파일은 `apps/server/src/` 아래 같은 서버 패키지를 가리킨다.

`ended`의 종료 이유는 허용 집합에 있는 문자열이어야 한다. 누락·오타·숫자·null은 그 집합에 속하지 않는다. 이후 문자열 변환은 이 검사를 통과한 경로에서만 실행된다. `submitted`로 대체하던 기본값은 없어졌다. 알 수 없는 phase도 거절한다.

거절된 사건 번호로 정정본을 받는 정책에서 계약 위반을 찾지 못했다. 계약의 사건 중복 규칙은 이미 저장된 `event_id`를 대상으로 한다. 거절된 입력은 저장된 사건이 아니므로 기존 사건을 고치거나 지우지 않는다. 같은 요청 번호에 다른 내용을 금지하는 규칙은 별도의 `request_id` 규칙이다. 요청 번호 처리는 시험 계획에서 제외돼 있다.

`RunServiceTests.kt:118`은 잘못된 입력 다섯 가지의 거절 수를 확인한다. 실행이 `running`으로 남는지도 확인한다. 해당 순번의 사건이 저장되지 않는지도 조회한다. 정상 `failed` 종료도 확인한다. 다만 정정본을 같은 `event_id`와 `seq`로 다시 보내는 시험은 없다. 결과 문서의 재전송 설명은 코드에서 추론한 정책으로만 확인했다.

- 확신: 높음.
- 병합 막음: 아니오.

### R3. 세대 판정과 새 청구 사이의 경쟁 — 구현 해소, 시험 보강 필요

작업 행 잠금이 세대 조회와 보고 처리 사이의 변경을 막는다. 위치는 `RunService.kt:84`다. 보고 트랜잭션이 끝나기 전에는 청구가 같은 작업의 세대를 올릴 수 없다. 청구가 먼저 작업 행을 갱신하면 보고는 그 갱신을 기다린 뒤 최신 세대를 판정한다.

현재 SQL과 PostgreSQL 17 구현에서 보고의 행 잠금 순서는 실행 행, 작업 행이다. 파서는 명시된 잠금 대상을 순서대로 등록한다. 플래너와 실행기는 그 row mark 목록을 사용한다. 이는 현재 쿼리와 버전에 대한 소스 분석이다. 모든 SQL 변형에 대한 잠금 순서 보장으로 확대하지 않는다. 근거는 PostgreSQL의 [파서](https://github.com/postgres/postgres/blob/REL_17_STABLE/src/backend/parser/analyze.c), [플래너](https://github.com/postgres/postgres/blob/REL_17_STABLE/src/backend/optimizer/plan/planner.c), [행 잠금 실행기](https://github.com/postgres/postgres/blob/REL_17_STABLE/src/backend/executor/nodeLockRows.c)다.

청구와 보고 사이의 교착은 다음 순서에서 성립하지 않는다.

1. 같은 실행 R의 청구가 먼저 R을 잡으면 보고는 R에서 기다린다. 보고는 아직 작업 행 W를 잡지 않았다. 청구는 W를 갱신하고 커밋할 수 있다.
2. 같은 실행 R의 보고가 먼저 R을 잡으면 청구의 `SKIP LOCKED`가 R을 건너뛴다. 청구는 충돌로 끝난다. 청구가 W를 잡은 채 R을 기다리는 경로는 없다.
3. 옛 실행 A의 보고와 새 실행 B의 청구는 각각 A와 B를 잡을 수 있다. 둘은 W에서 경합한다. W를 먼저 잡은 쪽은 자기 실행 행만 후속 갱신한다. A의 보고는 B를 요구하지 않는다. B의 청구는 A를 요구하지 않는다. 따라서 둘 사이의 대기 고리가 없다.
4. A의 보고가 W를 먼저 잡았다면 그 보고는 세대 증가보다 먼저 처리된다. B의 청구가 W를 먼저 잡았다면 보고가 증가한 세대를 기준으로 늦음을 판정한다. 두 순서 모두 트랜잭션 경계와 일치한다.

작업 행의 갱신본을 잠근 뒤 재평가하는 처리는 PostgreSQL 17의 `ExecLockRows`에서 확인했다. 실제 DB 실행 계획과 잠금 대기 그래프는 확인하지 못했다. 새 경쟁 시험의 한계는 N1에 적었다.

- 확신: 중간. 저장소 코드와 PostgreSQL 소스로 추론했다.
- 병합 막음: 아니오.

### R4. 잠긴 실행 행을 건너뛰는 시험 — 핵심 보강 완료

새 시험은 별도 트랜잭션이 실행 행을 잠갔다는 신호를 받은 뒤 청구한다. 위치는 `RunServiceConcurrencyTests.kt:26`이다. 거절 뒤 잠금을 풀고 같은 실행을 다시 청구하는 데 성공해야 한다.

이 시험은 이전의 동시 시작 시험보다 강하다. 단순히 `SKIP LOCKED`만 제거하면 청구가 잠금 해제를 기다린 뒤 성공한다. 따라서 기대한 `ConflictException`이 나오지 않아 실패한다. 보유 트랜잭션이 일찍 끝나도 정상 청구는 성공하므로 거짓 통과로 이어지지 않는다.

2초 제한에는 거짓 실패 가능성이 있다. 정상 청구도 연결 확보나 스케줄링 지연으로 제한을 넘을 수 있다. 잠금 보유자의 10초 대기 만료도 검사하지 않는다. 긴 정지 때문에 보유자가 먼저 풀리면 정상 구현도 실패할 수 있다. 이 시험만으로 모든 대기 구현을 배제하지는 못한다. 짧은 제한 시간 뒤 충돌로 바꾸는 다른 구현도 통과할 수 있다.

개선 방향은 청구 Future가 끝날 때까지 보유 잠금을 유지하는 것이다. 제한 시간은 시험 정지 방지에 사용한다. 잠금 보유자의 대기 만료도 실패로 확인한다. 현재 코드의 `SKIP LOCKED` 존재는 별도로 직접 확인했다.

- 확신: 높음.
- 병합 막음: 아니오. 회귀 검증은 실질적으로 강화됐다.

### R5. 늦은 보고의 상태 불변과 사건 저장 — 요청한 범위 보강 완료

작업의 단계·대기 이유·세대·버전·수정 시각을 전후 비교한다. 위치는 `RunServiceTests.kt:35`, `:99`다. B의 상태·종료 이유·세대·늦은 보고 표시도 비교한다. 사건 번호로 저장 행을 다시 조회한다. 저장된 세대와 종류를 검사한다.

이 시험은 이전에 빠졌던 작업 상태 불변과 실제 사건 저장을 확인한다. A의 종료 이유 유지와 늦은 보고 표시도 계속 검사한다. 다만 B의 모든 열을 비교하지는 않는다. 그 문서 표현은 N2에 적었다.

- 확신: 높음.
- 병합 막음: 아니오.

## 비막음 지적

### N1. 700ms 시험은 보고가 잠금을 기다렸음을 보장하지 않는다

- 위치: `apps/server/src/test/kotlin/io/github/hanumoka/zmbaton/server/RunServiceConcurrencyTests.kt:67`, `docs/stage1/compat-test-results.md:52`.
- 검토 항목: 1. 수락 조건, 7. 시험, 12. 문서.
- 확신: 높음. 동기화와 검증문을 직접 확인했다.
- 병합 막음: 아니오. 구현의 작업 행 잠금은 별도로 확인했다.

보고 스레드가 700ms 이상 늦게 시작하면 잠금 없이도 시험이 통과할 수 있다. 보유자가 세대를 올리고 커밋한 뒤 보고가 시작되면 옛 구현도 최신 세대를 읽는다. 시험은 반환값의 `late=1`만 검사한다. 보고 SQL이 잠금 대기에 들어갔다는 증거는 확인하지 않는다.

시험은 실제 새 실행 B의 `claim`도 호출하지 않는다. 실행 A가 청구된 상태에서 별도 SQL로 작업 세대만 올린다. 따라서 두 서비스 경로의 교착 부재를 실행으로 증명한 시험이 아니다. 올바른 구현은 보고가 일찍 시작하든 늦게 시작하든 통과할 수 있다. 700ms 자체는 올바른 잠금 구현의 거짓 실패 원인이라기보다 잘못된 구현의 거짓 통과 원인이다.

고칠 방향은 보고를 별도 Future에서 실행하는 것이다. DB에서 해당 보고의 잠금 대기를 확인한 뒤 세대 갱신 트랜잭션을 풀어야 한다. 실제 A의 보고와 B의 청구도 별도 시나리오로 확인하는 편이 좋다. 그전에는 결과 문서에 세대 갱신을 모사한 시험이라고 적어야 한다. 실제 대기를 관찰했다는 단정도 줄여야 한다.

### N2. 실행 B 행 전체가 같다는 문구는 시험 범위보다 넓다

- 위치: `apps/server/src/test/kotlin/io/github/hanumoka/zmbaton/server/RunServiceTests.kt:39`, `docs/stage1/compat-test-results.md:44`, `:49`.
- 검토 항목: 7. 시험, 12. 문서.
- 확신: 높음. 조회 열과 비교문을 직접 확인했다.
- 병합 막음: 아니오. 요청된 작업 상태와 B의 실행 상태는 비교한다.

`runRow`는 B의 네 열만 읽는다. 임대 만료 시각·마지막 사건 시각·실행기 세션 번호 등은 비교하지 않는다. 따라서 결과 문서의 「실행 B 행」은 「실행 B의 상태·종료 이유·세대·늦은 보고 표시」로 좁히는 편이 정확하다. 전체 행 불변을 주장하려면 비교 열을 넓혀야 한다.

## 나머지 확인 결과

- 수정이 새로 만든 계약 위반이나 트랜잭션 오류는 발견하지 못했다. 부적합 lifecycle은 SQL 저장 이전에 분기한다. DB 오류를 잡은 뒤 실패한 트랜잭션을 계속 쓰는 경로가 새로 생기지 않았다.
- 시험 메서드는 11개다. 서비스 7개, 동시성 2개, HTTP 1개, 컨텍스트 1개다. 작성자의 시험 개수 서술과 일치한다. 실제 통과 수와 소요 시간은 재확인하지 못했다.
- 결과 문서의 종료 이유 거절과 순차 늦은 보고 설명은 N2의 표현 범위를 제외하면 시험 코드와 맞는다. 같은 사건 번호로 정정본을 보내는 동작은 직접 시험하지 않았다.
- 결과 문서에는 실행별 정확한 커밋이 없다. 이번 대상은 사용자 지시서로 특정했다. 작성자는 PR의 검증 표에서 실제 시험한 커밋을 명시해야 한다.
- 변경 텍스트에서 소유자 PC 절대 경로, 내부망 주소, 실제 비밀값을 발견하지 못했다. 주소 설정은 일반 루프백 설정이다. 비밀번호 예시는 교체용 문자열이다. 추적되는 환경 파일은 `.env.example`뿐이다.
- 브랜치 diff의 공백 검사는 통과했다. 변경된 텍스트 파일 중 1,000줄을 넘는 파일은 없었다.
- 핵심 모듈 2는 기록 미작성 목록에 올라 있다. 소유자의 설명·재현 기록은 대신 쓰지 않았다.
- 인증·위임·요청 번호 중복 처리·outbox 등 시험 계획의 제외 기능은 구현 완료로 평가하지 않았다.
