# work/compat-server 세 번째 독립 검토

판정은 **병합 가능**이다. 병합 막음 지적은 **0건**이다. 비막음 지적은 **2건**이다.

실행 자신의 세대 확인과 `lost` 처리는 현재 계약에 맞는다. 앞선 N1은 현재 시험 구성에서 해소됐다. N2의 문구도 바로잡혔다. 시험의 연결 식별 범위와 시간 제한 설명에는 보완할 점이 남는다. 이 판정은 설치·호환 시험의 서버 범위에 적용한다.

## 앞선 지적별 처리 결과

### N1. 잠금 대기를 보장하지 못하던 시험 — 현재 구성에서 해소

고정된 700ms 대기를 없앴다. 보고를 별도 Future에서 실행한다. 관찰 연결이 잠금 대기를 찾은 뒤에만 세대 증가 트랜잭션을 풀어 준다. 위치는 `apps/server/src/test/kotlin/io/github/hanumoka/zmbaton/server/RunServiceConcurrencyTests.kt:57`이다.

현재 구성에서는 관찰 대상 보고를 구분할 근거가 있다. Testcontainers 설정은 시험용 PostgreSQL 컨테이너를 만든다. 재사용 설정은 없다. 저장소에는 JUnit 병렬 실행을 켜는 설정이 없다. JUnit의 기본 실행은 순차 실행이다. 이는 [JUnit 공식 문서](https://docs.junit.org/6.2.0/writing-tests/parallel-execution.html)에서도 확인했다. 시험 내부의 보유 연결은 `work_items`만 조회하므로 보고 SQL의 JOIN 조건에 맞지 않는다. 관찰 연결 자신은 PID로 제외한다. 정상적으로 끝난 다른 시험의 유휴 연결은 `Lock` 대기 조건에 맞지 않는다.

관찰 코드는 시험 메인 스레드에서 실행된다. 이 스레드를 감싼 트랜잭션은 없다. 따라서 같은 트랜잭션의 통계 스냅샷을 반복해서 보는 구조도 아니다. 같은 데이터 소스를 사용하므로 다른 역할의 세션 내용이 가려지는 문제도 현재 구성에서는 예상하지 않는다. 세션 조회의 권한과 트랜잭션별 스냅샷 동작은 [PostgreSQL 17 공식 문서](https://www.postgresql.org/docs/17/monitoring-stats.html)로 대조했다.

작업 행 잠금을 제거하면 보고는 기존 세대를 읽고 끝난다. 현재의 격리된 시험에서는 관찰할 보고 잠금 대기가 남지 않는다. 따라서 관찰 제한 시간이 지나 시험이 실패하는 구조다. 이 판단은 코드 추론이다. 작성자의 변형 시험 결과를 독립 재현한 것은 아니다.

실제 A의 보고와 B의 청구를 함께 시작하는 시험도 추가됐다. 위치는 같은 파일의 93행이다. 다만 시작 신호를 함께 푸는 것은 DB 도착 순서까지 강제하지 않는다. 20회 성공은 모든 실행 순서의 교착 부재를 증명하지 않는다. 연결 식별의 일반화 한계는 아래 N3에 남긴다.

- 확신: 중간. 시험 구성과 동기화를 읽어 판단했다.
- 병합 막음: 아니오.

문서가 비교한 열을 정확히 적는다. 위치는 `docs/stage1/compat-test-results.md:55`다. 작업의 다섯 열과 B의 네 열을 구분한다. B의 다른 열은 비교하지 않았다고도 적는다. 이는 `RunServiceTests.kt:35`와 `:39`의 조회 및 88행 시험의 비교문과 맞는다.

- 병합 막음: 아니오.

### 앞선 R1~R5 — 해소 판단 유지

기본 수신 주소 제한과 잘못된 lifecycle 거절은 유지된다. 보고의 작업 행 잠금도 유지된다. 잠긴 실행의 청구 시험은 청구가 끝나기 전까지 보유 잠금을 풀지 않도록 강화됐다. 보유자의 30초 대기 만료도 오류로 처리한다. 늦은 보고의 저장과 작업 상태 불변 검증은 그대로 있다.

거절된 lifecycle을 같은 `event_id`와 `seq`로 고쳐 보내는 검증도 추가됐다. 위치는 `RunServiceTests.kt:139`다. 이전 검토가 확인하지 못했던 정정본 재전송 경로를 이제 시험 코드가 다룬다. 실제 실행 결과는 이번 세션에서 확인하지 못했다.

## 추가 구현 검토

### 실행 자신의 세대 확인은 늦은 보고 규칙과 충돌하지 않는다

정상 보고는 청구 때 받은 실행의 세대를 실어야 한다. 계약 v1의 「보고 한 건의 모양」과 데이터 모델의 `runs.generation` 정의가 같은 의미다. `RunService.kt:105`는 이 조건을 확인한다. 125행은 그 뒤 작업의 현재 세대와 비교한다.

예를 들어 A의 실행 세대가 1이고 작업의 현재 세대가 2라면 A의 세대 1 보고는 저장된다. 이후 늦은 보고로 표시된다. 반면 B가 A의 세대를 실어 보낸 입력은 정상적인 B의 보고가 아니다. 작업의 현재 세대보다 작다는 이유만으로 이를 정상 보고로 취급할 근거는 없다. 청구 전 실행은 세대가 null이므로 보고가 거절된다.

현재 코드에는 한 실행을 두 번 성공적으로 청구하는 경로가 없다. 청구는 `requested`만 대상으로 한다. 상태를 다시 `requested`로 돌리는 갱신은 없다. 청구·작업 세대 증가·실행 세대 저장은 한 트랜잭션이다. 중간 실패로 롤백되면 성공한 첫 청구가 존재하지 않는다. 따라서 재청구 때문에 실행의 예전 정상 세대가 덮어써지는 경우도 현재 범위에는 없다.

`RunServiceTests.kt:147`은 청구 전 보고와 다른 실행 세대의 보고를 거절하는지 확인한다. 기존 88행 시험은 자신의 옛 세대 보고가 계속 저장되는지 확인한다. 확신은 높음이다. 계약과 조건 분기를 직접 대조했다.

### lost 처리는 한 번의 상태 전이와 같은 트랜잭션에 묶인다

`RunService.kt:161`은 아직 끝나지 않은 실행만 종료한다. 실제 갱신 행 수가 1이고 이유가 `lost`일 때만 작업을 갱신한다. 위치는 168행이다. 사건 저장·실행 종료·작업 갱신은 `ingest`의 트랜잭션에 들어간다. 새 SQL 오류를 삼키고 처리를 계속하는 경로는 없다.

대기 이유는 배열에 덧붙인다. 다른 대기 이유는 보존한다. 이미 `outcome_unknown`이 있으면 작업을 갱신하지 않는다. 새로 추가할 때만 `version`을 1 올리고 `updated_at`을 갱신한다. 같은 사건 재전송은 중복 분기에서 끝난다. 다른 사건 번호의 두 번째 종료 보고는 실행 갱신 행 수가 0이다. 따라서 작업의 버전이 다시 오르지 않는다.

늦은 보고는 129행의 `continue`에서 끝난다. `applyLifecycle`에 도달하지 않으므로 늦은 `lost`가 작업에 대기 이유를 달지 않는다. 보고가 이미 잠근 작업 행을 갱신하므로 이 수정이 별도의 새 잠금 순서를 만들지도 않는다. 기존 청구와 보고 사이의 직렬화 구조는 유지된다.

`RunServiceTests.kt:163`은 최초 추가와 버전 증가 및 두 번째 종료 보고의 작업 불변을 확인한다. 이미 대기 이유가 있는 경우와 늦은 `lost` 자체는 전용 시험이 없다. 해당 두 경우는 조건 분기로 확인했다. 계약 적합성의 확신은 높음이다. 실제 동시 실행 안전성의 확신은 중간이다.

## 비막음 지적

### N3. 잠금 관찰 조건이 특정 보고 연결과 보유자를 식별하지 않는다

- 위치: `apps/server/src/test/kotlin/io/github/hanumoka/zmbaton/server/RunServiceConcurrencyTests.kt:132`.
- 검토 항목: 1. 수락 조건, 7. 시험.
- 확신: 높음. 조회 조건에 식별 조건이 없음을 직접 확인했다.
- 병합 막음: 아니오. 현재 격리된 순차 시험에서는 다른 일치 보고 경로를 발견하지 못했다.

관찰 조건은 JOIN 문자열과 `wait_event_type='Lock'`만 확인한다. 대상 보고 PID, 데이터베이스, 보유자 PID를 확인하지 않는다. `Lock` 자체도 특정 작업 행을 가리키지 않는다. 같은 서버에서 병렬 시험이나 별도 연결이 같은 SQL을 실행하면 그 연결의 대기로 조건을 만족할 수 있다.

그때 대상 보고가 아직 시작하지 않았다면 세대 증가를 먼저 풀 수 있다. 작업 잠금이 빠진 잘못된 구현도 이후 새 세대를 읽어 거짓 통과할 수 있다. 현재 시험에서 그런 상황이 발생했다고 주장하는 것은 아니다. 시험 환경을 병렬화하거나 공유 DB로 바꿀 때 드러나는 식별 한계다.

고칠 방향은 보고 트랜잭션의 백엔드 PID를 확보하는 것이다. 보유 트랜잭션의 PID도 확보한다. 관찰 시 대상 PID의 대기와 해당 보유자에 의한 차단을 함께 확인한다. 다른 보고 연결이 동시에 있어도 이를 혼동하지 않는 시험을 추가할 수 있다.

### N4. 느린 기계에서도 거짓 실패가 없다는 문구는 과장이다

- 위치: `docs/stage1/compat-test-results.md:50`, `apps/server/src/test/kotlin/io/github/hanumoka/zmbaton/server/RunServiceConcurrencyTests.kt:46`.
- 검토 항목: 7. 시험, 12. 문서.
- 확신: 높음. 제한 시간과 문구를 직접 대조했다.
- 병합 막음: 아니오. 잠금 유지 방식의 개선은 유효하다.

청구 Future에는 여전히 10초 제한이 있다. 정상 구현도 스케줄링이나 연결 확보가 그보다 늦으면 실패한다. 잠금 보유자의 대기에도 30초 제한이 있다. 그러므로 시간 측정을 없앴다는 사실이 모든 거짓 실패 가능성을 없애지는 않는다.

고칠 방향은 별도의 2초 성능 판정을 없앴다고 쓰는 것이다. 10초와 30초는 시험 정지 방지용 제한이라고 설명하면 된다. 심한 지연에서는 정상 구현도 제한 시간을 넘을 수 있다는 범위를 남긴다.

같은 문서의 69행도 두 Future가 공통 시작부터 각각 10초 안에 끝났다는 것을 코드만으로 입증하지는 못한다. 코드는 `report.get(10초)` 뒤 `claim.get(10초)`를 호출한다. 공통 마감 시각을 쓰거나 각각의 대기 호출이 제한 시간 안에 완료됐다고 표현하면 정확하다. 실제 작성자 실행의 소요 시간은 별도 측정이 있었는지 확인하지 못했다.

## 나머지 확인 결과

시험 메서드는 14개다. 서비스 9개와 동시성 3개 및 HTTP 1개와 기동 1개다. 결과 문서의 개수와 맞는다. 변형 시험 표의 세 변경은 대응 시험이 잡을 수 있는 결함과 연결된다. 표의 실행 사실과 실패 로그는 작성자의 결과로만 취급한다. 이번 세션에서는 재현하지 않았다.

새 계약 위반이나 트랜잭션 오류는 발견하지 못했다. 다만 전체 제품의 인증·권한·임대·재개·outbox를 구현했다고 판단하지 않았다. 이들은 시험 계획에서 제외한 범위다. 공급자 로그인 정보 접근이나 실행기 호출도 이번 수정에는 없다.

변경 텍스트에서 실제 비밀값과 소유자 PC 절대 경로 및 회사 자료를 발견하지 못했다. 사설 주소 패턴의 일치 3건은 모두 Windows 버전 표기였다. 추적하는 환경 파일은 `.env.example`뿐이다. 비공개 설계 본문을 복사한 변경도 발견하지 못했다. 검토 기록에는 공개 코드에서 확인되는 동작과 계약의 조항 식별만 남겼다. 이 검사는 비밀값의 절대 부재를 보증하지 않는다.

변경 텍스트 파일 중 1,000줄을 넘는 파일은 없었다. 핵심 모듈 2는 기록 미작성 목록에 올라 있다. 소유자의 설명·재현 기록은 대신 쓰지 않았다. 이번 증분에는 새 의존성이나 제삼자 코드가 없다. 기존 Wrapper와 전이 의존성의 출처·라이선스 전체는 다시 검증하지 않았다.

## 확인하지 않은 것

- 작성자의 시험 14개 통과와 31초 소요 시간을 독립 재현하지 못했다.
- 일부러 코드를 망가뜨렸다는 표의 세 실험을 재현하지 않았다. 원본 로그도 확인하지 않았다.
- 실제 DB의 대기 PID와 차단 관계 및 실행 계획은 관찰하지 못했다.
- 늦은 `lost`와 기존 `outcome_unknown` 보유 상태는 실행 시험을 하지 못했다.
- 실제 수신 소켓과 health 응답 및 다른 기기 접속은 재확인하지 않았다.
- 원격 PR 본문·필수 일곱 항목·CI·사람 필수 변경의 판단 이유와 위임 표시는 확인하지 않았다. 이 기록은 병합 직전 확인을 대체하지 않는다.
- 기존 Wrapper 스크립트와 JAR 전체의 무결성은 재검증하지 않았다. 모든 전이 의존성의 라이선스도 재검증하지 않았다.
- 첫 검토 기록 전체는 다시 정독하지 않았다. 두 번째 검토 기록과 이번 수정에 연결된 근거를 확인했다.
- Go 연결 프로그램과 실제 실행기 출력 및 프로세스 종료는 시험하지 않았다. 다른 OS도 시험하지 않았다.

지정된 검토 기록 외의 파일은 수정하지 않았다. 브랜치 생성·커밋·push·원격 변경·main 변경·병합을 하지 않았다.
