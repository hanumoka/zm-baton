## 병합을 막는 지적

### R1. 인증 없는 시험 서버를 루프백에 제한해야 한다

- 위치: `apps/server/src/main/resources/application.properties:3`, `apps/server/src/main/kotlin/io/github/hanumoka/zmbaton/server/Api.kt:72`.
- 검토 항목: 3. 권한, 5. 비밀값과 노출.
- 확신: 중간. 설정과 API 경로를 읽었다. 실제 수신 소켓과 원격 접속은 확인하지 못했다.
- 병합 막음: 예. 보안 지적은 확신이 중간이어도 병합을 막는 기준을 적용했다.

서버 설정에는 포트만 있고 `server.address`가 없다. 별도의 바인딩 제한이나 인증 필터도 없다. 기본 바인딩으로 서버를 실행하면 로컬 PC 밖에서도 접근 가능한 인터페이스에 HTTP 서버가 열린다. 방화벽이 허용하는 환경에서는 인증 없이 할 일을 조회하거나 실행을 청구하거나 종료 사건을 보낼 수 있다.

Compose의 `127.0.0.1:15432:5432`는 PostgreSQL에만 적용된다. 별도로 실행하는 Spring Boot 서버의 `18081` 포트를 제한하지 않는다.

인증과 권한 구현을 시험 범위에서 제외한 결정은 존중한다. 그 대신 시험 서버의 기본 주소를 `127.0.0.1`로 제한해야 한다. 실제 리스닝 주소도 확인해야 한다. 인증 구현 전체를 이번 변경에 추가하라는 지적은 아니다.

### R2. 잘못된 종료 보고를 성공 제출로 바꾸면 안 된다

- 위치: `apps/server/src/main/kotlin/io/github/hanumoka/zmbaton/server/RunService.kt:137`.
- 검토 항목: 1. 수락 조건, 2. 계약, 6. 사실대로 보고.
- 확신: 높음. 허용 목록 검사 뒤의 기본값을 코드로 직접 확인했다.
- 병합 막음: 예.

`end_reason`이 빠지거나 허용 목록 밖이면 서버가 `submitted`를 저장한다. 예를 들어 현재 세대의 새 사건에 `kind=lifecycle`, `phase=ended`, `end_reason=faild`를 넣으면 성공 제출로 처리된다. 숫자나 null을 넣어도 같은 경로를 탄다. 실행 상태는 `ended`가 되고 살아 있는 실행의 유일성 제약에서도 빠진다.

계약이 정한 종료 이유를 검증해야 한다. 알 수 없는 이유에서 성공을 추론하면 안 된다. 잘못된 종료 보고는 명시적으로 거부하고 실행 상태를 유지해야 한다. 누락·오타·잘못된 자료형과 정상 실패 종료를 시험해야 한다. 재전송할 수 있도록 거부된 사건의 저장과 중복 처리 정책도 함께 정해야 한다.

## 추가 지적과 부채 후보

### R3. 현재 세대 조회와 새 청구 사이의 경쟁을 검증해야 한다

- 위치: `apps/server/src/main/kotlin/io/github/hanumoka/zmbaton/server/RunService.kt:82`, 같은 파일 `:114`.
- 검토 항목: 2. 계약, 4. 중복 방지, 7. 시험.
- 확신: 중간. 코드로 추론했다. DB에서 재현하지 못했다.
- 병합 막음: 아니오. 경쟁 조건 후보로 남긴다.

보고 처리는 해당 `runs` 행만 잠근다. 판정에 쓰는 `work_items.generation`은 잠그지 않는다. 조회한 세대는 묶음 처리 내내 재사용한다.

종료된 A의 보고가 세대 1을 읽은 뒤 B의 청구가 세대 2를 커밋하는 순서를 검증해야 한다. 이 경우 A의 처리는 이전 값을 기준으로 계속 진행할 수 있다. 늦은 보고 표시 대신 `last_event_at` 갱신 경로를 탈 가능성이 있다. 이미 종료된 A의 상태를 다시 바꾸는 것은 현재 종료 상태 조건이 막는다. 따라서 새 B의 상태가 반드시 손상된다고 단정하지 않는다.

보고 판정과 세대 증가의 선후 관계를 명시해야 한다. 작업 행 잠금이나 동등한 동시성 제어를 검토해야 한다. 잠금을 추가하면 청구와 보고의 잠금 순서도 맞춰야 한다. 두 트랜잭션을 의도한 지점에서 멈추는 회귀 시험으로 확인해야 한다.

### R4. 동시 청구 시험은 잠긴 행을 건너뛰는 성질까지 증명하지 않는다

- 위치: `apps/server/src/test/kotlin/io/github/hanumoka/zmbaton/server/RunServiceTests.kt:45`, 같은 파일 `:59`, `docs/stage1/compat-test-results.md:27`.
- 검토 항목: 1. 수락 조건, 7. 시험, 12. 문서.
- 확신: 높음. 시험의 동기화와 검증문을 직접 확인했다.
- 병합 막음: 아니오.

시험은 8개 작업을 제출한 뒤 시작 신호를 푼다. 모든 작업자가 DB 청구 직전까지 도착했는지는 확인하지 않는다. 스케줄링 때문에 실질적으로 순차 실행되어도 성공 1건과 충돌 7건은 나온다. `SKIP LOCKED`를 제거하고 잠금 해제를 기다리게 만들어도 이 결과만으로는 구별하지 못한다.

다만 작업자 예외를 숨기는 시험은 아니다. 모든 Future의 결과를 확인한다. 예상 밖 예외와 시간 초과는 실패로 드러난다. 작업과 실행의 세대가 각각 1인지도 확인한다.

별도 트랜잭션이 대상 행의 잠금을 유지하는 동안 청구가 기다리지 않고 거절되는 시험을 추가하는 편이 좋다. 결과 문서의 표현도 동시 호출 시도와 실제 DB 경합 검증을 구분해야 한다.

### R5. 늦은 보고의 상태 불변 시험은 관찰 범위가 좁다

- 위치: `apps/server/src/test/kotlin/io/github/hanumoka/zmbaton/server/RunServiceTests.kt:85`, `docs/stage1/compat-test-results.md:28`.
- 검토 항목: 1. 수락 조건, 7. 시험, 12. 문서.
- 확신: 높음.
- 병합 막음: 아니오.

시험은 A의 종료 이유와 늦은 보고 표시를 확인한다. B의 상태도 확인한다. 실제 `run_events` 행과 작업의 `stage`, `wait_reasons`, `generation`, `version`은 전후 비교하지 않는다. 사건 저장은 반환값으로만 확인한다. A는 이미 종료되어 있어서 종료 상태 갱신의 별도 조건도 상태 변경을 막는다.

현재 코드에서 작업 상태를 갱신하는 사건 경로는 없다. 따라서 이 시험이 현재 실패한다고 보지는 않는다. 다만 통과 기준 2의 작업 상태 불변을 장기적으로 지키려면 해당 행의 전후 비교와 사건 행 조회를 추가해야 한다.

## 확인한 것

1. 청구는 `requested` 조건을 붙인 갱신 한 번으로 권리를 결정한다. 하위 조회에 `FOR UPDATE SKIP LOCKED`가 있다. 작업의 세대 증가와 실행의 세대 기록은 같은 `@Transactional` 메서드에 있다. 갱신 실패는 충돌 예외로 끝난다.
2. 부분 유일 인덱스는 살아 있는 네 상태를 대상으로 한다. `comparison_group is null` 조건도 데이터 모델과 같다. 현재 API는 비교 실행을 생성하지 않는다.
3. 순차 처리에서 옛 세대 사건은 저장된다. `late_reports`만 표시하고 lifecycle 적용 전에 빠져나간다. R3의 동시 청구 상황은 별도 검증이 필요하다.
4. 사건 저장은 `ON CONFLICT DO NOTHING`을 쓴다. 같은 `event_id`는 중복으로 집계된다. 같은 순번에 다른 사건 번호가 오면 거부로 집계된다. 유일성 예외를 잡은 뒤 실패한 PostgreSQL 트랜잭션을 계속 쓰는 구조는 아니다.
5. `createRun`의 중복 키 예외는 런타임 충돌 예외로 다시 던진다. 예외 뒤에 SQL을 더 실행하지 않는다.
6. 활동 일곱 종류와 `lifecycle`이 서비스와 DB 제약에 모두 있다. 알 수 없는 묶음의 `protocol_version`은 거절된다. 복합 필드 이름은 `@JsonProperty`로 snake_case를 지정한다.
7. 보고 API는 `run_id`를 URL로 받는다. `protocol_version`은 묶음에 한 번 둔다. 사건 자체의 `occurred_at`은 선택값이다. 계약의 사건 표를 그대로 직렬화한 형태와는 다르므로 연결 프로그램 연동 때 이 운반 형식을 명시해야 한다.
8. 애플리케이션 SQL의 외부 입력값은 모두 바인딩한다. 문자열 보간은 예외 메시지에만 있다. SQL 주입 경로는 발견하지 못했다.
9. Compose의 공개 포트는 `127.0.0.1:15432:5432`다. 비밀번호에는 환경 변수 필수 지정식이 있다. 실제 `.env`는 추적되지 않는다. `.env.example`의 값은 교체용 예시다. 셸 환경 변수로도 공급할 수 있으므로 공급원이 `.env`로 강제되는 것은 아니다.
10. 변경된 텍스트에서 실제 비밀값과 소유자 PC 절대 경로는 발견하지 못했다. 로그인 정보 파일은 열지 않았다. 시험은 합성 식별자를 사용한다.
11. 결과 문서의 시험 수 8개는 소스의 시험 메서드 수와 맞는다. 기준 2와 3의 구체적인 시나리오 설명도 시험 코드와 맞는다. 실제 통과와 소요 시간은 이번 세션에서 재확인하지 못했다. 결과 문서는 브랜치를 적었지만 각 실행의 정확한 커밋은 적지 않았다.
12. 모듈 2를 「기록 미작성」으로 올린 판단은 맞다. 청구·세대 번호·중복 사건 처리 코드가 처음 들어온다. 소유자의 설명·재현 기록은 대신 작성하지 않았다. PR 번호 `#3`의 실제 연결은 확인하지 않았다.
13. 변경은 서버 설치·호환 시험으로 묶인다. 손으로 쓴 변경 파일은 1,000줄을 넘지 않는다. Gradle 스크립트의 저작권·라이선스 헤더는 유지되어 있다.

검토 항목 9의 의존성 선정 이유·전체 라이선스·잠금 파일과 항목 10의 제삼자 재배포 조건은 완전히 검증하지 못했다. Kotlin·Spring 플러그인과 Gradle 버전은 지정되어 있다. 의존성 잠금 파일은 발견하지 못했다. 재현 가능한 의존성 고정과 시험 서버의 격리는 부채 후보로 남긴다. Go·Electron·화면·외부 동작 실행에 관한 항목은 이 변경에 해당하지 않는다.
