## R2 해석 판정

**작성자의 해석에 동의한다.** 데이터 모델의 `runs`는 `state`와 `end_reason`을 저장 열로 정한다. `last_event_at`도 보고 상태 계산에 쓰는 열이다. 계약의 보고 상태와 실행 시도의 수명 상태는 구별해야 한다.

서버가 적용한 수명 상태와 종료 이유를 읽는 것은 보고 상태 자체를 저장하는 것과 다르다. 이 방식은 역순 종료 보고와 옛 세대 보고 때문에 화면이 서버의 확정 결과를 뒤집는 문제를 막는다. `RunService.applyLifecycle`의 최초 종료 적용 조건과 `ReadApi.RunView`를 대조했다. 새 서버 시험도 서로 다른 묶음의 역순 종료를 다룬다.

앞선 R2의 수정 방향 중 저장 상태 열을 읽지 말라는 제한은 계약에 없는 제한이었다. 이번 검토에서는 그 제한을 유지하지 않는다. 다만 이 동의가 현재 `reportStatus`의 모든 계산 규칙에 대한 동의는 아니다. R6과 R7은 별개의 계약 불일치다.

## 병합 막음 지적

### R6. 열린 질문과 마지막 오류를 다른 규칙으로 계산한다

- 위치: `apps/web/src/runState.ts:25`, `:48`.
- 관련 문서: `docs/stage1/compat-test-results.md:257`, `apps/web/README.md:6`.
- 검토 항목: 2 계약, 6 보고의 정확성, 7 시험, 12 문서.
- 확신: 높음. 계약의 보고 상태 절과 실제 함수 실행으로 확인했다.
- 병합 막음: 예.

열린 질문이 있어도 뒤에 `action`이 오면 `working`이 된다. 질문이 닫혔는지는 읽지 않는다. 반대로 마지막 질문이 이미 해결됐더라도 현재 입력에는 그 사실을 전달할 필드가 없다. 따라서 마지막 활동의 종류만으로 열린 질문의 존재를 판단할 수 없다.

`usage`는 계약의 활동 종류에 포함된다. 그런데 `lastActivity`는 이를 버린다. 종료하지 않은 실행에 `error → usage`가 오면 마지막 사건이 오류가 아닌데도 `error`를 반환한다. 사용량 뒤에도 오류를 유지하려는 의도는 이해할 수 있다. 그러나 계약의 마지막 사건 조건을 마지막 비사용량 활동 조건으로 바꾸는 근거는 없다.

실제 `reportStatus` 호출에서 `question → action`은 `working`이었다. `error → usage`는 `error`였다. 기존 시험은 사용량 제외라는 구현의 선택을 고정할 뿐 계약 일치를 증명하지 않는다.

고칠 방향: 열린 질문 여부를 식별할 근거를 읽기 모델에 제공한다. 오류 판정은 계약의 마지막 사건 조건에 맞춘다. 질문 뒤 독립 동작, 질문 해결, 오류 뒤 사용량의 시험을 추가한다. 질문 기능을 이번 시험에서 미룬다면 해당 표시의 미지원 범위를 명시해야 한다. 계약 전체 구현이라고 설명해서는 안 된다. 계산 규칙 자체를 바꾸려면 소유자가 계약을 먼저 확정해야 한다.

### R7. 생성 후 대기 시간을 첫 응답 지연으로 잘못 센다

- 위치: `apps/web/src/runState.ts:51`.
- 관련 문서: `docs/stage1/compat-test-results.md:257`.
- 검토 항목: 1 경계 조건, 2 계약, 6 보고의 정확성.
- 확신: 높음. 시간 기준의 차이를 코드와 함수 실행으로 확인했다.
- 병합 막음: 예.

생성하고 2분 뒤에 청구한 실행은 청구 직후에도 `no_response`가 된다. 계약의 첫 응답 기한은 실행 시도를 받은 때부터 계산한다. 생성 시각은 그 기준을 대신할 수 없다. `claimed`로 막 바뀐 실행과 오래전에 청구한 실행을 현재 입력만으로 구별할 수도 없다.

`created_at=T0`, `state=claimed`, 사건 없음, 현재 시각 `T0+120초`로 실제 함수를 실행했다. 결과는 `no_response`였다. 아직 조회하지 못한 사건을 빈 배열로 넘기는 최초 로딩에서도 같은 오판이 가능하다.

고칠 방향: 서버가 확정한 청구·수락 시각이나 첫 응답 기한을 전달한다. 사건을 아직 읽지 못한 상태와 서버에 사건이 없는 상태도 구별한다. 생성 후 오래 대기한 실행을 방금 청구하는 시험을 추가한다. 청구 시각이 저장되지 않는다는 사유만으로 계약의 시간 기준을 바꾸지 않는다.

### R8. 빈 순번 뒤의 2,000건을 반복 조회하여 그 뒤를 영구 누락한다

- 위치: `apps/web/src/App.tsx:42`, `:101`, `:102`, `apps/web/src/runState.ts:114`.
- 검토 항목: 1 수락 조건, 2 사건 전달, 6 보고의 정확성, 7 경계 시험.
- 확신: 높음. 실제 병합·커서 함수와 호출부의 페이지 반복을 사용해 재현했다.
- 병합 막음: 예. R3의 남은 실패 경로다.

서버에 순번 1은 없고 2~2101이 저장된 경우를 재현했다. 매 폴링은 연속 구간 0부터 시작한다. 한 번에 200건씩 10페이지를 읽으면 2~2001까지만 얻는다. 다음 폴링도 빈 순번 때문에 0부터 시작한다. 같은 2,000건만 반복한다. 이미 서버에 있는 2002~2101은 순번 1이 채워지기 전까지 읽히지 않는다.

세 번 폴링을 모사한 결과는 다음과 같다. 서버 HTTP 요청을 실행한 시험은 아니다. 정렬된 서버 응답을 모사하고 실제 `applyPolled`와 `contiguousPrefix`를 호출했다.

```text
{"tick":0,"held":2000,"max":2001,"server":2100}
{"tick":1,"held":2000,"max":2001,"server":2100}
{"tick":2,"held":2000,"max":2001,"server":2100}
```

고칠 방향: 빈 구간 재조회와 뒤쪽 진행에 별도 커서를 둔다. 또는 서버의 안정적인 수신 커서를 제공한다. 한 번의 페이지 상한은 유지해도 다음 폴링이 뒤로 진행할 수 있어야 한다. 앞쪽 빈 순번과 10페이지를 넘는 사건이 함께 있는 시험을 추가한다.

## 거부 시험의 증명 범위와 부채 후보

`probe.mjs`는 지정한 밖 서버로 도달한 HTTP 요청을 센다. 양성 대조로 밖 서버에 실제 도달할 수 있음을 먼저 확인하지는 않는다. 따라서 0건이라는 숫자만으로 모든 외부 통신이나 모든 이동이 막혔다고 결론낼 수 없다.

다만 이 시험은 요청 수만 검사하지 않는다. 페이지의 보고 수신과 `new-window`, `navigate`, `redirect` 차단 기록도 요구한다. 페이지가 아예 실행되지 않은 경우는 실패한다. 이번 독립 실행도 그 조건에서 실패했다. 작성자가 기록한 차단 코드 제거 시험은 유용한 보완 근거다. 그 제거 시험은 이번 검토에서 재현하지 않았다.

`did-navigate`에서 되돌리는 것은 이미 일어난 요청을 취소하지 않는다. 시험의 최종 URL 검사는 이동 이력 전체를 관찰하는 검사가 아니다. 지정한 밖 서버로 잠시 이동했다면 요청 수 검사가 이를 잡을 수 있다. 다른 목적지까지 증명하는 것은 아니다.

생존 신호가 없는 구현에서 마지막 사건 시각만으로 무응답을 표시하는 것은 제한된 시험용 추정이다. 문서가 그 한계를 밝힌 점은 확인했다. 실제 생존 신호 조건까지 구현했다고 보지 않는다.

## 실행한 명령과 결과

환경은 Windows NT `10.0.26300.0`, PowerShell `5.1.26100.9549`, Git `2.50.1.windows.1`이다. Node.js는 `24.4.0`, npm은 `11.8.0`이다. 두 앱의 TypeScript는 `7.0.2`다. Vitest는 `5.0.3`, 설치된 Electron은 `44.5.1`이다.

기존 `node_modules`를 사용했다. 시험 프로세스의 `TEMP`와 `TMP`만 허용된 저장소 밖 scratchpad로 지정했다. 시스템 설정은 바꾸지 않았다. 새 빌드 산출물은 만들지 않았다.

거부 시험의 원문은 다음과 같다.

```text

FAIL

- the probe page never reported
```

이 결과를 보안 설정 통과로 세지 않았다. 시험이 자식 프로세스의 표준 오류를 버리므로 종료 원인은 확인하지 못했다. 제품 결함인지 실행 환경 문제인지도 단정하지 않는다.

`probe.mjs`는 `package.json`의 진입점인 기존 `dist/main.js`를 실행한다. 해당 파일에서 새 리디렉션·프레임·권한 차단 코드가 있는 것은 확인했다. 소스와 산출물의 완전 일치를 검증하지는 못했다. 메모리 내 변환 비교를 위해 `require('./apps/desktop/node_modules/typescript')`를 호출했으나 `Error: Cannot find module './apps/desktop/node_modules/typescript'`와 `MODULE_NOT_FOUND`로 실패했다. TypeScript CLI 검사는 별도로 통과했다.

추가 줄의 절대 경로 패턴 2개는 기반 연결 프로그램의 일반 예시였다. 사설 주소 패턴 5개는 Windows 버전 표기였다. UI 기반 비교에는 버전 표기 1개만 잡혔다. 토큰·개인키 대표 패턴은 0건이었다. 코드와 문서의 수동 확인에서도 소유자 PC 경로, 회사 정보, 명백한 비밀값을 발견하지 못했다. 이것을 모든 비밀 형태에 대한 보증으로 보지는 않는다.

## 확인하지 않은 것

- React 컴포넌트에서 지연 응답을 제어하는 통합 시험은 하지 않았다.
- 서버 HTTP·DB 시험과 Gradle은 실행하지 않았다. 새 서버 시험은 코드로 검토했다.
- `vite build`, `npm install`, 패키징은 실행하지 않았다.
- Electron 거부 시험의 통과와 작성자의 차단 코드 제거 시험을 재현하지 못했다.
- 실제 Claude Code 실행, 13초 상태 전환, 배포물의 화면과 크기는 재검증하지 않았다.
- 초기 로드 리디렉션과 실제 장치 권한 요청은 실행하지 않았다.
- 일반 브라우저, macOS, Linux, 접근성은 시험하지 않았다.
- 전이 의존성 전체의 라이선스·재배포 고지·최신 취약점은 재검사하지 않았다.
- 원격 PR 본문의 일곱 항목, CI, 사람 필수 변경의 위임 표시와 브랜치 보호는 확인하지 않았다. 이 기록은 병합 직전 확인을 대신하지 않는다.
- 오래된 로컬 main 비교에 포함된 연결 프로그램 전체를 재검토하지 않았다.

핵심 모듈 2·3은 이미 기록 미작성 목록에 있다. 이번 화면 수정 때문에 새 핵심 모듈의 첫 병합이 생긴 것으로 보지 않는다. 비밀 주입과 DB 마이그레이션 변경은 이번 수정에 없다.

R6~R8을 고친 커밋은 다시 독립 검토를 받아야 한다. 검토 기록 파일 외에는 수정하지 않았다. push, 원격 변경, main 변경, 브랜치 생성, 커밋, 병합은 하지 않았다.
