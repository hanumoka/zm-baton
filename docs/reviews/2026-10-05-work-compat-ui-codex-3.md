## 병합 막음 지적

### R6 잔여. 판정 보류를 문서에만 쓰고 화면에는 표시하지 않는다

- 위치: `apps/web/src/App.tsx:128`, `apps/web/src/App.tsx:172`, `apps/web/src/runState.ts:51`.
- 관련 문서: `docs/stage1/compat-test-ui.md:15`, `apps/web/README.md:6`.
- 검토 항목: 1 수락 조건, 2 계약, 6 보고의 정확성, 12 문서.
- 확신: 높음.
- 병합 막음: 예.

**현재 화면은 두 규칙을 판정하지 않는다는 사실을 알려 주지 않는다.** `reportStatus`에 최근 질문 사건을 주면 `working`을 반환한다. `statusLabel`은 이를 「작업 중」으로 바꾼다. `App.tsx`는 그 값을 별도 한계 설명 없이 「보고 상태」로 표시한다. 화면의 머리말에도 판정 보류 설명은 없다. 질문 사건 목록만으로는 열린 질문을 판정하지 않았다는 사실을 알 수 없다.

청구 뒤 사건이 없는 실행에는 「첫 사건 대기」가 나온다. 그러나 첫 응답 기한을 계산하지 않는다는 설명은 화면에 없다. 사용자는 이 상태를 기한 내의 정상 대기로 읽을 수 있다. 계획 문서는 두 규칙을 판정하지 않고 그렇다고 보여 준다고 명시한다.

**판정 보류 자체는 이번 설치·호환 시험의 미지원 범위로 둘 수 있다.** 계산 근거가 없다고 명시하고 계약의 규칙을 그대로 남기면 계약 값을 다른 방식으로 계산하는 변경이 아니다. 생성 시각으로 청구 시각을 대신하지 않은 수정은 그 방향에 맞는다. 다만 현재처럼 「작업 중」을 제한 없이 보여 주는 처리는 질문 규칙을 보류했다는 의미를 전달하지 못한다. 문서만으로 이 표시 문제를 해소했다고 볼 수 없다.

고칠 방향: 보고 상태 옆에 「입력 필요: 판정하지 않음」과 「첫 응답 기한: 판정하지 않음」을 실제로 표시한다. 또는 동등하게 명확한 미지원 표시를 둔다. 「작업 중」도 지원한 규칙만으로 계산한 결과임을 알 수 있게 한다. 질문 사건과 첫 사건 대기 사례에서 이 문구가 렌더링되는지 확인한다. 계약의 질문 조건이나 시간 기준을 새로 정의할 필요는 없다. 청구 시각의 저장 모델을 바꾸는 일은 소유자 결정으로 남긴다.

### R8 잔여. 앞의 빈 순번 다섯 개가 이후 빈 순번의 재조회를 막는다

- 위치: `apps/web/src/runState.ts:112`, `apps/web/src/runState.ts:116`, `apps/web/src/runState.ts:135`.
- 관련 시험: `apps/web/src/runState.test.ts:109`의 `pollEvents` 묶음.
- 검토 항목: 1 경계 조건, 2 사건 전달, 6 보고의 정확성, 7 시험.
- 확신: 높음. 실제 함수를 호출해 재현했다.
- 병합 막음: 예.

**빈 순번이 여섯 개 이상이면 일부 사건이 서버에 도착해도 화면에 계속 나타나지 않을 수 있다.** `missingSeqs`는 매번 가장 작은 빈 순번 다섯 개만 고른다. 재조회 응답이 요청한 순번과 다르면 버린다. 별도 재조회 커서나 순환 순서는 없다.

서버에 7·8만 있을 때 한 번 조회한다. 그 뒤 서버에 6이 늦게 도착하게 한다. 1~5는 계속 비워 둔다. 이후 세 번 조회해도 화면은 7·8만 보유한다. 각 재조회는 이미 도착한 6을 반환하지만 요청한 1~5와 다르다는 이유로 버린다. 같은 조건이 유지되면 아무리 반복해도 6을 받지 못한다.

```text
tick=1 stored=[6,7,8] held=[7,8]
tick=2 stored=[6,7,8] held=[7,8]
tick=3 stored=[6,7,8] held=[7,8]
각 tick의 요청(after,limit): [[8,200],[0,1],[1,1],[2,1],[3,1],[4,1]]
```

재현은 Node 표준 입력 스크립트에서 실제 `pollEvents`와 `applyPolled`를 가져와 수행했다. 모의 서버는 순번을 오름차순으로 두고 `seq > after`의 앞 `limit`개를 반환했다. 서버 HTTP·DB를 실행한 시험은 아니다.

고칠 방향: 폴링마다 재조회 대상을 순환시켜 모든 빈 순번에 기회를 준다. 또는 조회 결과로 돌아온 아직 없는 사건도 안전하게 병합하는 등 뒤늦은 사건을 버리지 않는 방식을 쓴다. 요청 수의 상한은 유지할 수 있다. 앞의 다섯 빈 순번을 영구히 비워 둔 채 여섯 번째 이후 사건만 늦게 저장하는 회귀 시험을 추가한다.

## 경계 조건과 문서 검토

요청 수는 정상 응답 기준으로 폴링당 최대 15개다. 앞으로 가는 요청은 최대 10개다. 빈 순번 요청은 최대 5개다. 각 빈 순번은 `limit=1`로 한 번만 묻는다. 빈 순번이 없으면 재조회 요청도 없다. `ReadApi.kt:136`의 `coerceIn(1, 500)`은 1을 그대로 허용한다. `ReadApi.kt:90`은 `seq > after`를 순번으로 정렬한다.

199·200·201·2,000·2,001건의 페이지 경계를 실제 함수로 확인했다. 2,001건은 첫 폴링에 2,000건을 받았다. 두 번째 폴링에는 2,001건을 모두 보유했다. 정확히 200건인 경우 다음 빈 페이지를 한 번 더 묻는 동작은 정상이다. 기존 시험의 2~2101 사례도 통과했다.

정상 API 응답에서 앞쪽 조회와 빈 순번 재조회가 같은 사건을 추가하는 경로는 발견하지 못했다. 빈 순번은 이미 받은 사건을 제외해 고른다. 재조회는 그 순번과 일치할 때만 추가한다. 반복 폴링의 기존 사건 중복 제거 시험도 통과했다. 페이지 경계 재현에서도 전체 수와 고유 사건 수가 같았다. 서버의 유일성 제약을 깨는 임의 중복 응답까지 보장했다는 뜻은 아니다.

N7의 양성 대조는 Node 요청이 지정한 밖 서버에 도달함을 확인한다. Electron에서 임의의 외부 통신이 가능함을 입증하는 대조는 아니다. 수정된 문서는 모든 외부 통신의 차단을 증명한다고 쓰지 않는다. 실제 위치 요청과 USB·HID·직렬 장치 접근도 미검증으로 명시했다. 이 범위 구분은 적절하다.

검토 기준 3·4항에 해당하는 새 권한 경로나 중복 실행 기능은 이번 수정에 없다. 보안 방어를 제거하는 변경도 없다. 5항의 공개 금지 정보는 아래 검사를 수행했다. 8항의 손으로 쓴 변경 파일 중 500줄을 넘는 파일은 없었다. 생성된 잠금 파일은 제외했다. 9·10항의 새 의존성이나 제삼자 코드 도입은 이번 수정에 없다. 11항의 기존 부채 N3·N6은 위 표에 남겼다. 12항의 문서 과장은 R6 잔여에 적었다.

| 저장소 | `rg`로 `apps/desktop/dist/main.js`의 확인 모드·결과·리디렉션 분기 조회 | 기존 산출물에 새 분기가 있음을 확인했다. 소스와 산출물의 완전 일치는 검증하지 않았다. |

추가 줄의 경로 검색 결과는 연결 프로그램 주석의 일반 예시였다. 사설 IP 형태로 잡힌 것은 Windows 버전 표기였다. 초기의 넓은 경로 패턴은 URL도 잡아 더 좁은 패턴으로 다시 확인했다. 대표 토큰·개인키 패턴은 발견하지 못했다. 수정 코드와 문서에서도 소유자 PC 경로·회사 정보·비공개 설계 본문의 복사를 발견하지 못했다. 이 검사는 모든 비밀값 형태에 대한 보증은 아니다.

## Electron 실패 기록

**이번 실패는 Electron 설치 디렉터리의 Windows ACL 문제로 보인다.** 두 자식 실행 모두 페이지 검증 전에 종료됐다. 시험 자체는 종료 코드 1이다. 두 자식의 종료 코드는 모두 `2147483651`이다. 페이지 보고와 확인 파일은 없었다. 양성 대조 실패는 보고되지 않았다. 밖 서버 요청 0건은 차단 통과로 세지 않는다.

표준 오류의 마지막 두 줄을 아래에 적는다. 두 경우에 같은 오류가 나왔다. 공개 금지 정보인 절대 경로는 `<electron-dist>`로 치환했다. 시각과 PID는 생략했다.

```text
ERROR:components\os_crypt\sync\os_crypt_win.cc:105] Failed to decrypt: 키를 지정된 상태에서 사용하기에 부적합합니다. (0x8009000B)
FATAL:electron\shell\browser\win\install_dir_access.cc:52] Sandboxed processes cannot read <electron-dist>: its ACL has an entry for an AppContainer package SID but none for ALL APPLICATION PACKAGES, so Windows denies the sandbox token access. Grant it with: icacls "<electron-dist>" /grant *S-1-15-2-1:(OI)(CI)(RX)
```

ACL이나 Electron 설정은 바꾸지 않았다. 재시도도 하지 않았다. 이 실패는 요청대로 병합 막음 지적에 포함하지 않았다. 문서의 거부 시험 통과는 작성자 실행 결과로만 취급한다.

## 확인하지 않은 것

- `vite build`, `npm install`, Gradle, 패키징은 실행하지 않았다.
- 서버 HTTP·DB 시험은 실행하지 않았다. 최소 limit 허용 여부는 코드로 확인했다.
- React 컴포넌트 경쟁과 실제 화면 렌더링은 실행하지 않았다. R6 잔여는 렌더링 소스와 순수 함수 결과로 확인했다.
- Electron의 거부 동작과 확인 모드별 종료 코드를 독립 실행으로 검증하지 못했다.
- 작성자의 방어 코드 제거 시험과 실제 Claude Code 13초 실행은 재현하지 않았다.
- 일반 브라우저, macOS, Linux, 접근성은 시험하지 않았다.
- 새 설치·배포물과 전이 의존성 전체의 라이선스·취약점은 재검증하지 않았다.
- 원격 PR 본문의 일곱 항목, CI, 위임 표시, 브랜치 보호는 확인하지 않았다.
- 오래된 로컬 main 비교에 포함된 연결 프로그램 전체와 관련 Go 파일은 다시 검토하지 않았다.

핵심 모듈 2·3은 기존 기록 미작성 목록에 있다. 이번 수정으로 새 핵심 모듈의 첫 병합이 생기지는 않는다. 주 수정은 일반 코드·시험·일반 문서다. 브랜치 전체에는 Electron 보안·의존성 변경이 있다. 병합 직전의 사람 필수 변경 판단과 위임 표시는 작성자가 확인해야 한다.

검토 기록 외의 저장소 파일은 수정하지 않았다. push·원격 변경·main 변경·병합·브랜치 생성·커밋은 하지 않았다. R6 잔여와 R8 잔여를 고친 커밋은 다시 독립 검토를 받아야 한다.
