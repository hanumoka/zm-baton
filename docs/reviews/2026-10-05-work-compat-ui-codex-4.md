## R6 확인 근거

`App.tsx:173`은 실제 상태 표시 위치에서 `RunStatusLine`을 사용한다. `RunStatusLine.tsx:20`은 보고 상태 문단 바로 아래에 판정 보류 목록을 둔다. `runState.ts:61`은 청구·실행·종료 대기 상태에서 두 규칙과 이유를 반환한다. `styles.css:26`은 해당 줄의 색과 글꼴 두께를 바꾼다.

`RunStatusLine.test.tsx`의 세 시험은 실제 컴포넌트를 `renderToStaticMarkup`으로 HTML로 만든다. 질문 사례는 「작업 중」과 두 판정 보류 문구를 검사한다. 질문 줄의 `relevant` 클래스도 검사한다. 첫 사건 대기는 「첫 사건 대기」와 첫 응답 기한 줄의 강조를 검사한다. 종료 사례는 「완료」와 판정 보류 문구의 부재를 검사한다.

이 시험은 함수의 문자열 반환만 검사하는 시험이 아니다. 실제 컴포넌트의 HTML 문구를 증명한다. 다만 이유 문장 자체를 단언하지는 않는다. 이유의 출력 연결은 소스로 확인했다. 브라우저 배치·색·접근성·App 전체의 상호작용까지 증명하지는 않는다.

## R8과 경계 조건 확인 근거

Node 표준 입력 스크립트에서 실제 `gaps`·`pollEvents`·`applyPolled`를 가져왔다. 모의 서버는 순번을 정렬한다. `seq > after`인 앞 `limit`개를 반환한다. 아래 검사는 모두 assertion을 통과했다.

| 조건 | 실제 결과 |
|---|---|
| 7·8 보유 뒤 6 도착, 1~5 영구 빈 | 다음 폴링에 `[6,7,8]`을 보유했다. 요청은 `(8,200)`, `(0,6)`이었다. |
| 고정된 빈 구간 6~103개 | 각 구간 수 N에서 `ceil(N/5)`번의 폴링 안에 모든 구간을 한 번 이상 물었다. |
| 1002 보유 뒤 501~1001 도착, 1~500 영구 빈 | 세 폴링의 보유 수는 201·401·502였다. 최종 빈 구간은 1~500뿐이었다. |
| 음수·0·중복·비정렬 순번 | `gaps([-10,0,1,3,3])`은 2만 빈 구간으로 반환했다. 음수·0만 있으면 빈 구간이 없었다. |
| 서버에 -1·0·1 | 첫 전방 조회의 `after=0` 때문에 1만 받았다. 계약의 순번은 1부터 시작한다. 비정상 사건의 표시를 보장하는 동작은 아니다. |
| 1과 1조, 1과 `Number.MAX_SAFE_INTEGER` | 빈 구간을 즉시 계산했다. 각 조회의 limit은 1~200이었다. 전체 정수 범위를 순회하지 않았다. |
| 짝수 사건 2,500개 | 한 폴링의 요청은 15개였다. 반환 배열 2,005개를 병합하면 고유 사건 2,000개였다. |

고정된 N개 구간에서는 조회 인덱스가 `(5*t+i) mod N`이다. 연속 폴링의 다섯 인덱스가 N개를 모두 덮는다. 시작 tick이 0이 아니어도 같다. 구간이 유한 번 변한 뒤 고정되면 같은 성질이 적용된다. 구간 수가 계속 늘어나는 무한 스트림에서의 절대 대기 시간 상한까지 증명한 것은 아니다.

PAGE보다 긴 구간은 한 번에 최대 200건을 받는다. 다음 폴링은 새 보유 사건으로 구간을 다시 계산한다. 앞부분이 영구히 비어 있어도 반환된 뒤쪽 사건을 버리지 않는다. 새로 생긴 뒤쪽 빈 구간에도 조회 기회가 간다.

전방 조회는 최대 10회다. 구간 조회는 최대 5회다. 한 폴링의 요청은 최대 15회다. 정상 API 응답 기준 최대 반환 건수는 3,000건이다. 같은 사건이 겹쳐 돌아오면 `applyPolled`가 같은 폴링 안에서도 `event_id`로 거른다. 서버의 순번 정렬과 limit 허용 범위는 `ReadApi.kt`에서 확인했다.

## 새 비차단 지적

### N8. 안전 정수 범위를 넘는 순번은 정확히 표현하지 못한다

- 위치: `apps/web/src/api.ts:29`, `apps/web/src/api.ts:44`, `apps/web/src/runState.ts:150`.
- 검토 항목: 1 경계 조건, 2 계약, 11 부채 후보.
- 확신: 높음.
- 병합 막음: 아니오.

서버와 데이터 모델의 순번은 64비트 정수다. 화면은 JSON 숫자를 JavaScript `number`로 읽는다. `9007199254740992`와 `9007199254740993`은 JSON 파싱 뒤 같은 값이 됐다. 이 범위에서는 빈 구간과 다음 조회 커서가 정확하지 않을 수 있다.

이번 수정이 만든 회귀는 아니다. 계약의 1부터 증가하는 순번으로 설치·호환 시험을 하는 현재 범위에서는 비차단 부채로 둔다. 1조 사례의 통과를 모든 64비트 정수에 대한 보장으로 확대하면 안 된다. 고칠 방향은 허용 상한을 명시해 검증하거나, 정밀도를 보존하는 전송·파싱 형식을 계약 절차에 따라 정하는 것이다. 계약 변경은 소유자 결정이 필요하다.

검토 기록 외의 저장소 파일은 수정하지 않았다. push·원격 변경·main 변경·병합·브랜치 생성·커밋은 하지 않았다. 병합 직전 다섯 조건의 확인은 작성 세션에 남는다.
