### 막음 지적의 재현 조건과 수정 방향

**R1. 자격 증명을 제거하기 전에 원격 주소를 자르면 안 된다.** 합성 입력 `https://` + `SYNTHETIC_` 60회 + `@example.invalid/repo.git`은 자른 뒤 `@`가 사라져 정규식과 일치하지 않는다. `https://example.invalid/repo.git?access_token=SYNTHETIC_TOKEN`도 토큰을 그대로 보존한다. 해당 절단·치환 식을 PowerShell에서 따로 확인했고 두 경우 모두 합성 표식이 남았다. 일반적인 `https://user:password@host/...` 형태만 다루는 기존 시험은 이 경우를 놓친다. 실제 DB 저장까지 실행한 재현은 아니다. 원문 전체를 먼저 구문 분석해 허용된 원격 식별 정보만 재구성하고, 비밀값을 포함할 수 있는 userinfo·쿼리·fragment와 지원하지 않는 형식은 제거하거나 거절해야 한다. 길이 제한은 그 처리 뒤에 적용해야 한다. 근거는 데이터 모델 「직접 연 AI 세션」의 사건 자료 제한과 검토 항목 5다.

**R2. 배치 사이에서도 최신 `current_work`를 보존해야 한다.** 사건의 실제 순서를 다음처럼 둔다: 순번 1은 `share=false`, 순번 2는 비공개 요약이며 `share` 생략, 순번 3은 공개할 요약과 `share=true`. 서버 도착 순서가 1→3→2이면 마지막 SQL이 순번 2의 비공개 요약을 저장하면서 현재의 `share=true`를 유지한다. 다른 세션의 상태 카드와 사람의 세션 목록에 그 요약이 나타난다. 순번 20의 공유 해제 뒤 순번 10의 공유 설정이 도착하는 단순한 경우도 최신 설정을 되돌린다. 이는 협업 계약 v1 「직접 연 AI 세션을 서버에 등록한다」의 사건 순서·공유 규칙과 어긋난다. 마지막으로 반영한 순번을 저장하고, 요약·참조·공유 상태를 순서에 맞게 반영해야 한다. 특히 `share` 생략을 어떻게 해석할지 함께 정하고 역순 배치 거부 시험을 추가해야 한다. 코드로 확인했으며 HTTP/DB 재현은 못 했다.

**R3. 만료 종료는 어느 경로에서 하든 기다림도 닫아야 한다.** 세션 S에 열린 기다림이 있는 상태에서 토큰이 만료되고, sweeper보다 먼저 같은 기기·실행기·실행기 세션 번호로 등록한다. `register()`가 S의 `ended_at`을 설정한 뒤 새 세션을 만든다. `endExpired()`는 `ended_at is null`인 행만 갱신하고 그 반환 ID의 기다림만 닫으므로 S의 항목은 정리되지 않는다. 새 세션이 기다리면 옛 항목과 새 항목이 함께 보인다. 만료된 옛 토큰으로 이를 닫을 수도 없다. 만료 종료와 기다림 종료를 같은 트랜잭션의 공통 경로로 묶고, 재등록이 먼저 실행되는 시험을 추가해야 한다. 협업 계약 v1 「직접 연 AI 세션을 서버에 등록한다」의 만료 시 기다림 종료 규칙 위반을 코드로 확인했다.

**R4. 배치 전체의 파일 잠금 순서를 통일해야 한다.** 같은 저장소에서 A가 X의 잠금을 얻고 B가 Y의 잠금을 얻은 뒤, A가 Y를 요청하고 B가 X를 요청하면 순환 대기가 된다. `pg_advisory_xact_lock`은 사건 하나가 끝나도 풀리지 않는다. PostgreSQL은 교착 시 한 트랜잭션을 중단하므로, 그 배치의 사건·알림·항목은 저장되지 않는다. 실패한 배치를 별도로 재전송하지 않으면 누락으로 남는다. 사건 적용 순서는 유지하되 필요한 파일 잠금은 공통 정렬 순서로 얻어야 한다. 두 파일을 반대 순서로 보내는 동시성 시험이 필요하다. 이 판정은 코드의 잠금 순서와 [PostgreSQL 17의 교착·advisory lock 명세](https://www.postgresql.org/docs/17/explicit-locking.html#LOCKING-DEADLOCKS)를 대조한 것으로, 실제 DB 교착을 재현한 결과는 아니다.

N1은 순번 30의 기다림 뒤 같은 종류의 순번 20이 도착할 때 `wait_seq=30`이면서 문구는 20이 되는 것으로 확인할 수 있다. 또한 실제 순서가 기다림 10→재개 20→기다림 30인데 도착 순서가 10→30→20이면 첫 기다림의 시작 시각이 남는다. 열린 항목의 존재 여부는 유지되지만 내용과 오래 기다린 순서가 부정확해진다.

### 확인한 보안·SQL 동작과 범위

- 토큰은 `SecureRandom` 32바이트로 생성하고 SHA-256만 저장한다. 인증 조회는 세션 ID와 전체 해시를 함께 비교하며 종료·해제·만료를 확인한다. DB 문자열 비교는 상수 시간 비교가 아니지만, 원문이 아닌 고엔트로피 토큰의 해시 비교에서 별도의 실용적 공격 근거는 찾지 못했다. 공급자 로그인 정보를 읽는 코드도 이번 변경에는 없다.
- 새 사람 API 세 곳은 해석 가능한 Bearer 헤더가 있으면 거부하고 감사 기록을 먼저 저장한다. 거부 기록은 실패하는 사람 동작 트랜잭션 밖에 있다. 등록 갱신은 기존 토큰을 교체하고, 사건 수신은 잔여 수명이 6시간 미만이면 같은 토큰의 만료를 12시간으로 연장한다. 갱신 경계와 sweeper 경합은 실행 확인하지 못했다.
- `file_touch.path`와 `repository.prefix`는 절대 경로·드라이브 경로·역슬래시·`.`·`..` 경로 요소를 걸러낸다. 다만 이것이 자유문인 요약·대기 문구 전체의 비밀값·절대 경로 제거를 보장하지는 않는다. 원격 주소의 제거 실패는 R1이다.
- 등록은 기기 행과 등록 키를 잠그고, 살아 있는 등록의 부분 유일 인덱스로 중복을 제한한다. 기다림·알림의 `ON CONFLICT` 대상 열과 조건은 해당 부분 유일 인덱스에 맞는다. 이 문법은 [PostgreSQL 17의 인덱스 추론 규칙](https://www.postgresql.org/docs/17/sql-insert.html#SQL-ON-CONFLICT)과 대조했다.
- 파일 하나의 충돌 확인은 잠금 취득 뒤 별도 조회를 하므로 기본 `READ COMMITTED`에서 앞선 커밋을 볼 수 있는 구조다. 세션 쌍을 정렬한 저장소·경로·쌍 키는 두 방향의 같은 충돌을 묶는다. 알림 판정과 첫 화면 닫기는 같은 트랜잭션이며, 재발 처리도 알림 행을 잠근다. 이 확인이 여러 파일 배치의 안전성을 의미하지는 않는다. [PostgreSQL 17의 격리 수준 명세](https://www.postgresql.org/docs/17/transaction-iso.html#XACT-READ-COMMITTED).
- `waiting`/`resumed`의 항목 개폐는 세션 행 잠금, `max_resumed_seq`, `wait_seq` 비교로 보호한다. 기존 시험에는 재개가 먼저 도착한 경우와 옛 재개가 새 기다림을 닫지 않는 경우가 있다. 내용·시작 시각 문제는 N1이다.

**로컬 무인증의 의미:** `README.md:8`, `docs/stage1/run-locally.md:12`, `application.properties:4`, V2 주석과 새 서비스 주석에 인증 미구현·루프백 사용이 명시돼 있다. 기본 주소는 `127.0.0.1`이지만 환경 변수로 바꿀 수 있다. 현재 로컬 호출자는 헤더 없이 기기·세션 등록, 세션·첫 화면 조회, 알림 판정을 할 수 있다. 등록에 필요한 식별자를 알면 재등록으로 토큰도 교체할 수 있다. AI 역시 Bearer 헤더를 빼면 사람 API에 접근할 수 있으므로, 토큰 거부가 사람과 AI를 분리하는 인증 경계는 아니다. 기존 문서의 신뢰하는 PC 내 개발·호환 시험에 한정된 제약으로는 명시돼 있지만, 협업 계약 v1 「직접 연 AI 세션을 서버에 등록한다」의 사람 인증 요건이나 1단계 보안 완료를 충족했다고 볼 수 없다. 알려진 단계적 미구현 자체를 이번의 추가 막음 지적으로 세지는 않았으며, 소유자는 이 제한을 포함한 권한·보안 변경을 판단해야 한다.

변경 종류는 **일반 코드·권한·보안·DB 구조·일반 문서**다. 계약 정본·의존성·배포 설정·정책 파일 자체의 변경은 없다. 계약과 구현의 차이를 승인 없이 계약 변경으로 간주해서는 안 된다. DB 변경의 되돌리는 방법, 기존 자료 영향, 위협 모델 대응 항목이 PR에 적혔는지는 확인하지 못했다. 병합 전 소유자의 결정 댓글이 필요하며, 호출은 결함 수정과 재검토를 대신하지 않는다.

핵심 모듈 6은 `docs/core-modules/README.md`에 기록 미작성으로 등록됐다. 기준의 첫 병합 목록 등록 요건은 충족한다. 모듈 2·3·6의 미작성 기록이 세 개가 되므로 개발 방식 재검토 기준에도 도달한다. 설명·재현 기록은 소유자 몫이며 대신 작성하지 않았다.

### 부채 후보

- **계약 범위의 명시:** 협업 계약 v1 「충돌을 찾아 관계자에게 알린다」의 실행 시도와 직접 세션 간 충돌은 아직 비교하지 않는다. 「직접 연 AI 세션을 서버에 등록한다」의 작업 바인딩(`work_item_id`), 상태 카드의 최근 결정·살아 있는 실행 시도도 없다. 조직·프로젝트·매니저 생략은 V2에 명시돼 있으나, 이 추가 생략도 이번 묶음의 한계로 명시해야 한다.
- **사후 검토 근거 보존:** `SessionService.kt:479`는 잘못된 `content_hash`·`head`를 거절하지 않고 null로 바꾸며 `patch_hash`는 보존하지 않는다. 첫 충돌 감지 묶음의 범위 밖으로 둔 선택인지 명시해야 한다. 위험 검토를 붙일 때 과거 사건의 누락된 근거는 복원할 수 없다.
- **시험 보강:** R1~R4, N1 외에 동시 재등록, 만료 전후 인증·갱신과 sweeper 경합, 사건 ID 재전송·다른 세션의 ID 재사용, 잘못된 알림 상태, `acknowledged` 반복 유지에 대한 시험이 필요하다. 기존 동시 파일 시험은 두 연결의 실제 경합을 관찰하고 알림과 열린 항목을 함께 검사하면 근거가 강해진다.
- **처리 정책:** `resolved` 알림은 다음 touch에 다시 열고 `acknowledged`·`not_a_conflict`는 유지한다. 키에는 파일 내용 해시가 없어서 같은 세션 쌍·파일의 이후 변경도 묶인다. 협업 계약 v1 「충돌을 찾아 관계자에게 알린다」의 같은 근거를 묶는 원칙을 이 정책으로 구체화한 이유와 적용 범위를 남길 필요가 있다.
- **모듈 크기·공개 API:** `SessionService.kt`는 541줄이며 전체 변경은 1,477줄 추가다. 1,000줄 금지에는 걸리지 않지만, 500줄 초과 파일의 이유와 400줄 초과 변경의 분할 검토 여부는 PR 조회 실패로 확인하지 못했다. 사건 형식을 `packages/contracts`와 공유할 범위도 CLI 추가 전에 정리할 후보이다.

### 확인하지 않은 것

- 테스트의 독립 실행, 실제 PostgreSQL에서의 교착·만료 재등록·역순 공유 사건 재현, 컴파일 경고 0건 여부. 작성자가 보고한 34건 통과를 내 검증으로 표시하지 않았다.
- PR의 필수 여덟 항목, 초안 여부, 최신 원격 커밋, CI 결과, 소유자 호출 시각·결정 댓글, 브랜치 보호와 병합 직전 조건. 조회 실패는 통과나 호출 누락 0건을 뜻하지 않는다.
- 지정된 절 밖의 비공개 설계·결정 기록·위협 모델 전체, 실제 CLI 훅·토큰 보관·갱신 스케줄, 브라우저 알림·집중 모드·권한 중계, 다중 사용자·기기 인증과 전송 암호화, Linux·macOS 동작.
- 실제 운영 DB 마이그레이션·되돌리기와 부하 시험, 제삼자 코드 출처의 전수 감사. 변경에 새 의존성이나 제삼자 코드 고지 파일 추가는 없었다.

검토 기록만 작성했으며 제품 코드 수정·커밋·push·병합은 하지 않았다. R1~R4 수정 후 새 커밋으로 다시 독립 검토받아야 한다.
