### 요청한 경계 조건 검토

**Windows 잠금.** `state.go:172`의 읽기·쓰기 핸들에, `lock_windows.go:28`은 exclusive와 fail-immediately 플래그, reserved=0, offset=0, 길이=1을 넘긴다. `syscall.Overlapped`는 0으로 초기화되어 hEvent도 0이다. 파일이 0바이트여도 EOF 밖 잠금은 허용된다. 동기 핸들과 즉시 실패 플래그의 조합이므로 비동기 잠금 완료를 기다리는 OVERLAPPED 수명이 필요하지 않다. 성공 반환값을 먼저 확인하고 경합 오류 33을 재시도로 처리한다. 같은 프로세스의 두 번째 open도 첫 핸들의 배타 잠금을 우회하지 못하며 해당 Go 시험이 통과했다. [Microsoft LockFileEx 문서](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-lockfileex)

`lock_windows.go:42`의 unlock은 같은 핸들·offset·길이를 사용한다. 잠글 때의 OVERLAPPED 객체 자체를 다시 써야 하는 API는 아니다. 해제 오류는 버리지만 바로 핸들을 닫는다. 정상 해제·재획득 시험에서 결함을 발견하지 못했다. 강제 종료에 따른 OS 해제는 즉각 완료를 단정하지 않고 다음 획득의 제한 시간 안에서 재시도한다. [Microsoft UnlockFileEx 문서](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-unlockfileex)

**Linux·macOS 잠금.** `lock_unix.go:14`의 `LOCK_EX|LOCK_NB`, `EWOULDBLOCK/EAGAIN` 재시도, `LOCK_UN` 뒤 close는 검토한 API 의미에 맞는다. Linux의 별도 open은 서로 독립된 잠금 소유자를 만들며 같은 프로세스에서도 경쟁한다. dup/fork의 공유와 혼동하지 않았다. Linux·Darwin 대상 vet는 통과했지만 실제 커널에서의 실행·사망 후 해제·파일시스템별 차이는 확인하지 못했다. [Linux man-pages 원문](https://raw.githubusercontent.com/mkerrisk/man-pages/master/man2/flock.2), [Apple flock 문서](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/flock.2.html)

**기기 잠금 보유자가 임계 구역에서 멈추는 경우.** 살아 있는 보유자의 잠금을 강탈하지 않는다. 따라서 같은 기기의 다른 세션들도 자기 잠금 대기 상한에서 실패하고 그 호출의 사건을 보내지 못한다. 배타성은 유지하지만 해당 기기의 보고 가용성은 보유자 종료까지 떨어진다. 임계 구역에는 네트워크·Git 호출이 없지만 상태 파일 읽기·쓰기·rename이 있고(`state.go:153`, `:164`), 이 동기 파일 I/O 자체는 context로 중단되지 않는다. 훅에는 watchdog이 있으나 일반 `session work/off` 명령에는 같은 강제 종료 장치가 없다. 디스크 I/O가 실제로 멈춘 상황은 재현하지 않았다.

**watchdog와 남는 작업.** 읽지 않는 stdout 파이프에 큰 합성 상태 카드를 쓰게 하자 시작 훅이 약 4.376초에 종료 0으로 끝났고 watchdog 로그가 남았다. 등록 상태는 이미 저장돼 있었으며 다음 훅은 전송할 수 있었다. 이것은 프로세스 종료 동작을 확인한 것이며 트랜잭션 완료를 확인한 것은 아니다.

- `main.go:102`의 `os.Exit`는 defer를 실행하지 않는다. `state.go:210` 이후 rename 전에 끝나면 토큰을 포함할 수 있는 임시 상태 파일이 남고, 기존 상태에는 새 순번·토큰·표식이 반영되지 않을 수 있다. OS는 핸들과 잠금을 회수하지만 임시 파일 삭제나 서버 동작 취소를 대신하지 않는다.
- 서버 등록 성공 뒤 응답·로컬 저장 전에 끝나면 서버와 로컬 상태가 달라질 수 있다. R9는 이 불확실성을 인증 실패만으로 완료 처리해서는 안 되는 실제 사례다.
- `git.go:142`의 `exec.CommandContext`와 watchdog은 Git 하위 필터 프로세스 전체의 종료를 보장하지 않는다. 하위 프로세스 잔류는 이번에 실행 재현하지 않았다.
- watchdog 설치 전에 `hookLog`가 실행되고(`main.go:85`), watchdog도 종료 전에 동기 로그를 쓴다(`:101`). 로그 I/O 자체가 멈추면 상한 보장은 성립하지 않는다. 따라서 README의 모든 디스크·Git 대기가 상한에서 끝난다는 설명 전체를 검증 완료로 보지 않는다. 이 디스크 정지 경로는 미재현이며 별도 P1로 판정하지 않았다.

**설정 재확인의 창.** 승인 대기 뒤 첫 확인, 백업·임시 파일 생성 뒤 두 번째 확인으로 긴 창은 닫혔다. 마지막 확인과 rename 사이의 창은 남는다. 다른 작성자가 이 프로그램의 잠금에 참여하지 않으면 단순히 자체 잠금을 하나 더 두는 것만으로 모든 외부 저장을 보호할 수는 없다. 이번 R1의 원래 재현 통과와 남은 경쟁 가능성을 구분했다.

**알림 문구·절대 경로.** 자동 알림에서는 정확한 정규식에 맞는 권한 문구만 전송된다. 도구 이름의 실제 존재까지 검증하는 것은 아니지만, 일반적인 절대 경로의 슬래시·역슬래시와 자유 문장은 이 형식에 들어가지 않는다. 허용한 다섯 종류는 [Claude Code 공식 Notification 문서](https://code.claude.com/docs/en/hooks#notification)와 대조했다. 등록의 저장소 뿌리와 file_touch의 `_root`를 전송하지 않는 기존 시험도 통과했다.

다만 **모든 전송 경로에서 절대 경로를 막는 것은 아니다.** `commands.go:46`은 사용자가 명시적으로 준 summary와 refs를 그대로 보낸다. 합성 `session work --ref C:/Synthetic/document.md "synthetic work"`의 절대 경로가 요청에 그대로 도착했다. 이는 수정 전에도 있던 직접 입력 경로이며 R4의 자동 알림 유출과 구분한다. 자동 수집 경로의 개선을 제품 전체의 절대 경로 차단 보장으로 확대해서는 안 된다.

**기타 수정.** `executor_version`의 환경 변수 주입은 제거됐다. 매 current_work에 share를 넣으며, 기본 → private → 생략 → share → 생략의 실제 요청 값은 `true,false,false,true,true`였다. 세션 재등록 코드가 `Private`를 초기화하지 않는 것도 확인했다. 실제 서버의 비공개 표시까지 이 시험으로 확인한 것은 아니다.

### 소유자 호출·변경 종류

1. 변경 종류는 **일반 코드·보안·시크릿·일반 문서**다. 새로운 외부 의존성, DB 구조, 배포 설정, 정책 문서 변경은 없다.
2. 기준 표의 모든 조건 1·2 경로를 `git diff --no-renames --name-only c0341ff HEAD -- ':(top,glob)…'`로 각각 대조했고 출력은 모두 0줄이었다. 새 `cmd/zm-baton/main.go`를 보호 경로인 `cmd/zm-baton-agent/main.go`와 혼동하지 않았다.
3. 소유자 호출은 경로 검사 결과가 아니라 기준의 「결정보다 넓힌 곳」과 보안·시크릿 변경 종류에 근거한다. 1차 검토에도 이미 해당으로 기록돼 있다.
4. 이번 판정은 「병합 막음」이므로 조건 3의 「판정 불가」는 아니다. 작성자의 이견·면제 시도는 확인되지 않았다. 이후 막음 지적 또는 호출 판정에 이견이 있으면 조건 4, 면제 시도는 조건 5에 해당한다.
5. 핵심 모듈은 기존 2·3의 확장이다. 기준 커밋의 `docs/core-modules/README.md`에서 두 모듈은 이미 「기록 미작성」이며 첫 병합 PR이 기재돼 있다.

### 부채 후보

- 토큰 회전과 응답 유실·역전, 401 뒤 살아 있는 등록, 로컬 off 저장 실패를 모의 서버 회귀 시험에 추가해야 한다. 현재 고정 토큰 모의 서버와 정상 E2E만으로 이 실패들을 다루지 못한다.
- 복구 실패에도 재개 보고 의도를 잃지 않는 상태 전이, 설정 교체 마지막 경쟁, watchdog 중 임시 상태 파일·하위 프로세스 처리가 남는다.
- 손으로 쓴 변경 파일은 1,000줄을 넘지 않는다. 가장 긴 `session_test.go`는 520줄이다. 500줄 파일과 큰 PR의 유지·분할 판단 이유는 PR 본문에서 확인하지 못했다.
- 직접 입력 summary·refs와 자동 수집 필드에 적용할 절대 경로 정책을 명확히 하고 거부 시험으로 고정할 필요가 있다. 부채의 최종 판정은 소유자가 한다.

### 확인하지 않은 것

- PR 필수 여덟 항목, 작성 실행기 버전·계정 종류, CI 결과, 원격 PR HEAD, 소유자 질문·결정 댓글. `gh pr view work/sessions-cli --repo hanumoka/zm-baton --json body,comments,headRefOid,url`은 프록시 연결 거부로 실패했다. 빈 항목이 있다고 확인한 것도, 갖춰졌다고 확인한 것도 아니다.
- Linux·macOS 실제 실행, Linux race 시험, NFS·SMB·네트워크 홈에서의 잠금, Windows 다른 사용자 ACL 거부 시험. cross-vet 통과를 이 시험들의 통과로 쓰지 않았다.
- 작성자가 보고한 Docker Linux race 및 실제 서버 E2E 22개 검사의 원본 로그와 재실행. **작성자 보고이며 이번 검토자의 통과 결과가 아니다.**
- 실제 Claude Code 실행과 설치, 실제 공급자 로그인 파일. 연동 서버 `37f231e`는 토큰 회전·인증 부분만 읽었고 전체 서버 PR이나 웹 PR을 재검토하지 않았다.
- 설정의 마지막 read/rename 사이를 강제한 실행 시험, 실제 디스크 I/O 정지, watchdog가 상태 파일 작성 중 끝나는 상황, Git 필터 하위 프로세스 잔류·종료. 해당 분석을 실행 통과로 표시하지 않았다.
- 비공개 설계 전체. 협업 계약 v1 「직접 연 AI 세션을 서버에 등록한다」를 읽어 대조했으며, 비공개 원문이나 소유자 PC 경로를 이 기록에 복사하지 않았다.
