### N1 상세: 새 설치에서 시드 자리값 `owner`를 실제 이름처럼 채운다

1. 새 설치의 서버는 조직 이름과 관리자 표시 이름을 모두 시드 자리값 `owner`로 돌려준다.
2. 바뀐 코드는 이 값을 두 칸에 그대로 채우고 조직 칸에 초점을 둔다(`:38`).
3. `why`가 비어 주 단추가 바로 열린다. 그래서 **Enter 한 번이면** 조직 이름 「owner」, 관리자 이름 「owner」로 최초 설정이 끝난다.
4. 바꾸기 전에는 이렇게 되지 않았다.
   - 조직 칸은 비어 있었다.
   - `:11`은 `owner`를 빈칸으로 바꿨다. 이 줄은 이제 `:28`이 덮어써서 죽은 코드다.
5. 머리 문구 「기존 이름을 확인하고」(`:72`)도 자리값을 실제 이름처럼 보이게 한다.
6. 시험이 이 경로를 잡지 못했다.
   - 합성 시험의 고정 자료에는 실제 이름만 있다(`setup_recovery.py:61-62`).
   - 새 설치 시험은 `Ctrl+A`로 덮어쓰도록 바뀌었다(`server_admin.py:69,72`). 이 시험은 다시 돌리지 않았다.
7. 이름을 잃지는 않는다. 나중에 조직 화면에서 고칠 수 있다(`Org.kt:195,231`).
8. 고칠 방법: 시드 값 `owner`는 두 칸 모두 빈칸으로 시작한다. `:11`의 규칙과 같다. 합성 시험에 시드 사례를 더한다.

### N2 상세: effect 의존성의 `onChanged`가 입력을 덮어쓸 수 있다

1. effect 의존성에 `onChanged`가 있다. 그런데 AuthGate는 그릴 때마다 새 화살표 함수를 넘긴다.
2. 그래서 설정 대기 상태로 AuthGate가 다시 그려지면 effect가 다시 돈다. 이때 다음이 일어난다.
   - `loaded`가 false, `error`가 null로 돌아간다.
   - 서버 이름으로 칸을 다시 채운다(`:22-28`).
3. 실제로 일어날 수 있는 경로가 하나 있다.
   1. 다른 탭에서 다시 로그인해 CSRF가 바뀐다.
   2. 이 탭에서 제출하면 403이 난다(`AuthInterceptor.kt:88-91`).
   3. `:51`이 `onChanged`를 부르고 인증 상태를 다시 읽는다. 아직 설정 대기 상태다.
   4. effect가 다시 돈다. 사용자가 고친 이름과 방금 보인 거절 문구가 사라진다.
4. `/api/server`와 `/api/auth/state`의 답이 서로 어긋나면, 읽기 → `onChanged` → 다시 그리기 → 읽기가 지연 없이 반복된다.
   - 정상 서버에서는 두 답이 같은 행에서 나오므로 반복 경로는 찾지 못했다.
5. 관리 화면은 같은 콜백을 의존성에 넣지 않는다. 같은 문제를 다르게 푼 셈이다.
6. 고칠 방법: 콜백을 ref에 담거나 AuthGate에서 `useCallback`으로 고정한다.

### N4 상세: 403 뒤 안내와 초점

- `report`는 모든 403을 권한을 잃은 것으로 본다.
- CSRF 403이면 다시 읽은 뒤에도 여전히 관리자다. 그런데 poll 의존성이 바뀌지 않아 바로 다시 읽지 않는다.
  - 그래서 자리 표시, 「CSRF … 화면을 다시 불러온다」, 「다시 읽기」가 함께 남는다.
  - 「다시 읽기」를 누르거나 30초가 지나면 회복한다.
- 권한을 정말 잃은 경우의 화면도 부족하다.
  - 빈 상태 문구는 「서버 관리자만 볼 수 있다」뿐이고, 권한이 넘어갔다는 말이 없다.
  - 알림(`role=alert`)은 곧바로 사라져 화면 낭독기가 읽을 틈이 없다.
  - 누른 단추가 없어지면서 초점이 본문으로 떨어진다.

## 짚어 달라고 한 점검 항목

- **상태 전이와 취소**: 문제없다.
  - 설정 화면의 읽기는 `AbortController`로 취소하고, 늦게 온 응답을 버린다(`:21-35`).
  - 제출과 로그아웃은 `inFlight`로 겹치지 않는다.
  - 관리 화면 poll은 `usePoll`이 취소와 중복을 막는다.
  - 이전에 성공하면 `#me`로 옮긴 뒤 인증을 다시 읽는다. 순서가 맞다.
- **비동기 갱신과 useEffect**: N2, N3.
- **정체된 화면**: 403을 받으면 표시를 지우고, 다시 읽은 뒤 빈 상태로 바뀐다. 이 부분은 해결됐다. N3, N4와 새 관리자 쪽 문제는 남는다.
- **기존 이름 손실**: 업그레이드한 설치의 실제 이름은 보존된다. 새 설치는 N1이다. 입력을 덮어쓰는 경로는 N2다.
- **읽기 실패 재시도**
  - 500이나 연결 실패가 나면 거절 줄과 「설정 다시 읽기」가 보인다. 키보드로 다시 읽으면 칸이 보이고 초점이 간다(합성 시험).
  - 다시 실패하면 초점이 본문으로 떨어진다. 사소하다.
- **기기 401과의 관계**: 두 경로가 섞이지 않는다.
  - 401은 `apps/web/src/http.ts:31`의 전역 `onUnauthorized`로 가서 로그인 화면이 뜬다.
  - 403은 두 화면이 각자 인증 상태를 다시 읽는다.
  - 연결 프로그램의 기기 401 처리는 이번 diff에 없다. 다른 검토의 범위다.
- **로그인 정보가 출력될 위험**
  - 화면은 이름, ID, 시각, 모드만 보인다. 오류 문구는 서버 message를 그대로 보이고 토큰이 없다.
  - 결과 JSON과 스크린샷에도 비밀값이 없다. 스크립트에 남은 위험은 N10이다.
- **키보드와 모바일**
  - 두 화면 모두 키보드만으로 완료하는 경로를 시험했다. 설정 화면은 합성 응답, 관리 화면은 실제 API였다.
  - 390에서 가로 넘침이 없다. 단추와 칸은 44px다.
  - 남은 것은 N7, N4(초점)다.
- **실제 화면 문구**
  - 「기존 이름을 확인하고…」는 새 설치에서 맞지 않는다(N1).
  - 읽기에 실패해도 단추 옆 이유가 「기존 설정을 먼저 불러온다」로 남는다. 사소하다.
  - 권한을 잃은 빈 상태가 원인을 말하지 않는다(N4).
  - 「내 계정」과 「나」가 다르다(N5).
- **거짓으로 성공하는 시험**: N8.
  - 결과 JSON의 `unexpected_browser_errors: 0`은 상수다. 그러나 모든 단언을 통과한 뒤에만 쓰므로 거짓 기록은 아니다.
  - 합성 시험은 서버 성공 증거가 아니라고 스스로 밝혔다.
- **권한 판정 위치**: 화면이 권한을 대신 판정하지 않는다.
  - 화면은 서버가 준 `auth.server_admin`과 API의 403을 따른다.
  - `auth.mode`는 단추를 잠그고 이유를 보이는 데만 쓴다.
