# 사람·기기 인증과 전송 암호화 — 1단계 종료 기준 4

1단계 종료 기준 4번 「서버를 이 PC 밖으로 열기 전에 사람·기기 인증과 전송 암호화가 있다」(설계 허브 zm-docs, DEC-0094 1항)를 위한 장치다. 사람은 웹에 로그인하고, 기기(로컬 연결 프로그램과 `zm-baton` 명령)는 기기 토큰을 보내고, 서버를 이 PC 밖에서 받게 하려면 전송 암호화(TLS)가 있어야 서버가 뜬다. **이 판은 서버를 이 PC 밖으로 열지 않는다.** 기본 설정도 compose도 그대로 `127.0.0.1`이다. 밖으로 열지는 소유자가 따로 정한다(아래 「이 PC 밖으로 열기 전에」).

- **대상**: 1단계 서버를 설치해 쓰는 소유자 PC 한 대. 서버를 띄우고 설정을 바꾸는 사람.
- **소유자**: 저장소 소유자. 마지막 확인 2026-10-14(`work/person-device-auth`).
- **전제**: 서버·`zm-baton` 명령·웹이 모두 이 판이다. 서버를 띄우는 방법은 [sessions.md](sessions.md), 업데이트는 [backup-restore-update.md](backup-restore-update.md)를 따른다.
- **근거**: 협업 계약 v1 「등록과 세션 토큰」(사람이 판단하는 일은 웹 인증으로만, 토큰은 해시만), 위협 모델의 「로컬 연결 프로그램은 기기 인증을 받는다」, 결정 DEC-0106(지키는 선 셋).

## 두 모드

서버 설정 `ZM_BATON_AUTH` 하나로 고른다. 기본은 `local`이다. 서버를 다시 띄울 때만 바뀐다.

| | `local`(기본) | `required` |
|---|---|---|
| 사람의 요청 | 로그인 없이 소유자(`usr_owner`)의 요청으로 본다. 지금까지와 같다 | 웹에 로그인한 사람의 요청이다. 로그인하지 않은 요청은 401 |
| 바꾸는 요청 | 그대로 | 로그인 쿠키에 더해 `X-CSRF-Token` 머리가 있어야 받는다 |
| 기기의 요청(청구·보고·임대 갱신·세션 등록·기기 저장소·가져오기·내보내기) | 기기 토큰이 없어도 받는다. 보내면 검사한다(모르는 토큰·폐기한 기기·다른 기기의 토큰이면 거절) | 기기 토큰이 있어야 받는다. 토큰은 그 기기의 요청만 대신한다 |
| 세션 토큰 | 직접 연 세션의 요청에만 쓴다. 사람이 하는 일에 쓰면 거절하고 감사 기록에 남긴다 | 같다 |
| 권한 요청 중계(`ZM_BATON_RELAY=on`) | 켜지지 않는다. 서버 기록에 경고를 남기고 꺼진 채로 둔다 | 켤 수 있다. 답은 로그인한 사람만 한다 |
| 이 PC 밖에서 받기 | 서버가 뜨지 않는다 | TLS가 있을 때만 뜬다 |

어느 모드든, 다른 사이트의 웹 페이지가 브라우저로 보낸 요청(`Sec-Fetch-Site: cross-site`)은 받지 않는다. 이 PC의 다른 웹 페이지가 소유자 몰래 내보내기를 받거나 API를 부르지 못하게 하려는 것이다.

`local`에서 `ZM_BATON_RELAY=on`을 시작 거부로 하지 않고 「꺼진 채로 두고 경고」로 정했다. 이미 `.env`에 `on`을 둔 설치도 업데이트 뒤에 그대로 뜨게 하려는 것이다. 그때는 첫 화면 「권한 요청」 묶음 머리에 「꺼져 있다(로그인을 요구하는 서버에서만 켤 수 있다)」가 보이고, 훅은 지금처럼 터미널에서 묻는다(고도화 후보 H-21).

## 무엇을 어디에 두나 — 비밀값은 해시만

| 비밀값 | 서버에 남는 것 | 다른 곳 |
|---|---|---|
| 비밀번호 | BCrypt 해시(`person_passwords`). 12자 이상, UTF-8로 72바이트까지 | 어디에도 없다 |
| 웹 로그인 | 쿠키 값의 SHA-256(`web_logins`). 7일 안 쓰면 끝나고, 쓰더라도 30일이면 끝난다 | 브라우저의 쿠키. `HttpOnly`·`SameSite=Strict`, TLS면 `Secure`와 `__Host-` 이름 |
| CSRF 토큰 | 저장하지 않는다. 로그인 쿠키 값에서 만든다 | 웹 화면의 메모리 |
| 설정 토큰(처음 비밀번호) | SHA-256(`setup_tokens`). 한 번만 쓰이고, 24시간 지나거나 서버를 다시 띄우면 바뀐다 | **서버 기록에 한 번 나온다**(아래) |
| 기기 토큰 | SHA-256(`devices.token_hash`) | 그 기기의 zm-baton 설정 폴더 `config.json` |
| 기기 로그인 코드 | SHA-256(`device_logins`). 10분 | 화면에 보이는 짧은 코드만 |

비밀번호·토큰은 감사 기록·서버 기록·내보내기에 들어가지 않는다. 내보내기는 기기 토큰의 해시와 위의 인증 표를 빼고 그 사실을 `withheld_fields`·`not_exported`에 적는다. 예외는 설정 토큰 하나다. 서버를 띄운 PC의 서버 기록을 읽을 수 있어야 처음 비밀번호를 정할 수 있게 하려고 일부러 그 자리에 쓴다. 쓰고 나면 소용이 없다.

## `required`로 바꾸기 — 처음 소유자 비밀번호 정하기

**전제조건**: 서버와 기기가 이 판이다. Docker로 띄운 설치면 `deploy/compose/.env`를 고칠 수 있다.

1. **기기마다 기기 토큰부터 받는다.** `required`가 되면 토큰 없는 기기는 거절된다. 각 기기에서 다음을 실행한다.

   ```powershell
   zm-baton status
   ```

   `기기 토큰: 없음`이면, 아직 `local`인 지금 `zm-baton login`을 한 번 실행한다. 이 판 전에 등록한 기기는 같은 기기 번호로 토큰만 받는다(저장소 등록과 기록이 그대로다). `기기 토큰: 있음`이면 할 일이 없다. 웹 「나」의 「내 기기」에서도 기기마다 「기기 토큰 있음 / 없음」이 보인다.
2. **`deploy/compose/.env`에 `ZM_BATON_AUTH=required`를 넣고 서버를 다시 띄운다.**

   ```powershell
   cd $repo
   docker compose -f deploy/compose/compose.yaml --profile app up -d
   ```

3. **서버 기록에서 설정 토큰을 찾는다.** 비밀번호가 없는 조직 소유자마다 한 줄이 나온다.

   ```powershell
   docker compose -f deploy/compose/compose.yaml logs server | Select-String "setup token"
   ```

   `zmbt_`로 시작하는 값이 설정 토큰이다. 이 값을 다른 곳에 붙여 두지 않는다.
4. **브라우저로 `http://127.0.0.1:18081/`을 연다.** 아직 비밀번호가 없으므로 「처음 비밀번호 정하기」가 먼저 열린다. 설정 토큰, 아이디(기본 `owner`), 새 비밀번호 두 번을 넣고 「비밀번호 정하고 로그인」을 누른다.
5. **완료 확인**: 화면이 평소처럼 열리고, 「나」 화면 「로그인」에 「아이디 owner로 로그인했다」가 보인다. `zm-baton status`가 `기기 토큰 확인: 정상 (…, 서버 모드 required)`라고 답한다.

**실패하면**

| 증상 | 대응 |
|---|---|
| 「설정 토큰이 맞지 않거나, 이미 썼거나, 기한이 지났다」 | 서버를 다시 띄우면 새 토큰이 서버 기록에 나온다. 앞 토큰은 쓸 수 없게 된다 |
| 비밀번호를 잊었다 | `.env`에 `ZM_BATON_AUTH_SETUP=usr_owner`를 넣고 다시 띄운다. 서버 기록에 새 설정 토큰이 나오고, 로그인 화면의 「설정 토큰으로 비밀번호 정하기」로 새 비밀번호를 정한다. 그 순간 그 사람의 다른 로그인은 모두 끝난다. 정한 뒤 이 줄을 지운다(남겨 두면 다시 띄울 때마다 토큰이 새로 나온다) |
| 「시도가 너무 많다. N초 뒤에 다시 한다」(429) | 같은 아이디나 같은 주소에서 다섯 번 틀리면 30초 잠기고, 더 틀릴 때마다 두 배(최대 15분)다. 서버를 다시 띄우면 풀린다 |
| 훅이 등록하지 않는다, 연결 프로그램이 멈춘다 | 그 기기에 토큰이 없거나 폐기됐다. `zm-baton status`가 이유를 말한다. 아래 「기기 토큰과 `zm-baton login` 다시 하기」 |
| 다 되돌리고 싶다 | `ZM_BATON_AUTH=local`로 바꾸고 다시 띄운다. 로그인 없이 예전처럼 쓴다. 정한 비밀번호와 기기 토큰은 남아 있어 다시 `required`로 바꾸면 그대로 쓰인다 |

## 기기 토큰과 `zm-baton login` 다시 하기

`zm-baton login`은 서버의 모드를 먼저 묻고 그에 맞게 한다.

1. **`local` 서버**: 한 번 부르고 끝난다. 새 기기면 등록과 토큰을, 이 판 전에 등록한 기기면 같은 기기 번호로 토큰만 받는다.
2. **`required` 서버**: 명령이 주소와 코드를 보여 주고 기다린다(최대 10분).

   ```text
   이 서버는 로그인을 요구한다. 웹에 로그인한 브라우저에서 아래 주소를 열고, 코드가 같은지 본 뒤 「연결 허락」을 누른다.
     http://127.0.0.1:18081/#me?device_login=BCDF-GHJK
     코드: BCDF-GHJK (10분 동안 쓸 수 있다)
   ```

   그 주소를 열면 「나」 화면 맨 위에 「기기 연결 요청」이 보인다. 새 기기인지 내 기존 기기가 새 토큰을 달라는 것인지, 그리고 기한이 적혀 있다. **터미널의 코드와 같을 때만** 「연결 허락」을 누른다. 모르는 요청이면 「거절」한다. 주소 대신 「내 기기」 아래 칸에 코드를 넣어도 된다. 허락하면 명령이 토큰을 받아 끝난다. 이 흐름은 OAuth 기기 인가(RFC 8628)의 모양을 따랐다(클라이언트 등록과 `grant_type`은 두지 않았다).
3. 토큰은 `config.json`에만 있고 화면에 찍지 않는다. 훅의 세션 등록, `zm-baton repo`·`import`·`export`, `zm-baton agent`의 청구·보고·임대 갱신이 이 토큰을 저장한 서버에만 보낸다. `zm-baton export --server <다른 주소>`처럼 다른 서버를 주면 토큰을 보내지 않는다.
4. 이미 토큰이 있으면 `zm-baton login`은 아무것도 하지 않는다. 새 기기로 다시 등록하려면 `--force`를 준다(새 기기 번호가 생기고 저장소는 다시 등록한다).
5. 서버가 401을 주면: `zm-baton agent`는 기다리지 않고 멈추며 「run zm-baton login to get a device token again」을 남긴다. 다른 명령은 「zm-baton login으로 기기 토큰을 다시 받는다」를 덧붙인다. 훅은 세션에 아무것도 보이지 않고 `hook.log`에 남긴다.
6. 설치·호환 시험용 연결 프로그램(`zm-baton-agent`)은 환경 변수 `ZM_BATON_DEVICE_TOKEN`에서 토큰을 읽는다. 명령줄 인수로 받지 않는다(프로세스 목록에 보이지 않게).

## 기기 폐기 — 기기를 잃어버렸을 때

1. 다른 PC의 브라우저로 로그인해 「나」 화면의 「내 기기」에서 그 기기의 「폐기하기」를 누르고, 한 번 더 「폐기하기」를 누른다.
2. 그 순간 그 기기의 토큰이 멈추고, 그 기기에서 등록한 살아 있는 세션이 끝나며(기다림·중계도 닫힌다), 새 청구·세션 등록·저장소 등록이 거절된다. `local` 모드에서도 폐기한 기기 번호로 오는 청구와 등록은 거절된다.
3. **완료 확인**: 그 행이 「폐기함」으로 바뀌고 「폐기하기」 단추가 없어진다. 감사 기록에 「기기 폐기」가 남는다.
4. **폐기가 하지 않는 것**: 그 기기가 이미 돌리던 실행은 그 기기에서 끝까지 돌 수 있다. 서버는 그 실행의 임대 갱신을 받지 않으므로 재연결 유예(5분) 뒤 「결과 확인 필요」로 끝낸다. 아직 청구되지 않은 맡긴 일은 작업 상세의 「맡긴 일 거두기」로 직접 거둔다. 그 기기에 남은 파일과 설정 폴더는 지울 수 없다(위협 모델 T13의 한계와 같다).
5. 되찾은 기기를 다시 쓰려면 `zm-baton login --force`로 새 기기로 등록한다.

## TLS — 두 방법

서버가 이 PC 밖에서 받으려면 둘 가운데 하나가 있어야 한다. 이 PC 안(`127.0.0.1`)에서만 쓰면 둘 다 없어도 된다. TLS를 쓰면 `/api/auth/state`의 `secure`가 `true`가 되고 로그인 쿠키가 `Secure`·`__Host-zmb_login`이 된다.

**A. 서버가 직접 TLS를 한다.** Spring Boot의 표준 설정(`server.ssl.*`)을 쓴다. PKCS12 키 저장소의 경로와 암호를 환경 변수로 준다. 키 저장소 파일과 암호는 저장소에 넣지 않는다.

| 환경 변수 | 뜻 |
|---|---|
| `ZM_BATON_TLS_ENABLED` | `true` |
| `ZM_BATON_TLS_KEY_STORE` | 키 저장소 경로. 예: `file:C:/zm-baton-keys/server.p12` |
| `ZM_BATON_TLS_KEY_STORE_PASSWORD` | 키 저장소 암호 |
| `ZM_BATON_TLS_KEY_STORE_TYPE` | 기본 `PKCS12` |

이 판의 compose에는 키 저장소를 넣는 자리(볼륨)를 만들지 않았다. compose는 이 PC의 루프백에만 열기 때문이다. 서버 시험(`AuthTlsTests`)은 JDK의 `keytool`로 시험 안에서 자체 서명 인증서를 만들어 쓰고 지운다. 다른 사람이 쓰는 서버에는 자체 서명 인증서를 쓰지 않는다.

**B. 앞단 프록시가 TLS를 끝낸다.** 같은 기계의 리버스 프록시(예: Caddy, nginx)가 HTTPS를 받고 서버에는 평문으로 넘길 때 `ZM_BATON_TLS_PROXY=on`을 둔다. 서버는 그 말을 믿고 쿠키에 `Secure`를 붙인다. 프록시와 서버 사이는 같은 기계 안이어야 한다. 그 구간이 네트워크를 지나면 이 설정을 쓰지 않는다. 로그인 시도 제한은 요청 주소로도 세는데, 프록시 뒤에서는 그 주소가 프록시의 것이 된다(고도화 후보 H-50).

## 이 PC 밖으로 열기 전에 — 이 판은 열지 않는다

서버가 받는 주소(`ZM_BATON_SERVER_ADDRESS`, 기본 `127.0.0.1`)가 루프백(`127.0.0.1`, `::1`, `localhost`)이 아니면, 서버는 **`required`와 TLS(A 또는 B)가 둘 다 있을 때만 뜬다.** 하나라도 없으면 포트를 열기 전에 멈추고 무엇이 빠졌는지 출력한다.

```text
APPLICATION FAILED TO START
Description:
zm-baton refused to start: the server is set to listen on 0.0.0.0, beyond this PC's loopback, without: ZM_BATON_AUTH=required ...; TLS: ...
```

Docker 안에서는 서버가 컨테이너의 모든 주소(`0.0.0.0`)에서 받고, compose가 그 포트를 이 PC의 루프백(`127.0.0.1:18081`)에만 연다. 그래서 compose는 `ZM_BATON_PUBLISHED_ON_LOOPBACK=on`으로 그 사실을 서버에 알린다. **compose의 `ports` 줄을 바꾸면 이 줄을 지운다.** 남겨 두면 서버가 루프백만 열린 줄 알고 `local`로 뜬다(고도화 후보 H-53).

밖으로 여는 것은 소유자의 결정이다. 열기 전에 다음을 모두 확인한다.

1. 소유자가 무엇을, 누구에게, 어떤 네트워크(사내망·VPN·인터넷)로 열지 정하고 결정 기록에 남겼다.
2. 서버가 `required`다. 모든 기기에 토큰이 있고, 쓰지 않는 기기와 토큰 없는 기기는 폐기했다.
3. TLS가 있다. 다른 사람이 쓰면 그 사람의 브라우저가 믿는 인증서다(자체 서명 금지).
4. 방화벽이 정한 범위 밖의 접속을 막는다.
5. [고도화 후보 목록](../hardening-backlog.md)을 전부 다시 봤다(그 목록 「쓰는 방법」 4). 특히 H-49(데이터베이스 행 수준 보안 없음), H-50~H-54(이 판에서 더한 것), 사람이 둘 이상일 때의 H-45~H-48.
6. 백업과 되돌리기를 시험했다([backup-restore-update.md](backup-restore-update.md)).
7. 비밀번호 하나로만 로그인한다는 한계를 받아들였다. 패스키(WebAuthn)와 2단계 인증은 아직 없다.
8. 서버 기록을 볼 수 있는 사람을 정했다. 처음 비밀번호와 재설정의 설정 토큰이 서버 기록에 나온다.
9. 권한 요청 중계를 켤지 정했다(켜면 로그인한 사람만 답한다).

## 1단계 종료 기준 4를 어디까지 채웠나

| 항목 | 상태 |
|---|---|
| 사람 인증 | 있다. 비밀번호(BCrypt)·로그인 쿠키·CSRF·시도 제한·로그아웃·비밀번호 바꾸기, 처음 비밀번호는 설정 토큰 |
| 기기 인증 | 있다. `zm-baton login`의 기기 토큰(로그인을 요구하는 서버는 웹 승인), 기기 요청마다 검사, 그 기기만 대신, 폐기 |
| 전송 암호화 | 설정 경로가 있다(A·B). 자체 서명 인증서로 시험만 했고, 실제 인증서로 연결해 보지는 않았다 |
| 밖에서 받기 전의 막음 | 있다. 루프백 밖이면 `required`와 TLS 없이는 뜨지 않는다 |
| 실제로 밖으로 열기 | 하지 않았다. 소유자 결정 대기 |

그래서 기준 4의 문장 「열기 전에 … 있다」의 장치는 갖췄다. 여는 결정과 위 점검은 소유자의 몫이다.

## 이 판이 하지 않는 것

- 패스키(WebAuthn)와 2단계 인증. 다음 판에서 본다. OAuth·OIDC로 외부 로그인에 붙이는 것도 없다(1단계는 이 PC 하나라 외부 신원 제공자가 없다)
- 운영자가 화면에서 다른 사람의 설정 토큰을 만드는 것(지금은 `ZM_BATON_AUTH_SETUP`), 로그인 기록 화면, 기기 이름 바꾸기
- compose에서 TLS 키 저장소를 넣는 자리
- 서버를 이 PC 밖으로 여는 것
