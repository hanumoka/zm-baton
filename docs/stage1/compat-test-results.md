### 동시 청구를 두 가지로 확인했다

첫째 시험은 **동시 호출 시도**다. 실행 시도 20개마다 스레드 8개가 같은 실행을 청구했다. 매번 하나만 성공하고 일곱은 거절됐고, 작업과 실행의 세대 번호는 1이었다. 다만 이 시험은 스레드들이 정말 같은 순간에 DB에 닿았는지 보장하지 않는다. 순서대로 실행돼도 같은 결과가 나온다.

둘째 시험은 **실제 DB 잠금 경합**이다.

1. 다른 트랜잭션이 실행 행을 잠근다.
2. 그 트랜잭션은 청구가 돌아올 때까지 잠금을 풀지 않는다.
3. 청구를 보낸다. 청구가 잠금을 기다리는 구현이라면 영영 돌아오지 않고, 시험은 10초 뒤 실패한다.
4. 청구는 충돌로 거절됐다. 잠금이 풀린 뒤 다시 청구하자 성공했다.

예전의 「2초 안에 거절」 같은 시간 판정은 없앴다. 남은 10초·30초 제한은 시험이 멈춰 버리지 않게 하는 안전장치다. 아주 느린 환경에서는 정상 구현도 이 제한을 넘겨 실패할 수 있다.

### 늦은 보고가 상태를 바꾸지 않음을 확인했다

1. 실행 A가 끝난 뒤 실행 B가 같은 작업에서 세대 2를 받았다.
2. 그 상태에서 두 가지를 기록해 두었다. 작업 행의 단계·대기 이유·세대·버전·수정 시각과, 실행 B의 상태·종료 이유·세대·늦은 보고 표시다.
3. A가 세대 1로 「성공 제출로 종료」를 보냈다.
4. 응답은 저장 1·늦음 1이었다. 사건 행은 세대 1, 종류 `lifecycle`으로 남았다.
5. A에는 「늦은 보고 있음」이 붙었고 종료 이유는 `replaced` 그대로였다.
6. 2단계에서 기록한 값은 모두 그대로였다. 실행 B의 다른 열(임대 만료 시각·마지막 사건 시각 등)은 비교하지 않았다.

보고 처리와 세대 증가가 겹치는 경우도 시험했다.

1. 다른 트랜잭션이 작업 행을 잠근다. 세대 번호는 아직 올리지 않는다.
2. 보고를 보낸다.
3. `pg_stat_activity`와 `pg_blocking_pids`로, 보고 SQL이 1단계의 그 트랜잭션에 막혀 기다리는 것을 확인한다. 막고 있는 연결의 번호까지 맞춰 본다. 이 시험에는 새 작업 행 하나에 보고 연결 하나만 있으므로 이것으로 대상 보고를 가려낸다. 같은 행에 여러 보고가 함께 기다리는 경우까지 가려내지는 않는다.
4. 그 뒤에야 다른 트랜잭션이 세대 번호를 올리고 끝난다.
5. 보고는 올라간 세대를 기준으로 늦은 보고로 판정됐다.

보고 처리가 실행 행과 작업 행을 함께 잠그기 때문이다. 이 시험은 진짜 청구 대신 SQL로 세대만 올려 청구를 흉내 낸다. 그래서 진짜 서비스 경로는 따로 시험했다. 옛 실행 A의 보고와 새 실행 B의 청구를 동시에 출발시키기를 20번 했다. 매번 두 결과를 각각 10초 제한으로 기다렸고, 둘 다 제한 안에 돌아왔다. 교착은 없었다. 보고는 어느 쪽이 작업 행을 먼저 잡았는지에 따라 정상 보고 또는 늦은 보고가 됐다.

### 보고는 자기 실행 시도가 청구 때 받은 세대 번호를 실어야 한다

계약 v1은 보고의 세대 번호를 「청구할 때 받은 세대 번호」로 정한다. 그래서 서버는 보고의 세대 번호가 그 실행 시도의 세대 번호와 같을 때만 받는다. 아직 청구되지 않은 실행 시도에는 세대 번호가 없으므로 어떤 보고도 받지 않는다. 작업의 현재 세대 번호를 실어 와도 마찬가지다. 다른 실행 시도의 세대 번호를 실은 보고도 거절한다.

### 잘못된 종료 보고를 거절한다

종료 보고(`lifecycle`, `phase=ended`)는 계약이 정한 종료 이유 다섯(`submitted` · `failed` · `cancelled` · `replaced` · `lost`) 중 하나를 가져야 한다. 종료 이유가 없거나, 오타(`faild`)이거나, 숫자·null이면 그 사건을 거절한다. `phase`가 `started`·`ended`가 아니어도 거절한다. 서버는 빠진 이유를 성공으로 추측하지 않는다.

거절된 사건은 저장하지 않는다. 거절된 동안 실행 상태는 `running` 그대로였다. 고친 내용을 거절된 사건과 같은 사건 번호·같은 `seq`로 다시 보내자 새 사건으로 저장됐고, 실행은 `ended`/`failed`가 됐다.

### `lost`로 끝나면 작업에 「결과 확인 필요」를 단다

계약 v1은 실행 시도가 `lost`로 끝나면 작업에 `outcome_unknown`(결과 확인 필요)을 달라고 정한다. 서버는 실행을 끝낼 때 이 대기 이유를 한 번만 더하고 작업의 버전을 올린다. 같은 실행에 종료 보고가 한 번 더 와도 작업은 바뀌지 않았다.

### 시험이 결함을 잡는지 일부러 망가뜨려 확인했다

코드를 하나씩 망가뜨리고 해당 시험만 돌렸다. 확인한 뒤 코드는 되돌렸다.

| 망가뜨린 것 | 실패한 시험 |
|---|---|
| 청구에서 `SKIP LOCKED`를 뺐다 | 잠긴 실행 행을 건너뛰는 시험 |
| 보고 처리에서 작업 행 잠금을 뺐다 | 보고가 세대 증가를 기다린 뒤 늦은 보고로 판정되는 시험 |
| 실행 자신의 세대 확인을 「작업의 현재 세대보다 크면 거절」로 되돌렸다 | 보고가 자기 실행의 세대를 실어야 하는 시험 |

### 서버는 이 PC 안에서만 접속을 받는다

인증이 아직 없으므로 서버는 기본으로 `127.0.0.1`에만 연다(`ZM_BATON_SERVER_ADDRESS`로 바꿀 수 있다). 서버를 실행하고 확인했다.

- 18081 포트에서 듣는 주소는 `127.0.0.1` 하나였다.
- `http://127.0.0.1:18081/actuator/health`는 200을 돌려줬다.
- 이 PC의 다른 IPv4 주소로 18081에 접속하자 거절됐다.

다른 기기에서 접속해 보지는 않았다.

함께 확인한 것: 한 작업에 살아 있는 실행 시도가 있으면 새 실행 시도 만들기가 거절되고(부분 유일 인덱스), 그 실행이 끝나면 다시 만들 수 있다. 알 수 없는 활동 종류와 모르는 `protocol_version`은 거절된다. HTTP로 다섯 API를 차례로 부르는 시험도 통과했다.

### 막힌 것

없다. `postgres:latest` 대신 `postgres:17`로 고정했다.

### Claude Code 출력이 사건 7건으로 저장됐다

1. 서버 API로 작업 하나와 실행 시도 하나를 만들었다.
2. 연결 프로그램을 `--once`로 실행했다. 허용 도구는 `Read` 하나, 지시는 「`hello.txt`의 첫 줄만 답하라」였다.
3. 연결 프로그램이 실행 시도를 청구해 세대 1을 받고, `claude -p`를 셸 없이 띄웠다.
4. 연결 프로그램은 종료 코드 0으로 끝났다. 종료 이유는 `submitted`였다.
5. 서버에 사건 7건이 이 순서로 저장됐다. 시작(PID·세션 번호), 도구 호출(`Read`), 사용량(한도 정보), 도구 결과, 답(`zm-baton compat check`), 최종 사용량, 종료.
6. 사건 번호는 모두 `evt_`로 시작했다. 서버 응답은 저장 7, 중복·늦음·거절 0이었다.

Claude Code의 `system` 줄은 사건으로 보내지 않고 연결 프로그램 로그에 개수만 남았다.

### 틀린 표식은 거부하고, 붙잡아 둔 실행기만 끝냈다

Windows에서 연결 프로그램은 실행기를 이렇게 붙잡는다.

1. 실행기를 일시 정지 상태로 띄운다.
2. 그 프로세스의 핸들을 연다. 핸들이 열려 있는 동안 운영체제는 그 PID를 다른 프로세스에 주지 않는다.
3. 새 작업 객체(Job Object)에 실행기를 넣은 뒤 실행을 재개한다. 실행기가 보통 방법으로 띄우는 하위 프로세스는 같은 작업 객체에 들어간다. WMI처럼 다른 경로로 띄운 프로세스는 들어가지 않을 수 있다.
4. 종료할 때는 붙잡은 핸들로 실행기가 살아 있는지 보고, 같은 핸들로 명령줄을 읽어(`NtQueryInformationProcess`) 세션 번호(표식)가 있는지 확인한다. 그다음 PID가 아니라 작업 객체를 끝낸다. 확인과 종료 사이에 실행기가 끝나고 종료 호출이 성공하면, 그 작업 객체에 남은 하위 프로세스만 끝난다. 그 사이 명령줄 조회가 실패하면 아무것도 끝내지 않는다.
5. 핸들은 종료 판단이 끝난 뒤에 닫는다.

실제 Claude Code로 두 가지를 확인했다.

- 실행 시간 제한(20초) 시험: 시간이 지나자 연결 프로그램이 표식을 확인하고 실행기를 끝냈다. `claude.exe`와 그 하위 프로세스(`mcp-server-windows-x64.exe`)가 모두 끝났다. 끝났는지는 미리 열어 둔 프로세스 핸들로 확인했다. 서버에는 시작, 오류(「실행 시간 제한」), 종료(`failed`) 3건이 저장됐다.
- 표식 시험: 시험용 임시 프로그램이 연결 프로그램과 같은 방법으로 실제 `claude.exe`를 띄워 붙잡았다. 틀린 표식으로 종료를 요청하자 「명령줄에 표식이 없다」며 거부했고, 1초 뒤에도 실행기는 살아 있었다. 맞는 표식으로 요청하자 실행기와 하위 프로세스가 끝났다. 끝난 뒤 다시 요청하자 「이미 끝났다」며 거부했다. 이 임시 프로그램은 저장소에 넣지 않았다.

이 시험을 돌린 Claude Code 세션 자신과, 다른 Claude Code·Codex 세션의 하위 프로세스는 영향을 받지 않았다.

### 결과 줄 없이 실행기가 사라지면 `lost`가 된다

1. 오래 걸리는 실행을 띄웠다. 실행 시간 제한은 3분으로 두었다.
2. 연결 프로그램 밖에서, 명령줄에 표식이 있는 것을 확인한 뒤 그 실행기를 끝냈다. 스스로 죽은 경우와 같은 상황이다.
3. 연결 프로그램은 결과 줄을 받지 못했으므로 오류 사건과 종료(`lost`)를 보냈다.
4. 서버는 실행 시도를 `ended`/`lost`로 바꾸고 작업에 `outcome_unknown`을 달았다.

### 서버가 사건을 받지 못하면 성공으로 알리지 않는다

실행기가 결과를 제출했어도 서버가 사건을 받지 못했거나 거절했으면, 연결 프로그램은 「전달 실패」를 따로 돌려주고 `--once`의 종료 코드를 1로 한다. 서버가 그 실행을 아직 실행 중으로 보고 있을 수 있기 때문이다. 단위 시험으로 세 경우를 확인했다. 서버 오류(500), 영구 거절(400), HTTP 200 안의 개별 거절이다. 마지막 사건을 보내며 기다리는 시간은 30초까지다. 이미 보내고 있던 요청도 이 제한에 걸리면 끊는다.

### 시험이 결함을 잡는지 일부러 망가뜨려 확인했다

| 망가뜨린 것 | 실패한 시험 |
|---|---|
| 종료 전 표식 확인을 건너뛰었다 | 틀린 표식을 거부하는 시험 |
| 종료 전 「살아 있는지」 확인을 건너뛰었다 | 실행기가 이미 끝났으면 아무것도 끝내지 않는 시험 |
| 보고 전달 결과를 늘 성공으로 돌려주게 했다 | 서버가 사건을 받지 못하면 전달 실패를 알리는 시험(세 경우 모두) |
| 종료 대기에서 시간 제한을 무시했다 | 보내던 요청도 종료 제한에 걸리는 시험 |

확인한 뒤 코드는 되돌렸다.

### 확인하지 못한 것

- 실제 Ctrl+C 신호가 연결 프로그램에 전달되는 경로는 시험하지 않았다. 단위 시험은 실행 중 context를 취소하는 경로(`cancelled`)만 확인한다.
- Linux 종료 경로는 CI(PR #7)의 ubuntu에서 처음 실제로 돌았다. 시험(`TestKillChecksTheMarkerBeforeStopping`)이 틀린 표식은 거부하고 맞는 표식으로 실행기를 끝내는 것을 확인했다. Linux에서는 실행기 하나만 끝내고 하위 프로세스는 끝내지 않는다. 실제 Claude Code를 Linux에서 돌려 보지는 않았다.
- macOS는 시험하지 않았다. 명령줄을 읽을 수 없어 종료를 거부한다.
- Windows 작업 객체 종료 시험은 CI의 windows 실행기(이 PC가 아닌 기기)에서도 통과했다.
- 다른 기기의 연결 프로그램이 이 서버에 붙는 경우는 시험하지 않았다. 서버가 아직 루프백에만 열리기 때문이다.

### 다음 단계로 넘기는 것

- 도구 호출 입력에는 작업 폴더의 절대 경로가 그대로 들어간다. 도구 결과 본문은 4,000자로 자르기만 하고 비밀값을 가리지 않는다. 비밀값 가리기는 금고 단계(2단계)에서 다룬다.
- 한도 사건(`rate_limit_event`)에는 추가 과금 상태를 뜻하는 값(`overageStatus`)이 들어 있었다. 추가 과금 신호를 읽는 작업(DEC-0083)에서 이 값을 쓸 수 있는지 확인한다.
- 연결 프로그램이 재시작하면 `seq`를 1부터 다시 매긴다. 같은 실행 시도를 이어서 보고하는 재개는 1단계 본작업에서 정한다.
- 실행기가 정상으로 끝난 뒤 남은 하위 프로세스는 작업 객체에 남아 계속 돈다. 실행이 끝날 때 남은 하위 프로세스를 정리할지는 1단계 본작업에서 정한다.

### 데스크톱 창에서 보고 상태가 바뀌는 것을 봤다

1. 서버 API로 작업 하나와 실행 시도 하나를 만들었다.
2. Electron을 확인 모드로 띄웠다. 확인 모드는 창을 숨긴 채 가장 최근 작업을 사람처럼 눌러 열고, 0.5초마다 화면의 보고 상태·실행 시도 상태·사건 수를 읽는다. 실행 시도가 끝나는 것을 보면 종료 코드 0, 시간 안에 못 보면 2로 끝난다.
3. 4초 뒤 연결 프로그램을 `--once`로 실행했다. 실제 Claude Code가 `hello.txt`의 첫 줄을 읽어 답했다.
4. 화면의 보고 상태는 「청구 대기 → 작업 중 → 완료」 순서로 바뀌었다.
5. 마지막에 실행 시도 상태는 `ended/submitted`로 서버의 값과 같았고, 사건 수는 7로 서버에 저장된 수와 같았다. 확인 모드의 결과는 `ended`, 종료 코드는 0이었다.
6. 확인 모드가 시작부터 끝까지 걸린 시간은 13초였다. 청구와 첫 사건 사이가 0.5초보다 짧아 「첫 사건 대기」는 화면에 잡히지 않았다.

### 화면이 서버와 다른 결론을 내지 않게 한 것

Codex 검토가 찾은 R1~R3·R6~R8은 화면이 서버나 계약과 다른 것을 보여 줄 수 있는 경로였다. 이렇게 고쳤고, 각각 단위 시험이 있다.

- 실행 시도를 바꾼 뒤 늦게 온 옛 응답: 선택이 바뀌면 옛 요청을 취소하고, 응답이 와도 지금 고른 실행 시도의 것이 아니면 버린다. 순수 함수 시험은 「A를 고른 뒤 B로 바꿨는데 A의 응답이 B보다 늦게 왔다」 경우를 다룬다. 화면 컴포넌트 자체를 띄우는 시험은 없다.
- 종료 이유: 화면이 종료 사건을 다시 고르지 않고, 서버가 처음 적용해 저장한 종료 이유를 그대로 쓴다. 서버 시험이 「순번 10의 `lost`를 먼저 받고, 다른 묶음으로 순번 9의 `submitted`를 받은」 경우에 읽기 API가 `lost`를 돌려주는지 확인한다. Codex 두 번째 검토는 이렇게 서버의 저장값을 읽는 해석에 동의했다.
- 늦게 저장된 작은 순번과 많은 사건: 화면은 받은 가장 큰 순번 뒤를 한 번에 최대 10쪽(2,000건)까지 묻는다. 빈 순번은 구간으로 계산해 폴링마다 다섯 구간까지 다시 묻고, 묻는 구간을 폴링마다 돌아가며 바꾼다. 빈 구간 조회가 요청하지 않은 순번을 돌려줘도 버리지 않는다. 구간은 받은 순번에서 계산하므로 순번이 갑자기 아주 커져도 계산량이 늘지 않는다. 시험은 다섯 경우를 확인한다. 순번 1이 빠진 채 2~2101이 저장된 경우, 1·3·4를 받은 뒤 2가 저장된 경우, 1~5가 계속 빈 채 6이 늦게 저장된 경우, 빈 구간이 15개인데 15번째에 늦게 저장된 경우, 순번 1과 1조가 함께 있는 경우다.

보고 상태는 협업 계약 v1의 표를 따르되, 판정할 근거가 없는 규칙은 판정하지 않는다.

- 실행 시도가 끝났으면 서버가 정한 종료 이유로 완료(`submitted`)·오류(`failed`·`lost`)를 정한다. `cancelled`·`replaced`는 계약 표에 없어 「취소됨」「다른 실행으로 넘김」으로 따로 보여 준다. 이것을 정식 보고 상태로 넣을지는 소유자가 정한다.
- 끝나지 않았으면, 종류와 상관없이 마지막 사건이 `error`일 때 오류다. 오류 뒤에 사용량 사건이 오면 오류가 아니다. 계약 문장 그대로다.
- 서버가 기록한 마지막 사건 시각 뒤 10분이 지나면 응답 없음이다. 생존 신호가 아직 없으므로 「생존 신호만 오고 사건이 없다」는 이 시각으로만 판단한다.
- 「입력 필요」는 판정하지 않는다. 질문에 답이 왔는지 알 수단(질문 경로)이 아직 없다. 질문 사건은 사건 목록에는 그대로 보인다.
- 「첫 응답 기한(60초) 안에 사건이 없으면 응답 없음」은 판정하지 않는다. 계약은 청구 시각부터 재도록 하는데 데이터 모델에 청구 시각 칸이 없다. 청구됐지만 서버에 사건이 없는 실행은 「첫 사건 대기」로 보여 준다.
- 화면은 끝나지 않은 실행의 보고 상태 바로 아래에 이 두 규칙을 「판정하지 않음」과 그 이유로 보여 준다. 그래서 「작업 중」이 이 두 규칙까지 확인한 결과로 읽히지 않는다. 시험이 질문 사건이 있을 때와 첫 사건을 기다릴 때 이 문구가 실제 HTML에 나오는지 확인한다.

### 서버 밖으로 나가지 못하고 권한을 얻지 못한다

거부 시험(`apps/desktop/test/probe.mjs`)은 Node 내장 모듈만 쓴다.

1. 「안」 서버(`127.0.0.1`)가 zm-baton 서버 대신 시험 페이지를 낸다. 「밖」 서버(`127.0.0.2`)는 들어온 요청을 센다.
2. 양성 대조: 시험이 먼저 밖 서버에 직접 요청을 보내 도착하는지 확인한다. 도착하지 않으면 「0건」이 의미가 없으므로 시험이 실패한다.
3. 첫째 경우: 데스크톱 껍데기를 안 서버에 붙여 띄운다. 시험 페이지가 알림 권한 요청, 위치·알림 권한 확인, 새 창, 밖 서버를 가리키는 iframe, 밖 서버로의 직접 이동, 밖 서버로 보내는 리디렉션을 차례로 시도한다.
4. 둘째 경우: 처음 여는 주소 자체가 밖 서버로 리디렉션되게 해서 띄운다.
5. 결과: 두 경우 모두 밖 서버에 들어온 요청은 0건이었다. 첫째 경우에 권한은 모두 「거부」였고 새 창은 열리지 않았으며 창은 끝까지 안 서버에 있었다. 둘째 경우에 껍데기는 리디렉션을 막고 「로드 거부」로 종료 코드 1을 냈다.

이 시험이 보이는 것은 위 시나리오에 한정된다. 다른 프로토콜, 다른 목적지, 실제 위치 요청, USB·HID·직렬 장치 접근은 시험하지 않았다.

이 시험이 결함을 잡는지 껍데기 코드를 하나씩 망가뜨려 확인했다. 확인한 뒤 코드는 되돌렸다.

| 망가뜨린 것 | 결과 |
|---|---|
| 리디렉션 막기를 뺐다 | 실패. 두 경우 모두 밖 서버에 요청(`/landing`, `/start-landing`)이 닿았다 |
| 권한 확인 거부를 뺐다 | 실패. 위치·알림 권한이 「허용」으로 나왔다 |
| 콘텐츠 보안 정책을 뺐다(iframe 막기는 둠) | 통과. iframe 이동은 iframe 막기가 잡았다 |
| 콘텐츠 보안 정책과 iframe 막기를 둘 다 뺐다 | 실패. 밖 서버에 `/frame` 요청이 닿았다 |

권한 확인 거부를 뺐을 때 권한이 「허용」으로 나온 것은, 고치기 전 코드(요청만 거부)에서도 같은 일이 일어났다는 뜻이다.

### 새 의존성의 라이선스

React·React DOM·Vite·@vitejs/plugin-react·Vitest·Electron·@types 패키지는 MIT, TypeScript는 Apache-2.0, @electron/packager는 BSD-2-Clause다(`npm view`로 확인). Electron은 Chromium을 함께 묶으며 그 고지(`LICENSES.chromium.html`)가 묶은 폴더에 들어 있다. 전이 의존성 전체는 확인하지 않았다.

### 확인하지 못한 것

- Chrome 같은 일반 브라우저로 화면을 직접 열어 보지는 않았다. Electron 안의 Chromium 152로만 봤다.
- 화면 컴포넌트를 띄워 선택 전환 경쟁을 재현하는 시험은 없다. 순수 함수 시험만 있다.
- Codex 검토 환경에서는 Electron이 시작하지 못해 거부 시험을 독립적으로 재현하지 못했다. 시험이 남긴 표준 오류에 따르면, 검토 샌드박스가 Electron 설치 폴더를 읽지 못하는 Windows 접근 권한(ACL) 문제였다. 거부 시험 통과는 작성자 실행 결과다.
- 서버가 처음 화면을 내주지 못하면(서버가 꺼져 있으면) 데스크톱 껍데기는 그냥 끝난다. 오류 화면은 1단계 본작업에서 만든다.
- 코드 서명, 설치 프로그램, 자동 업데이트, macOS·Linux 빌드, 접근성, 화면 디자인은 하지 않았다.
