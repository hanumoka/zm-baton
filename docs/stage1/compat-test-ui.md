# 1단계 설치·호환 시험 — Web·데스크톱 화면

**목적**: 먼저 시험할 화면 기술 후보(React + TypeScript, Electron)가 이 PC에서 서버와 연결 프로그램이 만든 실행 기록을 보여 줄 수 있는지 확인한다. 결과는 서버·연결 프로그램 시험([compat-test.md](compat-test.md))과 함께 기술 스택 최종 확정을 소유자에게 묻는 근거가 된다. 근거는 `zm-docs`의 DEC-0079 D8과 DEC-0087이다.
**대상 기기**: 소유자의 Windows 11 PC.

## 하는 것

가장 작게 이어 붙인다.

1. **서버 읽기 API 셋**(`apps/server`): 작업 목록, 한 작업의 실행 시도 목록(최근 것부터 최대 100개), 한 실행 시도의 사건 목록(`after_seq` 뒤의 것만). 실행 시도 목록에는 서버가 정한 상태·종료 이유·마지막 사건 시각이 들어 있다. 데이터 모델이 이 값들을 `runs`에 저장하기 때문이다.
2. **Web 화면**(`apps/web`, React + TypeScript, Vite)
   1. 작업 목록을 2초마다, 고른 실행 시도의 새 사건을 1초마다 묻는다. 고른 것이 바뀌면 옛 요청을 취소하고 늦게 온 옛 응답은 버린다.
   2. 사건은 두 가지로 묻는다. 받은 가장 큰 순번 뒤를 묻고, 빈 순번 구간은 따로 다시 묻는다. 빈 구간이 많으면 폴링마다 묻는 구간을 돌아가며 바꾼다. 서버는 큰 순번 뒤에 작은 순번을 저장할 수 있기 때문이다.
   3. 협업 계약 v1의 「보고 상태」를 보여 준다. 종료 여부와 종료 이유는 서버가 정한 값을 그대로 쓰고, 사건에서 다시 계산하지 않는다. 끝나지 않은 실행은 마지막 사건이 `error`이면 오류, 마지막 사건 뒤 10분이 지나면 응답 없음, 그 밖에는 작업 중이다.
   4. 계약 표의 두 규칙은 이 시험에서 판정하지 않고, 화면의 보고 상태 바로 아래에 「판정하지 않음」과 그 이유를 보여 준다. 「입력 필요」는 질문에 답이 왔는지 알아야 하는데 질문 경로가 아직 없다. 「첫 응답 기한 안에 사건이 없으면 응답 없음」은 청구 시각부터 재야 하는데 데이터 모델에 청구 시각 칸이 없다. 청구됐지만 사건이 없는 실행은 「첫 사건 대기」로 보여 준다. 질문 사건이 있거나 첫 사건을 기다리는 중이면 해당 줄을 강조한다.
   5. 사건 내용은 실행기 출력이므로 글자로만 보여 준다. HTML로 해석하지 않는다.
   6. 작업과 실행 시도를 만드는 입력란이 있다.
3. **서버가 화면을 함께 내준다**: `ZM_BATON_WEB_DIR`에 빌드한 화면 폴더를 주면 서버가 같은 주소에서 화면을 내준다. 화면과 API의 출처가 같아 CORS 설정이 필요 없다.
4. **데스크톱 껍데기**(`apps/desktop`, Electron)
   1. 서버가 내주는 화면을 창에 띄운다.
   2. 창에는 Node 기능을 주지 않는다(`contextIsolation`, `sandbox`, `nodeIntegration: false`).
   3. 서버 밖으로의 이동을 막는다. 직접 이동, 리디렉션, iframe 이동, 새 창이 모두 대상이다. 그래도 서버 밖 주소에 도착하면 서버 화면으로 되돌린다.
   4. 권한 요청·권한 확인·장치 권한을 모두 거부한다.
   5. 서버 응답에 콘텐츠 보안 정책을 더한다. 서버가 보낸 정책은 지우지 않는다.
   6. Windows 실행 파일 폴더로 묶는다(`@electron/packager`).

## 통과 기준

1. Web 화면의 타입 검사·단위 시험·빌드와 데스크톱 껍데기의 컴파일·묶기가 이 PC에서 된다.
2. 서버가 빌드한 화면과 그 자원 파일을 내준다.
3. 연결 프로그램이 실제 Claude Code를 돌리는 동안, 데스크톱 창의 보고 상태가 작업 중에서 완료로 바뀌고, 실행 시도 상태가 서버의 값(`ended/submitted`)과 같고, 사건 수가 서버에 저장된 수와 같다.
4. 데스크톱 창 안의 페이지에서 Node 기능(`require`, `process`)이 보이지 않는다.
5. 묶은 실행 파일이 같은 화면을 연다.
6. 거부 시험(`apps/desktop/test/probe.mjs`): 정해 둔 시나리오에서 밖 서버에 요청이 하나도 닿지 않고, 창이 서버에 머물고, 알림·위치 권한이 거부된다. 시나리오는 페이지가 시도하는 새 창·iframe·직접 이동·리디렉션, 그리고 처음 여는 주소의 리디렉션이다. 밖 서버가 실제로 요청을 받을 수 있는지는 먼저 확인한다(양성 대조). 이 시험이 모든 종류의 외부 통신이 막힌다는 것을 증명하지는 않는다.

## 하지 않는 것

인증과 로그인 화면, 작업 단계 바꾸기, 질문 답하기, 실시간 알림(WebSocket), TUI, 자동 업데이트·코드 서명·설치 프로그램, macOS·Linux 빌드, 접근성 점검, 화면 디자인. 이 시험 뒤 1단계 작업으로 한다.

## 기록할 것

- 도구 버전(Node, npm, React, TypeScript, Vite, Vitest, Electron, Chromium)
- 새 의존성의 라이선스
- 통과 기준별 결과와 실행한 명령
