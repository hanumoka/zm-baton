# 사람 검토 고르기 — AI 결과 가운데 사람이 볼 것만 받기

1단계 필수 기능 FN-0411이다. 사람은 AI 결과를 전부 볼 수 없다. 그래서 맡긴 AI 실행이 결과를 내면 서버가 그 결과를 고정하고 위험 목록과 대조한다. 위험 목록에 걸린 결과는 사람에게 보내고, 걸리지 않은 결과 가운데 일부를 표본으로 사람에게 보낸다. 나머지는 「사람 미확인」으로 남긴다. 사람은 첫 화면 「나를 기다리는 것」에서 승인하거나 반려한다. AI는 이 요청을 닫을 수 없다. 근거는 협업 계약 v1의 「사람에게 보낼 것을 고른다」와 「첫 화면 「나를 기다리는 것」」, DEC-0102, DEC-0105다(설계 허브 zm-docs).

- **대상**: 셋째 묶음([handoff.md](handoff.md))을 설치하고 작업을 AI에게 맡겨 본 소유자 PC 한 대. 서버는 이 PC의 `127.0.0.1`에서만 받는다.
- **소유자**: 저장소 소유자. 마지막 확인 2026-10-14.
- **전제**: 서버·연결 프로그램·웹을 이 판으로 함께 바꾼다. 결과를 고정하는 스냅샷 커밋은 새 연결 프로그램이 만든다. 옛 연결 프로그램의 결과는 「대상을 고정할 수 없음」이 된다.

## 무엇이 어디에 뜨는가

| 무엇 | 어디 |
|---|---|
| 위험 목록에 걸린 결과 | 첫 화면 4번 묶음 「위험 목록 검토」. 바로 알린다 |
| 표본으로 뽑힌 결과 | 첫 화면 5번 묶음 「표본 검토와 나머지 알림」. 하루 두 번 묶어 알린다(브라우저 알림은 묶음 알림을 아직 하지 않는다) |
| 24시간 넘게 기다린 검토 | 첫 화면 1번 묶음 자리로 올라오고 행에 「오래 기다려 위로 올림」 |
| 결과마다 사람 검토 상태와 자동 검사 상태 | 작업 상세 「실행 기록」의 「사람 검토 …」 줄. 예: 「사람 검토 사람 미확인」, 「자동 검사 안 함」 |
| 위험 경로 목록, 표본 비율·하루 상한, 목록 후보 | 사이드바 「위험 목록」(`http://127.0.0.1:18081/#risk`) |
| 결과의 스냅샷 커밋 | 그 저장소의 `refs/zm-baton/snapshots/<실행 시도 번호>`. 브랜치가 아니다 |

## 전제조건

- [handoff.md](handoff.md)의 1~4단계(서버·웹, `zm-baton` 명령, 저장소 등록, `zm-baton agent`)를 이 판으로 마쳤다.
- 맡길 작업은 「수행 준비」에 있는 여기서 만든 작업이다.

## 단계

### 1. 위험 목록을 확인한다

1. 사이드바에서 「위험 목록」을 연다.
2. 「조직 기본」을 고른다. 처음에는 zm-baton의 처음 목록(정책·권한·보안·CI·배포·마이그레이션 경로와 zm-docs에서 정한 경로) 32개가 있다.
3. 프로젝트를 고르면 그 프로젝트가 쓰는 목록이 보인다. 처음에는 「조직 기본 목록을 쓴다」.
4. 고칠 때는 한 줄에 패턴 하나를 쓰고 저장한다. 프로젝트 목록을 저장하면 그 프로젝트는 조직 기본 대신 자기 목록을 쓴다. 「조직 기본 목록으로 되돌리기」로 돌아간다.

패턴은 저장소 뿌리 기준 경로다. `/`가 없는 패턴(`AGENTS.md`)은 뿌리의 그 파일만, `**/AGENTS.md`는 어느 폴더의 것이든, `.github/**`는 그 폴더 아래 전부, `*`는 이름 일부(`/`를 넘지 않음)다. 대소문자를 가린다. 검토 기준의 경로 표와 같은 뜻이다.

### 2. 작업을 맡기고 결과를 기다린다

[handoff.md](handoff.md) 5단계대로 맡긴다. 실행이 결과를 내고 끝나면 서버가 바로 정한다.

1. **결과를 고정한다.** 연결 프로그램이 끝날 때 작업 트리의 내용(커밋한 것, 커밋하지 않은 것, 새 파일. `.gitignore` 대상은 빼고)을 커밋 객체 하나로 묶어 `refs/zm-baton/snapshots/<실행 시도 번호>`에 둔다. 작업 트리의 파일·인덱스·브랜치는 그대로다. 커밋하지 않은 변경이 없으면 브랜치 끝 커밋이 곧 스냅샷이다.
2. **위험 목록과 맞춘다.** 마지막 바뀐 파일 목록과 실행기 도구가 고친 파일 경로를 그 작업의 프로젝트 목록(없으면 조직 기본)과 맞춘다. 하나라도 걸리면 「위험 경로」 검토 요청을 만든다. 작업에 「추가 과금으로 멈춤」이 붙어 있으면 「추가 과금」 요청도 만든다.
3. **표본을 뽑는다.** 요청이 없고 고정된 결과면 표본 비율(처음 10건 중 1건)로 뽑는다. 뽑는 수는 실행 시도 번호로 계산하므로 나중에 같은 값을 다시 낼 수 있다. 그 사람에게 간 표본이 오늘(서버 시간대 0시부터) 상한(처음 5건)에 닿았으면 뽑지 않는다.
4. **나머지는 「사람 미확인」이다.** 실행 기록에 왜 보내지 않았는지(뽑은 수와 비율, 상한)가 보인다.

위험 검토가 열려 있는 동안 작업은 「결과 검토」에 머문다. 조직이 결과 검토를 건너뛰어도 그렇다. 「완료로 옮기기」는 잠기고 이유가 보인다. 표본 검토는 작업을 막지 않는다.

### 3. 첫 화면에서 승인하거나 반려한다

1. 「나를 기다리는 것」에서 4번이나 5번 묶음의 항목을 고른다.
2. 상세에서 왜 나에게 왔는지(걸린 패턴과 파일, 또는 표본), 실행 브랜치·기준·스냅샷 커밋·바뀐 파일을 본다. 변경 내용은 그 PC에서 `git diff <기준> <스냅샷>`으로 본다.
3. 「승인하기」나 「반려하기」를 누른다. 단추 아래 글이 그 판정이 무엇을 하는지 말한다. 반려는 이유를 적어야 보낼 수 있다.
4. 판정하면 그 항목이 목록에서 빠지고 다음 항목이 열린다. 목록 위에 판정 결과 한 줄과 「작업 열기」가 남는다.

판정이 하는 일:

| 판정 | 작업이 그때 | 하는 일 |
|---|---|---|
| 승인 | 결과 검토, 조직이 결과 검토를 건너뜀, 다른 열린 위험 검토 없음 | 작업이 완료로 넘어간다 |
| 승인 | 그 밖 | 승인을 기록한다. 결과 검토를 쓰는 조직은 사람이 「완료로 옮기기」를 누른다 |
| 반려 | 결과 검토이고 이 결과가 마지막 실행의 것 | 작업이 수행으로 돌아간다. 반려 이유가 다음 실행의 지시에 「돌려보낸 이유」로 들어간다. 작업 상세에서 「이어서 맡기기」를 누른다 |
| 반려(표본) | 완료 | 작업은 그대로 두고, 반려 이유를 수락 조건 초안으로 한 「고침: <제목>」 작업을 초안으로 새로 만든다 |
| 반려 | 그 밖(다른 단계로 옮겨졌거나 취소됨, 새 실행이 있음, 이미 한 번 돌려보냄) | 반려만 기록한다. 되돌리는 일은 사람이 한다 |

승인과 반려는 화면에서 본 스냅샷 커밋과 함께 간다. 그 사이에 새 실행이 결과를 내 요청이 대체됐으면 서버가 거절하고 「새 실행 결과로 대체된 요청이다」를 보인다. 승인은 승인 기록(`approvals`)에 사람의 승인으로 남는다.

### 4. 이어서 맡기고 다시 검토한다

반려로 작업이 수행으로 돌아갔으면 작업 상세의 「이어서 맡기기」로 다시 맡긴다. 새 실행이 결과를 내면 새 스냅샷으로 새 요청이 생긴다. 이전 실행의 요청이 아직 열려 있었으면 「새 판으로 대체됨」으로 닫히고 새 요청과 이어진다. 작업 상세에서 「돌려보내고 이어서 맡기기」를 바로 눌러도 같다.

### 5. 표본에서 놓친 종류를 목록 후보로 올린다

1. 표본을 반려할 때 「위험 목록 후보(선택)」 칸에 경로 패턴을 둔다. 바뀐 파일로 만든 제안(파일 하나면 그 파일, 여럿이면 공통 폴더 아래 전부)이 미리 들어 있다. 비우면 남기지 않는다.
2. 후보는 저절로 목록에 들어가지 않는다. 「위험 목록」 화면의 그 프로젝트(프로젝트 없는 작업이면 조직 기본)에 「표본 반려에서 올라온 후보」로 보인다.
3. 「목록에 더하기」를 누르면 그 목록에 더하고 감사 기록에 남는다. 그 프로젝트가 조직 기본을 쓰고 있었으면 조직 기본에 후보를 더한 목록을 자기 목록으로 갖게 된다. 「후보에서 빼기」는 더하지 않고 닫는다.

## 완료 확인

- 위험 경로를 고친 실행: 첫 화면 4번 묶음에 항목이 생기고, 작업이 결과 검토에 머물고, 실행 기록에 「사람 검토 기다림(위험 목록)」과 「자동 검사 안 함」이 있다.
- 승인한 뒤: 항목이 빠지고, 실행 기록이 「사람 검토 승인」, 결과 검토를 건너뛰는 조직이면 작업이 완료다.
- 위험 경로에 걸리지 않은 실행: 「사람 검토 사람 미확인」과 이유, 또는 5번 묶음의 표본 항목.
- 저장소에서 `git rev-parse refs/zm-baton/snapshots/<실행 시도 번호>`가 커밋을 돌려주고, `git diff --name-only <기준> <그 커밋>`이 실행 기록의 바뀐 파일과 같다.

## 실패하면

| 증상 | 원인과 대응 |
|---|---|
| 상세에 「대상을 고정할 수 없음」 | 연결 프로그램이 옛 판이거나 스냅샷을 만들지 못했다(연결 프로그램 창의 경고를 본다). 승인은 되지만 승인 기록에 「대상 고정 안 됨」(`unpinned:`)이 남는다. 이런 결과는 표본에서 빠진다. 연결 프로그램을 이 판으로 바꾼다 |
| 「완료로 옮기기」가 잠기고 「마지막 결과에 열린 위험 목록 검토가 있다」 | 첫 화면에서 그 검토를 승인하거나 반려한다 |
| 반려가 「결과를 돌려보내는 반려에는 작업의 work_version이 필요하다」나 「the work item changed」로 거절됨 | 다른 화면에서 작업이 바뀌었다. 목록을 다시 읽고 판정한다 |
| 「화면에서 본 대상과 지금 대상이 다르다」 | 새 실행 결과가 들어왔다. 목록을 다시 읽어 새 요청을 본다 |
| 표본이 하나도 오지 않는다 | 「위험 목록」 화면의 조직 기본에서 표본 비율과 하루 상한을 본다. 0%면 뽑지 않는다 |
| 위험 목록 저장이 「위험 경로 패턴이 맞지 않다」로 거절됨 | 이유 문장의 패턴을 고친다. 절대 경로, 역슬래시, 공백, `..`, `/`로 끝나는 패턴은 받지 않는다 |
| 세션 토큰으로 판정하려다 403 | 사람의 일이라 세션 토큰으로 할 수 없다(감사 기록 `person_action.refused`). 웹에서 한다 |

## 이 판이 하지 않는 것

- 직접 연 세션이 위험 경로를 고쳤을 때의 사후 검토 요청(계약 「위험 목록을 판정한다」 3번). 그 세션의 `file_touch`를 위험 목록과 맞추는 일은 다음 판에서 한다
- AI가 정책·권한·보안에 닿는다고 판단해 요청을 더하는 것(`ai_raised`, 1단계 마스터)과 검토 AI(2단계)
- 되돌릴 수 없는 동작·운영 배포 요청. 1단계의 외부 동작은 로컬 커밋뿐이고, 승인이 필요한 명령은 권한 요청 중계가 맡는다
- 결과 제출에 실린 시험 결과로 자동 검사 상태를 정하는 것. 지금은 늘 「자동 검사 안 함」(`not_run`)이다
- 「내가 책임자인 영역은 모두 본다」 개인 설정(DEC-0102 2.5)
- 저장소마다 다른 프로젝트 목록. 데이터는 저장소별 항목을 받지만 화면은 프로젝트의 모든 저장소에 쓰는 목록 하나만 고친다
- 묶음 알림(하루 두 번)의 실제 알림. 첫 화면에는 바로 놓인다

## 알아 둘 점

- **사람 검토 상태와 자동 검사 상태를 따로 둔다**: 사람 검토는 `required`(위험 요청 열림)·`sampled`(표본 요청 열림)·`reviewed`(요청이 있었고 모두 닫힘)·`not_reviewed`(사람 미확인) 넷이고, 대체된 요청은 세지 않는다. 자동 검사는 `passed`·`failed`·`not_run`이다. 「사람 미확인」 결과를 검토한 것처럼 보이지 않는다.
- **판정 기록**: 서버가 결과마다 판정 근거(`runs.review_basis`: 맞춘 목록, 걸린 패턴과 파일, 뽑은 수·비율·상한·규칙 판 `sample.v1`)를 남기고 감사 기록 `review.judged`에도 같은 것을 쓴다. 뽑은 수는 `sha256("sample.v1|<실행 시도 번호>")`의 앞 53비트를 0~1로 바꾼 값이다.
- **AI는 닫지 못한다**: 판정 API는 사람의 일이라 세션 토큰을 거절하고 감사 기록에 남긴다. 서버 안에서도 사람이 아닌 주체의 판정은 거절하고 `review.close_refused`를 남긴다. 위험 목록을 고치는 API도 사람의 일이다.
- **숫자(작성자가 정한 시작값)**: 표본 10건 중 1건, 하루 5건, 24시간 뒤 위로 올림(1분마다 확인). 표본 비율과 상한은 「위험 목록」 화면에서 바꾼다. 위로 올리는 시간은 조직 설정 `review_promote_after_hours`에 있고 화면에서는 바꾸지 않는다.

## 정리

- 스냅샷 커밋은 `refs/zm-baton/snapshots/` 아래에 실행마다 하나씩 남는다. 지우려면 `git update-ref -d refs/zm-baton/snapshots/<실행 시도 번호>`를 쓴다. 지우면 그 결과의 검토 대상을 다시 볼 수 없다.
- `V10`은 되돌리는 마이그레이션이 없다. 이 기능을 통째로 떼려면 [handoff.md](handoff.md) 「정리」처럼 데이터베이스 볼륨까지 지우고 옛 판으로 다시 띄운다.
