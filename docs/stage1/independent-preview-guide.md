# 독립 서버 시험판 확인과 반영

**목적**: 독립 서버 시험판에서 무엇을 확인하고 어떤 범위까지 반영할지 정한다.
**대상·소유자**: 서버 관리자·조직 구성원 / hanumoka.
**마지막 검토**: 2026-10-18.
**2026-10-18 검증 시점의 상태**: `work/preview-final`의 누적 시험판(서버 기능 `9e2915b`, 화면 `f73cb9d`). 이 시점에는 기본 브랜치 병합·기존 운영 적용 전이며, 이후 승인·반영 여부는 PR #53에서 확인한다.

## 제공하는 기능

한 서버에 한 조직을 설치한다. 별도 문서 저장소나 개발용 대화 세션 없이 조직과 계정을 만들고, 웹에서 요청한 작업을 백그라운드 실행 작업자가 처리한다.

| 사용하는 사람 | 하는 일 | 확인할 결과 |
|---|---|---|
| 최초 설치자 | 일회성 코드로 첫 비밀번호를 정하고 조직·관리자 이름을 입력. 업그레이드는 기존 이름을 확인 | 최초 설정은 한 번 성공하며 재시작해도 유지 |
| 서버 관리자 | 서버 관리 상태 확인, 다른 활성 구성원에게 관리 이전 | 조직 소유권·업무 역할은 그대로이며 이전 관리자는 서버 관리 권한을 잃음 |
| 조직 운영자 | 구성원·역할·로그인 코드·활성 상태 관리 | 정지하면 웹 로그인·기기 자격·AI 세션이 폐기됨 |
| 구성원 | 작업 요청·AI 위임·실행 취소·결과 확인·이어 맡기기 | 실행 이력과 결과가 서버에 남고 브라우저를 닫아도 실행 지속 |
| 서버 운영 담당자 | 백업·복원·업데이트·실행 작업자 서비스 운영 | DB와 서버 판을 함께 보존하고 복제 환경에서 먼저 확인 |

서버 관리자가 된다는 이유로 다른 사람의 개인 메모나 비공개 자료를 읽을 수 있지는 않다. 마스터 작업에 복사된 원본도 현재 열람 권한을 적용한다. 여러 조직을 하나의 서버에서 전환하거나 고객에게 서버를 자동 발급하는 상위 호스팅은 이번 범위에 없다.

## 10~15분 확인 절차

전제조건: 소유자에게 전달한 **격리 시험판 주소**를 사용한다. 합성 조직·구성원·저장소이며 기존 운영 주소와 다르다. 로그인 정보는 별도로 지정한 로컬 비공개 파일에서 읽는다. 조직 API 자격은 준비되지 않았다면 마지막 항목으로 남긴다.

1. 로그인한 뒤 「나」에서 본인 계정·기기를 확인하고 「서버 관리 열기」를 누른다. 조직 이름·현재 관리자·최초 설정이 보이는지 확인한다.
2. 「조직」에서 구성원·역할·로그인 관리가 보이는지 확인한다. 필요하면 시험 구성원을 추가하고 일회성 로그인 코드를 발급한다. 코드나 비밀번호는 검토 댓글에 붙이지 않는다.
3. 별도 브라우저 프로필에서 시험 구성원으로 로그인한다. 그 사람의 개인 메모와 개인 업무를 관리자 화면에서 볼 수 없는지 확인한다.
4. 서버 관리 화면에서 넘겨받을 구성원을 선택하고 이전 결과를 확인한 뒤 「서버 관리 넘기기」를 실행한다. 이전 관리자는 관리 화면을 사용할 수 없어야 한다. 새 관리자로 들어가 원래 관리자에게 돌려놓는다. 조직 소유권은 별개다.
5. 「작업」에서 시험용 작업을 만들고, 준비 단계에서 「AI에게 맡기기」를 연다. 등록된 시험 저장소와 읽기 전용 도구를 골라 README의 확인 문구를 읽도록 맡긴다. 본인 구독 시험은 본인 자료에만 사용한다.
6. 브라우저를 닫았다가 다시 열어 실행 이력과 제출 결과를 확인한다. 작업자는 별도 프로세스이므로 개발용 Codex·Claude 대화 세션이 실행을 붙들고 있지 않는다.
7. 실행 중 「실행 취소」와 끝난 뒤 「이어서 맡기기」의 설명을 확인한다. 종료가 확인된 실행은 이전 작업 트리·CLI 세션을 재사용할 수 있고, 확인되지 않은 실행은 이전 브랜치에서 새 작업 트리를 만든다. 결과를 자동으로 기본 브랜치에 합치지는 않는다.
8. 조직용 API 자격을 사용할 서버에 준비한 뒤, 별도의 API 계정과 `--server-worker`로 위 흐름을 다시 실행한다. 본인 구독 성공이나 모의 시험으로 이 항목을 완료 처리하지 않는다.

완료 확인: 소유자가 화면·임시 정책·배포 대상을 선택하고 실제로 확인한 결과만 기록한다. AI가 소유자의 이해·재현 기록을 대신 쓰지 않는다. 4주 사용 기간을 채우는 조건은 없다.

실패 대응: 해당 실행 번호와 화면의 오류만 남기고 기존 운영 적용을 멈춘다. 로그·브라우저 상태에는 자격이 있을 수 있으므로 원본 전체를 공개하지 않는다. 시험판 재시작은 전달한 전용 절차를 사용한다.

시험 데이터·비밀번호·공급자 로그인·DB 백업을 이 문서에 포함하지 않는다. 서버 검증은 Corretto 25.0.4.1 / Gradle 9.7.1 / PostgreSQL 17, 웹은 Node.js 24.16.0 / TypeScript 7.0.2 / Vite 8.3.2다. 실제 AI 실행기는 공식 Claude Code 2.1.302다.

[민감 자료를 제외한 실행·복원 결과](../reviews/assets/2026-10-18-runtime-proof/results.json), [Windows 실행 정책 시험](../reviews/assets/2026-10-18-runtime-proof/agent-review-windows.txt), [CLI 종료 78 시험](../reviews/assets/2026-10-18-runtime-proof/cli-review-windows.txt)에 근거를 보존했다. 전체 로그와 백업의 공개 사본은 만들지 않았다.

현재 코드의 Linux 종료는 실행기 본체만 대상으로 한다. macOS는 표식을 확인하지 못해 본체 종료도 거절한다. 대상 서버에 설치하기 전에 [H-16과 관련 후보](../hardening-backlog.md)를 검토하고 그 OS에서 확인해야 한다. 원본 권한은 실행 청구 직전까지 확인하며 이미 실행기에 전달한 내용의 회수는 보장하지 않는다.

## 최종 확인할 임시 정책

| 선택 | 현재 시험판 | 다른 선택의 영향 |
|---|---|---|
| 서버 관리자 수 | 한 명, 다른 활성 구성원에게 이전 | 여러 명이면 마지막 관리자 보호·권한 부여/회수 확대 필요 |
| 조직 소유자와 서버 관리자 | 처음에는 같고 이후 서버 관리만 이전 가능 | 처음부터 별개이면 두 계정의 초기 설정 순서 필요 |
| 구성원 정지 | 웹·기기·AI 세션과 미사용 설정/승인 자격 폐기 | 원격 프로세스 즉시 종료는 네트워크·OS에 따라 한계가 있음 |
| 재활성화 | 기존 비밀번호 유지, 다시 로그인·기기 연결 | 비밀번호까지 폐기하려면 새 설정 코드 발급 필요 |
| 질문과 마스터 원본 | 원본을 볼 수 없는 수신자·실행자를 거절 | 별도 자료 공유·실행 주체의 권한 설계가 필요 |
| 초기 설정·관리 화면 | A 배치를 임시 적용, A/B/C 비교 자료 제공 | 다른 안이면 해당 화면의 배치·검증 재실행 |
| 첫 배포 대상 | 이 PC의 격리 시험판은 검증됨 | 조직 API와 대상 OS 서비스 검증 후 운영 범위 선택 |

## 승인 뒤 반영하기

전제조건: 소유자의 정책 선택과 병합·운영 적용 범위가 기록되고, 반영할 최종 커밋의 독립 검토·CI를 확인한다. 여러 초안 PR은 개발·검증 근거다. 반영할 누적 변경에는 독립 검토의 막는 지적 수정이 모두 포함돼야 한다.

1. 대상 설치의 DB 접속 설정·인증 모드·현재 이미지 ID·볼륨 이름을 비공개로 기록한다. 다른 설치와 구별한다.
2. [백업·복원·업데이트](backup-restore-update.md)의 백업 명령으로 적용 전 덤프와 해시를 만든다. 별도 볼륨에 복원하고 선택한 서버 판으로 시작해 마이그레이션·로그인·관리자·자료를 확인한다.
3. 기존 이미지에 별도 태그를 붙이거나 이미지 ID를 보존한다. DB 백업과 그때의 서버 판을 한 쌍으로 기록한다.
4. 승인된 최종 판으로 [업데이트 절차](backup-restore-update.md)를 실행한다. V15·V16이 필요하다. 기존 데이터의 ID·조직·소유자는 보존한다.
5. 처음 인증을 켜는 기존 `local` 설치는 [인증 절차](auth.md)대로 별도로 전환한다. 마이그레이션만으로 인증 모드가 바뀌지는 않는다. 설정 코드 사용 뒤 복구 환경 변수를 지운다.
6. [서버 작업자](server-worker.md)를 전용 OS 계정·기기·저장소·조직 API 계정으로 설치한다. 실행별 턴·시간·비용 상한을 정하고 실제 작업 한 건을 확인한다.
7. `/actuator/health`, 로그인·관리자, 기존 자료, 작업 요청·취소·재개, 백업 파일의 생성을 확인한다. 실패하면 새 요청을 멈추고 아래 절차를 따른다.

이 절차가 서버를 외부 주소에 자동 공개하는 것은 아니다. 현재 Compose는 loopback에 바인딩하며 외부 운영은 [인증과 TLS](auth.md)의 전제조건과 대상 OS 검증을 갖춘 뒤 선택한다.

## 되돌리기

전제조건: 업데이트 직전 DB 백업과 당시 서버 이미지가 있고, 소유자가 되돌림으로 잃을 업데이트 이후 기록의 범위를 확인했다.

1. 새 작업 요청을 멈추고 실행 중인 작업의 결과·브랜치를 확인한다. 작업자·서버·정기 백업을 중지한다.
2. 실패한 새 DB도 조사용으로 별도 백업한다. 원본 백업을 덮어쓰지 않는다.
3. [복원 절차](backup-restore-update.md)로 업데이트 직전 DB를 복원하고 **그 백업과 짝인 이전 이미지**로 시작한다. V16 DB에 이전 코드만 연결하지 않는다. 인덱스 충돌 조건이 달라 이전 SQL이 실패할 수 있다.
4. 건강 상태·DB 마이그레이션 판·인증 모드·작업과 결정 건수·로그인을 확인한다. 정상일 때 작업자와 정기 백업을 다시 시작한다.
5. 복원도 실패하면 볼륨을 지우지 않고 중지 상태에서 원본 백업·해시·오류를 보존한다. 검증된 다른 복제본과 대조한다.

일회성 시험은 정지한 PostgreSQL 17의 물리 백업과 같은 주 버전에서 실제 되돌리기를 확인했다. 일반 업데이트에는 문서의 `pg_dump`·`pg_restore` 절차를 쓴다. 실행기의 작업 트리·로컬 설정·공급자 자격은 DB 덤프에 들어 있지 않으므로 서버 운영자가 별도로 보존한다.
