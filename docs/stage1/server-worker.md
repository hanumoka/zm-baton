# 서버에서 맡긴 작업 실행하기 — 시험판

**목적**: 사용자의 대화형 터미널과 독립된 실행 프로세스를 서버에서 운영한다.
**대상**: 서버 관리자·조직 운영자.
**소유자·마지막 검토**: hanumoka · 2026-10-18.
**상태**: 최종 확인 전의 공용 서버 실행 제안. systemd 설치는 대상 서버에서 검증해야 한다.

웹/API 서버와 실행 작업자는 별도 프로세스다. 실행 작업자는 기존 Go 연결 프로그램을
`zm-baton agent --server-worker`로 띄운다. 사람이 브라우저를 닫거나 개발용 Codex·Claude 대화를 끝내도
실행 작업자는 요청을 받으며, 필요한 때 공식 Claude Code CLI를 직접 시작한다.
실행 서버는 웹/API 서버와 같은 머신이거나 별도 머신일 수 있다.

## 전제조건

- 로그인 필수 모드의 zm-baton 서버. 외부 연결은 [인증·TLS 절차](auth.md)를 먼저 적용한다.
- 실행 서버의 전용 OS 사용자, Git, 이 판의 `zm-baton`과 지원하는 공식 Claude Code CLI.
- 조직 사용이 허용된 API 키. 사람이 서버에 직접 준비하며 웹이나 저장소에 넣지 않는다.
- 체크아웃한 허용 저장소와 실행별 작업 트리 폴더. OS 임시 폴더 안에 두지 않는다.
- API 계정별 실행 턴·시간·비용 상한. 서버 모드는 셋 중 하나라도 없으면 실행 전에 거절한다.

개인 구독 로그인을 공용 서버의 대체 자격으로 사용하지 않는다.
`--server-worker`는 계정이 빠진 옛 요청, 구독 계정, 전용 설정 폴더가 없는 실행을 거절한다.
API 키가 없으면 명확한 준비 실패를 보고한다. 모의 실행 결과는 실제 AI 검증을 대신하지 않는다.

## 등록과 실행

1. 실행 전용 사용자로 `ZM_BATON_HOME`을 지속 저장 폴더로 정한다.
2. `zm-baton login --server https://baton.example.org --name server-worker`를 실행한다.
   출력된 기기 코드를 관리자가 웹에서 승인한다. 받은 기기 토큰은 그 폴더에만 저장한다.
3. `zm-baton repo add --worktrees /srv/zm-baton/runs /srv/zm-baton/repository`로 저장소를 등록한다.
4. 웹의 AI 계정에서 `api_key` 계정을 등록한다. 이 기기에 연결하고 턴·시간·실행 비용·하루 비용 상한을 정한다.
   자격 위치는 값이 아니라 `env:ANTHROPIC_API_KEY`라는 이름이다.
5. 실행 프로세스 환경에 `ANTHROPIC_API_KEY`를 준비하고 `zm-baton agent --server-worker`를 실행한다.
6. 웹에서 수행 준비 상태의 작업을 만들고 「AI에게 맡기기」에서 서버의 저장소와 API 계정을 고른다.
7. 실행 기록과 결과 검토, 남은 작업 트리의 변경 내용을 확인한다. 결과를 자동으로 병합하지 않는다.

실행기는 허용한 도구만 사용한다. 현재 도구는 읽기·찾기·파일 수정이며 셸 명령 실행은 없다.
서버 작업자는 한 번에 한 작업을 실행한다. 기기를 여러 대 두면 각자의 위임을 처리한다.
서비스를 띄웠다는 사실만으로 모든 저장소를 읽게 되지 않는다. 등록한 저장소의 위임만 가져간다.

## Linux 서비스 예시

[`zm-baton-worker.service`](../../deploy/worker/zm-baton-worker.service)는 systemd 예시다.
실제 경로·OS 사용자·API 키 파일은 설치 환경에 맞춰 준비한다. 예시를 복사하기 전에 내용을 검토한다.

1. `zm-baton-worker` OS 사용자와 `/srv/zm-baton`, `/var/lib/zm-baton-worker`를 만들고 해당 사용자만 쓰게 한다.
2. 위 등록 절차를 그 사용자로 마친다. CLI 두 개는 `/opt/zm-baton/bin/`에 둔다.
3. [`worker.env.example`](../../deploy/worker/worker.env.example)을 참고해 `/etc/zm-baton/worker.env`를 만든다.
   root만 읽고 쓸 수 있는 파일에 조직 키를 준비한다. 예시 파일에는 키가 없다.
4. unit 파일을 `/etc/systemd/system/`에 설치하고 `systemctl daemon-reload`를 실행한다.
5. `systemctl enable --now zm-baton-worker`로 시작한다. `systemctl status zm-baton-worker`와 서버의 실행 기록을 확인한다.

service는 사람이 로그인한 세션과 무관하게 시작하고 실패 시 다시 시작한다.
기기 인증 거절(종료 코드 78)이나 잘못된 설정(2)은 재시작을 반복하지 않는다.
관리자가 기기를 다시 승인하거나 설정을 고친 뒤 서비스를 시작한다.

## 취소·재시작·실패 처리

- 웹의 실행 취소는 다음 실행 권리 갱신(통상 5초) 때 정지를 요청한다. 현재 실행기와 자식 프로세스의 종료 확인은 Windows에서 검증했다. Unix 자식 프로세스 처리는 H-16에 남아 있다.
- 기기 토큰 폐기·구성원 비활성화로 인증이 거절돼도 정지를 요청한다. AI 계정 비활성화와 구성원 정지는 서로 다른 정책이다. 끊긴 네트워크의 원격 프로세스를 즉시 종료한다고 보장하지 않는다.
- API 서버를 재시작하면 연결 프로그램이 재연결한다. 기존 실행 권리·재연결 유예 규칙을 따른다.
- 실행 작업자 자체가 비정상 종료되면 서버는 실행 권리 만료 후 결과를 알 수 없는 실행으로 구분한다.
  사용자가 결과와 작업 폴더를 확인하고 「이어서 맡기기」를 선택한다. 무조건 재실행하지 않는다.
- 같은 실행기를 두 번 시작해도 실행 권리 청구에 성공한 쪽만 실행한다. 운영에서는 서비스 하나를 사용한다.
- 종료 확인 기록이 있는 실행만 이전 작업 트리와 CLI 세션을 이어 쓴다. 확인되지 않으면 기존 폴더를 보존하고 새 작업 트리를 쓴다.

## 검증 범위

`go test ./...`와 `ServerWorker` 시험은 자격·상한 거절과 실행 경로를 모의 실행기로 검사한다.
실제 검증에서는 별도로 웹에서 작업을 요청하고 브라우저를 닫은 뒤 AI가 파일을 읽고 결과를 서버에 남기는지 확인한다.
개인 구독을 쓰는 소유자 본인의 시험은 개인 연결 프로그램 경로의 증거다. 조직 API와 `--server-worker`의 실제 성공으로 계산하지 않는다.
대상 OS의 서비스 시작·종료·자동 재시작은 설치 환경에서 추가 확인한다.
