# 작업과 결정 기록 — 1단계 둘째 묶음 쓰기

1단계 둘째 묶음이다. 웹 화면에 「작업」과 「결정」 탭이 생긴다. zm-docs의 작업 목록(`registry/tasks.json`)과 결정 기록(`docs/governance/decisions/`)을 서버로 가져와 보여 주고, 여기서 만든 작업은 단계를 넘기며 쓴다. 근거는 협업 계약 v1의 「작업」 절과 기능 명세의 FN-0201(작업 단계와 대기 사유), FN-0604(결정 기록), FN-1004(zm-docs 옮기기)다(설계 허브 zm-docs).

- **대상**: 첫 묶음([sessions.md](sessions.md))을 설치한 소유자 PC 한 대. 서버는 이 PC의 `127.0.0.1`에서만 받는다.
- **소유자**: 저장소 소유자. 마지막 확인 2026-10-13.
- **전제**: 서버(`work/tasks-server`)·`zm-baton` 명령(`work/tasks-cli`)·웹(`work/tasks-web`) 세 PR이 모두 `main`에 들어간 판에서 따른다.

## 가져온 것과 여기서 만든 것은 다르게 동작한다

zm-docs에서 가져온 작업과 결정은 **정본이 Git 파일인 복사본**이다. 기존 Git 문서는 Git이 정본으로 남는다는 기준(G20.1)과, 1단계 결정 기록은 Git에서 고친다는 기능 명세(FN-0605)를 따른다.

1. 가져온 작업(`TSK-` 번호)과 결정(`DEC-` 번호)은 웹에서 고치거나 단계를 넘길 수 없다. 단추는 보이지만 눌리지 않고, 그 이유가 화면에 나온다.
2. 원본을 고치고 커밋한 뒤 `zm-baton import zm-docs --apply`를 다시 실행하면 복사본이 바뀐다. 무엇이 바뀌었는지는 작업의 이력에 「원본에서 다시 가져옴」으로 남는다.
3. 웹의 「새 작업」으로 만든 작업은 정본이 zm-baton이다. 여기서 고치고 단계를 넘긴다.

정본을 zm-baton으로 옮기는 일(zm-docs의 작업을 여기서 운영하기)은 이 묶음이 하지 않는다. 소유자가 써 본 뒤 zm-docs의 결정으로 정한다.

## 무엇이 어디에 뜨는가

| 무엇 | 어디 |
|---|---|
| 「작업」 탭: 지금 누가 들고 있나로 묶은 목록, 작업 상세(단계 경로·다음 행동·대기 사유·다음 단계 단추·이력), 새 작업, 검토 단계 설정 | `http://127.0.0.1:18081/#work` |
| 「결정」 탭: 상태로 묶은 결정 목록(정할 것·지금 유효·지난 것), 거르기 칩(프로젝트·상태·지난 것 보기), 입력줄로 번호·질문·결정 찾기, 결정 상세(고른 안·대체 관계·나머지 절·정본 파일·이 번호를 적은 작업. 본문의 Markdown 굵게·목록·표를 그려 보이고, 다른 결정 파일 링크를 누르면 그 결정을 연다) | `http://127.0.0.1:18081/#decisions` |
| 가져오기 명령 | `zm-baton import zm-docs` |
| 세션 상태 카드 | zm-docs에서 Claude Code를 열면 열린 작업의 「다음:」 줄과 「이 저장소의 최근 결정」 다섯 건이 더해진다 |

### 단계와 검토 단계 설정

작업 단계는 계약의 일곱 값이다. 초안 → 계획 검토 → 수행 준비 → 수행 → 결과 검토 → 완료, 그리고 취소다.

1. 1인 조직은 두 검토 단계(계획 검토, 결과 검토)를 쓰지 않는 것으로 시작한다. 그래서 「수행」에서 「완료로 옮기기」(결과 검토 건너뜀) 단추 하나로 끝난다.
2. 「작업」 화면의 거르기 칩 줄 끝 「검토 단계」 단추를 눌러 「계획 검토 쓰기」나 「결과 검토 쓰기」를 켜면 그 단계에서 멈춘다. 이 설정은 감사 기록에 남는다.
3. 결과를 돌려보내기(결과 검토 → 수행)와 다시 계획하기에는 이유를 적어야 한다.
4. 바꾸는 요청마다 화면이 본 판(`version`)을 함께 보낸다. 그사이 다른 곳에서 바뀌었으면 거절되고, 화면이 다시 읽는다.

### 대기 사유

사람이 직접 붙이고 떼는 것은 둘이다. 「다른 사정으로 막힘」(무엇을 기다리는지 적어야 한다)과 「선행 작업 대기」다. zm-docs의 `blocked` 작업은 「다른 사정으로 막힘」과 `blocker` 문장으로 가져온다. 나머지 대기 사유(결과 확인 필요, 한도 리셋 대기 등)는 서버가 실행 보고로 붙이는 것이라 사람이 떼지 않는다.

## 전제조건

- 첫 묶음이 설치돼 돌고 있다(서버·웹이 Docker `zm-baton-dev`로 실행 중, `zm-baton login`을 마침).
- zm-docs 체크아웃이 이 PC에 있다. 가져오기는 그 체크아웃의 **커밋된 내용**을 읽는다. 커밋하지 않은 수정은 가져가지 않는다.
- PowerShell에서 `$repo`에 이 저장소 루트, `$docs`에 zm-docs 체크아웃 루트를 담는다.

## 단계

### 1. 서버와 웹을 새 판으로 다시 띄운다

```powershell
cd $repo
git pull --ff-only
docker compose -f deploy/compose/compose.yaml --profile app up -d --build
```

서버가 뜰 때 데이터베이스 구조 변경 `V3`(표와 칸 추가만, 지우는 것 없음)이 한 번 적용된다. 이미 있던 세션·알림 기록은 그대로다.

### 2. `zm-baton` 명령을 새 판으로 바꾼다

첫 묶음 안내서 3단계의 첫 네 줄과 같다. 실행 중인 Claude Code 세션의 훅이 잠깐 실패할 수 있으니, 세션을 닫은 뒤 바꾸는 것이 안전하다.

```powershell
cd $repo/apps/agent
docker run --rm -v "${PWD}:/src" -w /src -e GOOS=windows -e GOARCH=amd64 golang:1.27 go build -o bin/zm-baton.exe ./cmd/zm-baton
Copy-Item bin/zm-baton.exe "$env:LOCALAPPDATA/zm-baton/bin/"
```

### 3. 무엇이 들어갈지 먼저 본다

```powershell
zm-baton import zm-docs --repo $docs
```

서버를 바꾸지 않고 보고만 받는다. 프로젝트·작업·결정 기록마다 새로·바뀜·그대로·건너뜀 수가 나오고, 바뀌는 것과 경고가 이어진다. 읽은 커밋 번호도 나온다.

### 4. 가져온다

```powershell
zm-baton import zm-docs --repo $docs --apply
```

같은 커밋으로 다시 실행하면 전부 「그대로」가 나온다. 원본을 고쳐 커밋한 뒤 다시 실행하면 바뀐 것만 바뀐다.

### 5. 써 본다

1. `http://127.0.0.1:18081/#work`를 연다. 작업이 기다림·AI 세션·사람으로 묶여 보인다. 가져온 작업을 누르면 정본이 Git 파일이라는 안내와 눌리지 않는 단추가 보인다.
2. 「새 작업」으로 작업을 하나 만든다. 「수행으로 옮기기」, 「막힘 표시」, 「완료로 옮기기」를 눌러 보고 이력을 본다.
3. `http://127.0.0.1:18081/#decisions`를 연다. 결정이 정할 것·지금 유효·지난 것으로 묶여 보이고, 맨 위의 입력줄에 번호나 낱말을 쓰면 찾는다. 「지난 것 보기」를 켜면 대체되거나 기각된 결정이 보인다. 상세의 「대체 관계」를 누르면 그 결정으로 가고, 브라우저의 뒤로 가기로 돌아온다.
4. zm-docs에서 Claude Code를 새로 열어 처음에 뜨는 상태 카드에 「다음:」 줄과 「이 저장소의 최근 결정」이 있는지 본다.

## 완료 확인

- 3단계 보고의 작업·결정 수가 zm-docs의 `registry/tasks.json` 작업 수와 결정 문서 수와 같다.
- 4단계를 두 번 실행하면 두 번째는 바뀜 0이다.
- 웹의 「새 작업」으로 만든 작업이 「완료」까지 가고 이력에 단계마다 한 줄씩 남는다.

## 실패하면

1. **`this device is not registered yet`**: 첫 묶음 4단계의 `zm-baton login`을 먼저 한다.
2. **`is not inside a Git checkout` 또는 `is this a zm-docs checkout?`**: `--repo`가 zm-docs 체크아웃 안의 폴더를 가리키는지 본다. 가져오기는 그 커밋에 `registry/tasks.json`·`registry/projects.json`·결정 문서가 있어야 한다.
3. **`HTTP 404`**: 서버가 아직 옛 판이다. 1단계를 다시 한다.
4. **경고가 나온다**: 경고는 그 항목만 건너뛰었다는 뜻이고 나머지는 들어간다. 원본의 머리말(`id`·`title`·`status`)이나 프로젝트 번호를 고친 뒤 다시 가져온다.
5. **화면 위에 「「작업」을 읽거나 바꾸지 못했다」가 뜬다**: 서버가 멈췄는지 `zm-baton status`로 본다.

## 정리

가져온 복사본만 지우는 명령은 아직 없다. 둘째 묶음을 통째로 떼려면 서버를 첫 묶음 판으로 되돌려야 하는데, `V3`은 되돌리는 마이그레이션이 없다. 데이터베이스까지 처음부터 다시 만들려면 아래처럼 볼륨을 지운다. 세션·알림·작업·결정 기록이 모두 지워지고, 다음에 띄울 때 빈 데이터베이스로 시작한다. 지우기 전에 `pwsh "$repo/deploy/compose/backup.ps1"`로 백업해 두면 [backup-restore-update.md](backup-restore-update.md)의 「복원하기」로 되돌릴 수 있다.

```powershell
cd $repo
docker compose -f deploy/compose/compose.yaml --profile app down -v   # -v: 볼륨 zm-baton-pg까지 지운다
```

## 이 묶음이 하지 않는 것

- zm-docs 작업의 정본을 zm-baton으로 옮기기, zm-baton에서 고친 것을 `registry/tasks.json`으로 내보내기
- 결정 기록을 웹에서 쓰거나 고치기(1단계는 Git에서 고친다)
- 질문과 재협의(FN-0210), 위임·승인·업무 기준, 실행 시도가 수락될 때 작업을 「수행」으로 넘기기
- 결정과 어긋나는 작업·문서를 찾는 모순 후보 알림(마스터)
- 권한 요청과 선택형 질문을 첫 화면에서 답하기, Codex 세션 등록

## 알아 둘 점

- zm-docs 세션은 zm-docs 자신의 시작 훅으로도 `registry/tasks.json`의 열린 작업을 받는다. 그래서 병행하는 동안 Claude Code 세션 맥락에 열린 작업 목록이 둘 들어간다. 가져오기를 다시 하지 않으면 zm-baton 쪽이 오래된 목록이 된다.
- 닫힌 날(`closed`)은 날짜만 있어서 그날 0시(UTC)로 저장한다.
- 결정 상세의 「이 번호를 적은 작업」은 작업 찾기(제목·번호·다음 행동)에 결정 번호를 넣어 찾은 것이다. 서버에는 결정과 작업을 잇는 기록이 없어서, 작업 글에 번호를 적지 않은 관련 작업은 보이지 않는다.
